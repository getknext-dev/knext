Put a CDN you run in front of your app with `cdn` in `knext.config.ts`, for example `cdn: { provider: "cloudflare", htmlTTLSeconds: 30 }`. The CLI sends it as `spec.cdn` on the NextApp resource and the operator hands it to the runtime as `KNEXT_CDN_*` environment variables; knext never creates or configures the CDN. You can set `provider` (`cloudflare`, `google-cloud-cdn`, `cloudfront`, `azure-front-door`), the edge TTL (`htmlTTLSeconds`, 1 to 3600, default 30), an optional `staleWhileRevalidateSeconds`, path prefixes to keep out of the edge cache (`excludePaths`) or to opt back in (`includePaths`), and a `purge` block that names a Secret you create for the purge token. `knext deploy` checks all of it before building. The cache-tag prefix is derived by the operator from the app's namespace and name; there is no field for it. Names that start with `KNEXT_CDN_` are now reserved in `env` and `secrets.envMap`, whether or not `cdn` is set: `knext deploy` rejects them before building, and the operator ignores any such entry (it is never set on the container) and names it, never its value, in a `CDNReservedEnvIgnored` condition. A Secret imported whole through `secrets.envFrom` is not filtered, so keep that namespace trusted; when `cdn` is set the values knext renders still win. Leaving `cdn` out changes nothing: no variable is rendered and no revision is created. Preview deployments do not inherit `cdn`. On `build: "vinext"` (Beta) the operator renders nothing and reports an informational `CDNAdvisory` condition. This is a new field on the NextApp resource and a new reserved prefix, so it only works once you run an operator release that includes it: install that operator release first, then upgrade the CLI. A CLI that sends `cdn` to an older operator is stopped by the deploy preflight, which names the field.
