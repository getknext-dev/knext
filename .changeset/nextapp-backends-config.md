Declare the zone functions your app uses once, in `knext.config.ts`, and `knext deploy` sends them for you. Add `backends`, for example `backends: [{ name: "user-profile" }]`. The CLI sends the list as `spec.backends` on the NextApp resource, which is your zone's half of the binding to each function, so you no longer patch the NextApp by hand after `knext deploy function`. `service` defaults to `name`, which is how `knext deploy function <name>` names the function; set it only when they differ. Names are checked before building against the same rules the cluster enforces: lowercase letters and digits in parts joined by single hyphens, starting with a letter, at most 63 characters, each name and each function listed at most once, at most 64 entries. The operator reads the list and renders `<NAME>_SERVICE_URL` and the rest of the binding variables into your app's pods; it never writes them into your NextApp. Removing an entry takes that function down. Leaving `backends` out, or empty, sends no field at all, so a config that does not use it deploys exactly as before. Preview deployments do not inherit `backends`. This is a new field on the NextApp resource, so it only works once you run an operator release that includes it: install that operator release first, then upgrade the CLI. A CLI that sends `backends` to an older operator is stopped by the deploy preflight, which names the field.
