Zone functions (Beta) in the operator: a new `BackendService` resource runs a Go or Rust function beside a zone as a cluster-local, scale-to-zero Knative Service on an h2c port. A binding needs both halves: the function names its zone with `spec.zone` (the operator sets the ownerReference itself), and the zone lists the function in the new `NextApp` field `spec.backends`. Until both agree nothing is run. Removing the zone's entry takes the function down. For each bound function the operator writes `<NAME>_SERVICE_URL`, `<NAME>_SERVICE_PROTO_VERSION` (the contract version the function actually serves) and `KNEXT_WAKE_FUNCTIONS` into the zone's revision, never into your spec. A zone without `spec.backends` renders exactly as before, with no new revision. A function may only read its zone's database Secret or a Secret marked for its zone, runs as an operator-owned ServiceAccount with no permissions, mounts only its own zone's public keys, and gets a NetworkPolicy that admits the Knative data path only. A check for another zone's database host in plain env values is reported as a warning (a lint), not enforced. The operator now holds `get` (only) on Secrets, to read a referenced Secret's labels. The CLI's schema preflight knows the new fields. Install the operator release that includes this before you use the new fields.
