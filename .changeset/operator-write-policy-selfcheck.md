`knext doctor` now checks that the operator's Secret and ConfigMap write policy is in force. The policy, a `ValidatingAdmissionPolicy` shipped in the install bundle, is the only thing that limits the operator to its per-zone signing-key Secrets and JWKS ConfigMaps. It can be off with nothing saying so: a cluster older than Kubernetes 1.30 rejects it while the rest of the bundle installs, an install under a different namespace or ServiceAccount name than the bundle rendered leaves a policy that names a user the operator is not, and an admin or a GitOps prune can delete it. The new `write-policy` row reports a `WARN` that names which of these it is, and `PASS` only when the policy exists, covers create/update/delete on Secrets and ConfigMaps without narrowing, carries the validations this release ships, has a binding that denies, and names the ServiceAccount the operator runs as. A read it cannot classify or parse is a `WARN`, never a skip. The operator reports the same verdict as the `knext_operator_write_policy_enforced` gauge (re-checked every five minutes, warning log on change, still starts when it is `0`), with a `KnextOperatorWritePolicyNotEnforced` alert (a `0`) and a `KnextOperatorWritePolicyUnreported` alert (an operator pod that is scraped but exports no gauge). The operator's role gains `get` on exactly the policy and its binding, by name, and nothing else.
