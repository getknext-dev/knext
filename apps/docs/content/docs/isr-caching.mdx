title: ISR & the Redis cache
description: How a knext app's ISR/data cache reaches Redis — where the wiring lives, what the runtime guarantees, and how to upgrade an app scaffolded before the cache wiring landed.
---

knext's ISR / data cache is **Redis**. Every pod shares one keyspace, so a page rendered (or a tag
invalidated) by one pod is seen by all of them — which is what makes ISR coherent under
scale-to-zero, where pods appear and disappear constantly.

## Where the wiring lives

**On the default build** (`build: 'turbopack'` or `'webpack'`), Next reads the `cacheHandler`
option in `next.config.ts`. `knext create` scaffolds it, pointing at a `cache-handler.js` file in
your project, together with `cacheMaxMemorySize: 0` so the per-pod memory cache never diverges
from Redis:

```ts title="next.config.ts"
const nextConfig: NextConfig = {
  cacheHandler: new URL('./cache-handler.js', import.meta.url).pathname,
  cacheMaxMemorySize: 0,
};
```

Keep the handler file inside your project so `next build` copies it into the standalone output.

**On the vinext build** (`build: 'vinext'`), the app builds with **vinext** (Vite/rolldown). vinext
does **not** read the `cacheHandler` option in `next.config.ts` — that option belongs to Next's
webpack/turbopack pipeline, which this build never runs. The line is kept in scaffolded apps for
Next-aware tooling, but it is inert at runtime.

The live registration on vinext is in `vite.config.ts`, on the `vinext()` plugin itself:

```ts title="vite.config.ts"
import vinext from 'vinext';

export default defineConfig({
  plugins: [
    vinext({
      cache: {
        data: {
          // `-node` on `runtime: 'node'`, `-bun` on the default Bun runtime.
          adapter: '@getknext/core/internal/vinext-cache-adapter-bun',
        },
      },
    }),
    // …nitro(…)
  ],
});
```

The adapter is picked per runtime so the Redis client is resolved at build time: the `-node`
adapter imports `ioredis` directly, so the build ships it in the image, and the `-bun` adapter uses
Bun's built-in Redis client. If `REDIS_URL` is set but the client cannot be loaded, the app logs one
`Redis client unavailable` error at startup and serves from memory — ISR is then not shared between
pods and is lost on scale-to-zero. All three subpaths work with vinext 1.0.1 and 1.1.0. The generic
`…/vinext-cache-adapter` subpath still works for apps scaffolded earlier, but it cannot be traced by the build, so switch it to the one for your runtime.

At build time, vinext generates a registration module from this option and runs it in every server
entry, so the Redis-backed handler is registered before any route executes. Page-level ISR
(HIT / STALE serving and in-process background regeneration) then flows through that handler.

<Callout type="warn">
**Deleting this block does not fail the build.** The app still serves 200s — with a **per-pod
in-memory cache** instead: every pod renders independently, nothing survives scale-to-zero, and
the provisioned Redis stays empty. If you see `x-nextjs-cache: MISS` on every request and an empty
Redis, this block is the first thing to check.
</Callout>

## What the runtime guarantees

- **First request** after a cold cache is a `MISS` and writes the rendered page to Redis.
- **Within the revalidate window** requests are served `HIT` from Redis — including the first
  request after the app scales up from zero, for pages generated at request time as well as
  prerendered ones. Each entry carries its own revalidate window, so a freshly started pod does not
  need to have rendered the page to know it is still fresh. That applies only to entries written by
  the same build. After a redeploy, once the previous build has stopped serving (plus about two
  minutes, see the canary and redeploy bullet below), the first request for a page that build
  rendered may get the previous page once, as `STALE`, while a fresh copy renders in the background.
  Later requests get the new build's page. This holds for `revalidate: false` pages too.
- **Past the window** requests are served `STALE` from Redis while a background render replaces the
  entry — stale-while-revalidate, not a blocking re-render.
- **While two builds are serving the same app** (a canary split, or the overlap of a plain
  redeploy), each build keeps honouring the revalidate window of entries the other build wrote, for
  as long as that build is still serving requests. Pages therefore regenerate at their own cadence,
  not on every request during a long split. The same rule delays a plain redeploy: once the old
  build has stopped serving, its windows stop being honoured within about two minutes, and until
  then the new build can keep serving the old build's page without regenerating it. That includes
  `revalidate: false` pages, which can show the old build's HTML for up to about two minutes after
  the old pods drain. After that, the first request for each such page may get the previous page
  once while a fresh copy renders. Pages that use partial
  prerendering are the exception: their resume state is tied to the build that rendered them, so
  under a split they are re-rendered whenever the other build wrote the entry last.
- The Redis entry's TTL is deliberately **longer than the revalidate window** (it is the route's
  expire time when one is declared, and a floor of one hour otherwise). If the entry expired
  exactly at the revalidate window there would be nothing left to serve stale.
- When `REDIS_URL` is unset (local dev), the handler falls back to in-memory caching, so `vinext
  dev` and local builds work without a Redis.
- The Redis client depends on the runtime in your deploy config. On `node` the handler uses
  `ioredis`, which the build copies into the image. On `bun` it uses Bun's built-in Redis client.
  `knext build`, `knext deploy` and `knext preview` pick the right one for you.
- When `REDIS_URL` is set but the Redis client cannot be loaded in the pod, the handler still
  serves from memory, but it logs one error at startup that starts with
  `[CacheHandler] Redis client unavailable`. If you see it, cache entries are not shared between
  pods and do not survive scale-to-zero. Check that you built the image with `knext deploy` or
  `knext build` for the same runtime you deploy.
- When Redis becomes unreachable while the app runs, each pod serves from its own memory and tries
  Redis again every few seconds. A `revalidateTag` or `revalidatePath` during that time clears the
  pod's memory at once. The pod also remembers the tags. As soon as Redis answers again, it
  invalidates them in Redis and then purges them from your [CDN](/docs/cdn), so other pods stop
  serving the old page without waiting for its TTL. A pod remembers up to 1,000 distinct tags. Past
  that, it invalidates every cached page of the app instead and purges the whole app from the CDN,
  which costs a burst of re-renders but never leaves a page stale. The list is kept in the pod's
  memory only. If the pod restarts or scales to zero before Redis is back, those pages stay stale
  until their TTL.

<Callout type="warn">
**On the standalone build's Node runtime, the Redis-backed handler can silently fall back to a
per-pod in-memory cache.** This affects `runtime: 'node'` only — the Bun runtime (the default) and
the vinext compiled executable are not affected. The app still serves 200s, but pages render
independently per pod, nothing survives scale-to-zero, and the provisioned Redis stays empty — the
same symptom as deleting the `cacheHandler` block above. If you need a shared cache today, use the
Bun runtime. This is fixed in the next patch release; check the release notes for your version.
</Callout>

The connection details come from the environment — `REDIS_URL` and `REDIS_KEY_PREFIX` are injected
into your pods from the `cache` block of your deploy config (see
[the operator reference](/docs/operator)); nothing about Redis is hardcoded in your app.

## Each app has its own Redis keyspace [#key-prefix]

Every key an app writes starts with its key prefix, `REDIS_KEY_PREFIX`. Apps that share one Redis
are kept apart by that prefix alone.

- Set `cache.keyPrefix` in your deploy config to choose the prefix.
- Leave it unset and the operator gives the app a prefix of its own: `kn-` followed by 12 hex
  characters derived from the app's namespace and name. No two apps get the same one, including two
  apps with the same name in different namespaces.
- A `REDIS_KEY_PREFIX` you set yourself in `env` or `secrets.envMap` still wins. One baked into
  your image or loaded through `secrets.envFrom` does not: set `cache.keyPrefix` instead.

Two apps under one prefix read each other's entries and receive each other's invalidations.
`knext doctor` warns when apps on the cluster share a prefix, or when one prefix sits inside another
(`shop` and `shop:cache`).

Keys under `kn-next:*` belong to apps that run with no prefix at all, for example outside the
operator. Any number of apps can land there, so knext never deletes keys under it wholesale. After a
Redis outage long enough to miss more than 1,000 invalidations, an app with its own prefix clears its
whole cache to drop the entries it could not invalidate. An app on that shared fallback logs an error
instead and keeps those entries until they expire.

### Upgrading an app that set no prefix [#key-prefix-upgrade]

Before this change, an app without `cache.keyPrefix` wrote its keys under `kn-next:*`. When the
operator is upgraded, the app rolls out a new revision under its own prefix and starts with an empty
cache: pages and `'use cache'` entries are rendered again on their first request. The keys left under
`kn-next:*` are not deleted for you. They expire on their own, or you can remove them once no app
writes there any more:

```bash
redis-cli --scan --pattern 'kn-next:*' | xargs -r redis-cli del
```

To avoid the cold start, set `cache.keyPrefix` before you upgrade the operator; the app then keeps
whatever prefix you choose. Choose one no other app uses.

## `'use cache'` is shared across pods

Next.js runs the `'use cache'` directive (Cache Components) through a different option from ISR:
`cacheHandlers`, plural. On a knext app that uses knext's `cacheHandler` (the scaffold does), the
build wires `cacheHandlers` to the same Redis for you, so you add nothing to `next.config.ts`:

- A `'use cache'` entry written by one pod is a hit on every other pod behind the same Service,
  and it survives scale-to-zero.
- `'use cache: remote'` is backed by the same Redis, under its own key namespace.
- `revalidateTag` (and `updateTag`) on one pod invalidates the entry on all of them.
  `revalidateTag(tag, profile)` keeps its stale-while-revalidate behaviour: the entry is served
  once more while a fresh one is produced.
- The keys belong to your app (`REDIS_KEY_PREFIX`) and, by default, carry Next's own build
  identifier, so one build does not read another build's entries. If you turn on Next's
  experimental durable cache entries, the key carries a hash of the cached function's code
  instead, and a new build deliberately reuses the entries of every function whose code did not
  change.
- Every entry gets a Redis expiry: the shorter of the `cacheLife` `expire` you set and **24 hours**
  (Next's default `expire` is effectively unbounded). Lower the ceiling with
  `KNEXT_USE_CACHE_MAX_TTL_SECONDS`. An entry that holds one user's data should use a short
  `cacheLife` of its own, an hour or less.
- An entry with `expire: 0` (a dynamic result) is never stored.
- An entry larger than **2 MiB** is not stored: the function runs again on the next request, and
  the handler logs one warning. Change the limit with `KNEXT_USE_CACHE_MAX_ENTRY_BYTES` (in bytes;
  `0` removes it). The limit keeps one very large write from timing out and taking the ISR cache,
  which shares the Redis connection, offline with it.
- Invalidation times are taken from the Redis server's clock, so pods whose clocks disagree still
  agree on whether an entry was written before or after a `revalidateTag`.

The scaffold keeps `cacheMaxMemorySize: 0`. That setting only turns off Next's per-pod memory cache
for ISR; it no longer turns `'use cache'` into a no-op, because the Redis handler replaces Next's
built-in one.

You can still set your own entry for a kind (`cacheHandlers: { default: '…' }`), and yours wins for
that kind. The wiring applies to builds made by `knext build` and `knext deploy`, for both the Node
and the Bun runtime. A plain `next build` outside knext, and apps that bring their own
`cacheHandler`, are left alone.

**With Redis unavailable, `'use cache'` does not cache.** There is deliberately no per-pod fallback:
a `'use cache'` entry can hold one user's results, and a copy in pod memory would outlive its
expiry and never see another pod's invalidation. Reads become misses and your code runs as normal,
and writes are dropped. A `revalidateTag` issued during the outage is remembered by the pod that
received it and applied once Redis is back, without waiting for another request, the same way as
for ISR above, so the `'use cache'` entries it covers stop being served on every pod. It is applied
with the time Redis came back, never earlier, so an entry cached between the call and that moment
is re-rendered once more. It never undoes a newer invalidation of the same tag that reached Redis
first, from another pod or from a later call on the same pod: an `updateTag` that already expired
an entry keeps it expired. On Redis older than 5, or a Redis that refuses Lua scripts, the pod
falls back to a separate read and write, so a newer invalidation landing between the two can still
be overwritten. When a remembered `revalidateTag` with a profile is applied to a tag that
is already expired, its entries are marked stale (re-rendered on the next read) but the profile's
later expiry is not scheduled. A pod remembers up to 1,000 distinct tags; past that, once Redis is back
it removes every `'use cache'` entry of the app instead, which costs a burst of re-renders but never
serves a stale result. A pod that restarts or scales to zero before Redis is back forgets the list,
and those entries are served until they expire. Each pod logs one warning per outage (and one when
`REDIS_URL` is not set at all). ISR keeps its own per-pod fallback, as described above.

**Redis memory.** Set `maxmemory` on the Redis you point knext at, with
`maxmemory-policy volatile-lru`. Every cache entry carries an expiry, so it can be evicted; the tag
index (ISR) and the tag timestamps (`'use cache'`) carry none, so they are never evicted, which
matters because losing one would silently lose an invalidation. Do not use an `allkeys-*` policy.
Under the Redis default (`noeviction`) writes fail once the limit is reached and the handlers fail
open to rendering.

**The vinext build** (`build: 'vinext'`) is unchanged: it has its own cache adapter and does not
read `cacheHandlers`, so `'use cache'` there is not backed by this Redis store.

`knext doctor` reports an app that enables `cacheComponents`: PASS when the shared store is wired,
and a warning for an app with no `cacheHandler`, where Next's per-pod built-in handler applies.

### `'use cache'` metrics [#use-cache-metrics]

The app's Prometheus endpoint (port `9464`, `/metrics`, the port the shipped scrape configuration
collects) serves one counter for the `'use cache'` store, `knext_use_cache_events_total`, labelled
`event`. Every event is served from the first scrape, at `0` until it happens, so you can alert on
the rate of any of them:

| Event | Counts |
|---|---|
| `hit` | Reads served from Redis |
| `miss` | Reads that found nothing usable, so the function ran |
| `corrupt` | Reads of an entry that could not be decoded |
| `expired` | Reads of an entry invalidated by a `revalidateTag` |
| `stored` | Entries written to Redis |
| `skipped` | Entries not stored because they are dynamic (`expire: 0`) |
| `invalid` | Entries not stored because Next passed a malformed entry |
| `oversize` | Entries not stored because they exceed `KNEXT_USE_CACHE_MAX_ENTRY_BYTES` |
| `aborted` | Entries not stored because the render failed part-way |
| `dropped` | Entries not stored because Redis was unavailable |
| `tags_updated` | Tag invalidations written to Redis |
| `tags_dropped` | Tag invalidations that could not reach Redis; they are applied once it is back |
| `tags_replayed` | Tags whose invalidation was applied after Redis came back |
| `tags_collapsed` | Times a pod had over 1,000 tags to apply and removed every `'use cache'` entry of the app instead |
| `tags_collapse_refused` | Times a pod had over 1,000 tags to apply but kept its entries, because its key prefix is the shared fallback `kn-next:*` ([why](#key-prefix)) |
| `prune_error` | Failed clean-ups of old invalidation timestamps (the invalidation itself was written) |
| `error` | Redis commands that failed; the request carried on without the cache |

A read is counted once as `hit` or `miss`. `corrupt` and `expired` are also counted as `miss`, so a
hit ratio is `hit / (hit + miss)`. A rising `oversize` means entries are being re-rendered on every
request: raise the limit or cache something smaller. A rising `dropped` or `tags_dropped` means
Redis is unreachable. `tags_dropped` counts calls and `tags_replayed` counts tags, so the two are
not expected to match. The label is a fixed set of values: no cache keys, tags or paths.

The counters are kept by your app's server process and reach port `9464` through the small local
metrics listener that the app's `src/instrumentation.ts` starts. An app generated by `knext create`
starts it already. An app whose `instrumentation.ts` does not start it serves no `'use cache'`
series; add the lines in
[Existing apps: start the deep-health gauge](/docs/observability#deep-health-existing-apps) to get
them. With tracing on, the instrumentation already starts that listener and no change is needed.

The series appear once Next has loaded the `'use cache'` store in that process, at the latest on the
first request that uses it. The `vinext` build
uses its own cache adapter, so it serves no `'use cache'` series.

## The Cache-Control header clients see

Next.js marks cacheable pages with directives meant for a shared cache in front of the server, such
as `s-maxage=2, stale-while-revalidate=31535998` for an ISR page or `s-maxage=31536000` for a
static one. knext serves your app directly, with no shared cache in between, so every build
rewrites those responses to `public, max-age=0, must-revalidate`: the standalone server
(`build: 'turbopack'` or `'webpack'`, on Node or Bun — the default), the vinext compiled
executable, and vinext on Node (`build: 'vinext'` with `runtime: 'node'`). That's the header a deployed Next.js app
returns to browsers.
The first request for a `fallback: true` page gets the same header rather than `private, no-store`.
Hashed static assets (`immutable`) and non-`GET`/`HEAD` responses are never changed.

With the vinext build (the compiled executable, or vinext on Node), two layers produce this header:

- **vinext's own deploy mode** covers the responses vinext builds itself: ISR and static pages,
  `/_next/data` requests, and the first request for a `fallback: true` page. The server turns it
  on by setting `VINEXT_NEXT_DEPLOY_CACHE_CONTROL=1`, unless you've set that variable yourself.
- **knext's rewrite** covers `s-maxage` headers your own code sets, for example in a route handler
  or on a redirect.

If you put your own CDN or shared cache in front of knext and want it to see the `s-maxage` values,
set `KNEXT_CACHE_CONTROL_NORMALIZE=0` in the app's environment. That one switch turns both layers
off, and the server sends Next.js's original headers. To turn off only vinext's layer, set
`VINEXT_NEXT_DEPLOY_CACHE_CONTROL=0`.

That switch is deprecated for CDN use. The `cdn` block in `knext.config.ts` sends cache-correct
edge headers, tags and purges on revalidation; see [CDN caching](/docs/cdn).

On vinext on Node, both layers live in the app's `knext-node-entry.mjs`. An app created before
this behaviour shipped has an older copy of that file and still serves Next.js's original headers;
replace it with the one from a freshly created app (`knext create`).

## Upgrading a vinext app scaffolded before the cache wiring

Vinext apps created by earlier versions of `knext create` wired the cache handler **only** through
`next.config.ts`'s `cacheHandler` — which the vinext build ignores, so their ISR never reached
Redis. To fix an existing app, add the `cache` block to the `vinext()` call in your
`vite.config.ts` exactly as shown above, and make sure `@getknext/core` is in your
`devDependencies`. No other change is needed: the handler, the environment contract, and the
operator side were already in place.

To verify after deploying: request an ISR route twice — the second response should carry
`x-nextjs-cache: HIT` — and `redis-cli KEYS '<your-prefix>:cache:*'` should show the page's
entries, with `TTL` greater than the route's revalidate window.
