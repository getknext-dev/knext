---
title: Zone functions
description: Run a Go or Rust function beside a zone as a cluster-local, scale-to-zero Knative Service, bound to that zone and to no other.
---

**Beta.** A zone function is a backend function (Go or Rust, serving gRPC or Connect over h2c) that
belongs to exactly one zone, your `NextApp`. The operator runs it as its own scale-to-zero Knative
Service, reachable only from inside the cluster, and tells the zone where it is. You declare it
with a `BackendService` resource. The [`knext add function`](/docs/cli#knext-add-function) and
[`knext generate`](/docs/cli#knext-generate) commands write the function's contract and the zone's
typed client, [`knext deploy function`](/docs/cli#knext-deploy-function) applies the
`BackendService` for you, and [`knext deploy`](/docs/cli#knext-deploy-default) tells the zone about it from
the `backends` list in your `knext.config.ts`. You can also apply the `BackendService` yourself with
`kubectl apply --validate=strict` or your GitOps tool.

Upgrade the operator (and its CRDs) before you apply a `BackendService` or deploy a config with
`backends`. An older operator does not know these fields, and `knext deploy` stops before it changes
anything and names the field.

## Binding a function to its zone

A binding needs **both halves**:

1. **The function names its zone** with `spec.zone`, the name of a `NextApp` in the same namespace.
   You never write an `ownerReference`; the operator sets it from `spec.zone`. `spec.zone` cannot be
   changed after the function is created.
2. **The zone lists the function** in its `backends`. This is the zone owner's consent, and it lives
   in your zone's own config, so it is reviewed and versioned with the rest of the zone.

```yaml title="pricing.yaml"
apiVersion: apps.kn-next.dev/v1alpha1
kind: BackendService
metadata:
  name: pricing
  namespace: shop
spec:
  zone: orders
  image: registry.example.com/pricing@sha256:<digest>
  port: 8080            # the h2c port your server listens on (default 8080)
  protoVersion: 1.4.0   # the contract version this image serves
```

List the function in the zone's `knext.config.ts`:

```ts title="knext.config.ts (excerpt)"
export default {
  name: "orders",
  // ...
  backends: [
    { name: "pricing" }, // the function name your generated client uses
  ],
};
```

`knext deploy` sends this list on the zone's `NextApp` as `spec.backends`, in the same apply as the
rest of the zone, so you do not edit the `NextApp` yourself. `service` is the name of the
`BackendService` and defaults to `name`, which is how `knext deploy function pricing` names it; set
it only when the two differ. Each `name` is lowercase letters and digits in parts joined by single
hyphens, starting with a letter and at most 63 characters, and each name and each function may be
listed only once. `knext deploy` checks all of this before it builds anything. Leaving `backends`
out, or empty, sends nothing, so a zone without functions deploys exactly as before.

If you apply the zone with your own GitOps tool instead of `knext deploy`, write the same list on
the resource:

```yaml title="orders zone (excerpt)"
apiVersion: apps.kn-next.dev/v1alpha1
kind: NextApp
metadata:
  name: orders
  namespace: shop
spec:
  image: registry.example.com/orders@sha256:<digest>
  backends:
    - name: pricing     # the function name your generated client uses
      service: pricing  # the BackendService
```

A preview deployment does not inherit `backends`: a function belongs to exactly one zone, and a
preview is a different one.

Until both halves agree, the operator runs **nothing** for the function: no Knative Service, no
mounted Secret, and nothing in the zone's environment. The function's `Bound` condition says which
half is missing.

**Removing the zone's `backends` entry takes the function down.** Its Knative Service is deleted,
and the zone's next revision drops the function's variables. If a GitOps sync briefly drops the
entry, the function comes back through a cold start when the entry returns.

A `backends` entry that names a function belonging to another zone is refused and reported on the
zone's `BackendBindings` condition.

### Pin the function's image

A binding matches **names**. Without more, anyone who may **update** the function's `BackendService`
can change `spec.image` to an image they chose, and the operator runs that image with your zone's
database Secret and key set mounted. Your zone then sends it your users' identity tokens. In other
words, **permission to update `backendservices` is equivalent to permission to read your zone's
database Secret**. Grant `update`, `patch` and `create` on `backendservices` only to people who may
already read that Secret. A GitOps tool that applies the `BackendService` has this power too.

Pinning the image narrows this, but does not remove it: see [What the pin does not cover](#what-the-pin-does-not-cover).
To pin, put the function's image digest in the zone's entry. `knext deploy function` prints the
exact entry after it applies the function:

```ts title="knext.config.ts (excerpt)"
export default {
  // ...
  backends: [
    { name: "pricing", image: "@sha256:0a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2e3f4a5b6c7d8e9f0a1b" },
  ],
};
```

`image` is the digest only: `@sha256:` followed by 64 lowercase hexadecimal characters. It is not the
whole image reference, so the registry path and tag can change while the content stays the same. The
same field exists on the resource if you apply the zone yourself:

```yaml title="orders zone (excerpt)"
spec:
  backends:
    - name: pricing
      service: pricing
      image: "@sha256:0a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2e3f4a5b6c7d8e9f0a1b"
```

**What happens on a mismatch.** The operator runs the function only while the digest in its
`spec.image` is exactly the pinned one. Any other digest, or an image with no digest, refuses the
function: `Bound` and `Ready` turn `False` with the reason `BindingImageMismatch`, the message names
both digests, the function's Knative Service is removed, and nothing is mounted into it: no database
Secret and no key set. Put the pinned image back, or change the pin, and the function runs again.
The pin itself never appears in your zone's pods, so setting, changing or removing it does not roll a
zone revision. A refused function stops reporting a served version, so, as with any refused function,
the zone's next revision drops `<NAME>_SERVICE_PROTO_VERSION` and its calls to that function fail
closed until the function is bound again. A failed read of a Secret can never cause this refusal,
because the check compares the two resources and nothing else.

**Rotating the pin.** A new function image and a new pin are two writes, and they cannot land in the
same instant. Change both in one step (one `kubectl apply -f` of both resources, or one commit for a
GitOps tool). While only one of them has been written, the function is refused, and it starts again
(with a cold start) as soon as the other follows. If you update the function's image first, the
function is refused until you update the pin; if you update the pin first, it is refused until the
function's image follows. Either order works; neither avoids that window.

#### What the pin does not cover

**The pin binds the image content, and nothing else.** The function's other settings stay with
whoever can write its `BackendService`: its `env`, `envFrom` and `volumes`. Someone who can write the `BackendService` can keep the pinned image and still change
what runs inside it. For example, setting `NODE_OPTIONS=--import=...` in `env` makes a Node image
run code of their choosing, with your zone's database Secret mounted and your users' tokens arriving.
A pin does not stop that.

So, even with a pin on every function: **grant `update`, `patch` and `create` on `backendservices`
only to people who may already read your zone's database Secret.** The pin protects against a swapped
image, not against a writer who changes the function's settings.

Also:

- The pin is optional, so a zone that does not set it keeps the name-only binding.
- It says "this exact image", not "an image from a source you trust": pin only images you built and
  signed.
- Anyone who can edit your zone's `NextApp` can also change the pin, so keep write access to the zone
  as tight as access to its database Secret.

## What the zone receives

For each bound function, the operator writes these variables into the **zone's revision**, never
into your `NextApp` spec:

| Variable | Value |
| --- | --- |
| `<NAME>_SERVICE_URL` | `http://<service>.<namespace>.svc.cluster.local` |
| `<NAME>_SERVICE_PROTO_VERSION` | The contract version the function **actually serves**: the `protoVersion` of its latest Ready revision. Unset until one is Ready, so the zone's calls fail closed instead of guessing. |
| `KNEXT_WAKE_FUNCTIONS` | The bound functions to wake when the zone starts: their names, sorted and comma-separated. A function with `wakeAhead: false` is left out; with none left the variable is not set. |

`<NAME>` is the `backends` entry's name in upper case with `-` replaced by `_`, so `user-profile`
becomes `USER_PROFILE_SERVICE_URL`. Name each entry after the function your generated client was
built for.

The variables are sorted, so a reconcile with no change rolls no new revision, and a zone with no
`backends` renders exactly as before. When a function starts serving a new contract version, the
zone rolls one new revision with the new `<NAME>_SERVICE_PROTO_VERSION`.

If your zone's `spec.env` or `spec.secrets.envMap` already sets one of these names, your value is
kept, and the `BackendBindings` condition names the variable that was not written.

## Credentials: what a function may read

A function may reference a Secret (through `env` `secretKeyRef`, `envFrom`, a Secret volume or a
projected volume) only if it is:

- **its zone's database Secret**, the one named in the zone's `spec.database`; or
- **marked for its zone**: the label `apps.kn-next.dev/zone: <zone>`, or an `ownerReference` to
  the zone's `NextApp`.

Everything else is refused, and so is any reference to **another zone's** database Secret or a
Secret marked for another zone, even one that also carries this zone's mark. `imagePullSecrets`
are exempt: they expose no data store. A refused function is not run at all, and its
`SovereigntyCompliant` condition names the reference and its source.

This allowlist **is** the data-sovereignty control: a function holds no credential for another
zone's database. Two things keep it airtight:

- **The function runs as an operator-owned ServiceAccount** with no Role, no RoleBinding and no
  mounted API token. `BackendService` has no `serviceAccountName` field, so a manifest cannot pick
  a more privileged identity; a stray one is rejected by a strict apply and has no effect otherwise.
- **The binding is two-sided**, so someone who may create a `BackendService` but cannot edit the
  zone cannot get a Secret mounted into a pod they control. It matches names, though, so someone
  who may *update* a function that is already bound can swap its image, or change its `env` or
  `envFrom`. [Pinning the image](#pin-the-functions-image) stops the image swap only; keep `update` on
  `backendservices` limited to people who may read the zone's database Secret.

**The namespace is the trust boundary.** Anyone who can write Secrets in the namespace can set the
zone label. Put zones whose owners do not trust each other in separate namespaces.

### The database-host check is a lint

The operator also looks at your function's plain `env` values for another zone's CloudNativePG
service (a `<cluster>-rw` or `<cluster>-ro` host named after another zone in the namespace, or one
in another namespace) and reports it as a **warning** on the `DatabaseHostLint` condition and as an
event. It never stops the function. It is a heuristic, not a control: an IP address, an
`ExternalName` Service, a URL built at run time or a value inside a Secret gets past it. The
control is the credential allowlist above.

## Identity and the JWKS

Every call from a zone to its function carries a short-lived token the zone signs with its own
key. The operator creates and rotates that key; you do not supply one.

As soon as a zone has at least one bound function, the operator creates two objects next to the
zone's `NextApp`, both owned by it (deleting the `NextApp` deletes them):

| Object | Holds | Mounted into |
| --- | --- | --- |
| Secret `<zone>-knext-signing-key` | The zone's Ed25519 private key (`current.key`, `current.kid`, and `previous.*` during a rotation) | The **zone** only, read-only at `/var/run/knext/signing-key` |
| ConfigMap `<zone>-knext-jwks` | The matching public keys (`jwks.json`, a JWK Set) | Each of the zone's **functions**, read-only at `/var/run/knext/jwks/jwks.json` |

Both are mounted as directories, never through environment variables, so a rotated key reaches a
running pod without a restart. A function never mounts a signing key: a reference to any zone's
`-knext-signing-key` Secret, its own included, is refused, and so is a reference to another zone's
JWKS ConfigMap. `/var/run/knext` is reserved for these mounts. Until the zone's keys exist, the
function starts, but its generated interceptor refuses every call except the health check.

The operator creates and rotates these two objects, and the install bundle's admission policy
lets its ServiceAccount write nothing but an `Opaque` Secret ending in `-knext-signing-key` and a
ConfigMap ending in `-knext-jwks` (Kubernetes 1.30 or later). See
[Security](/docs/security#write-policy).

A function mounts the JWKS only if the zone's `NextApp` controls the ConfigMap, meaning the
zone is the owner marked as its controller. If something else created a ConfigMap of that name
first, the operator does not mount it. The function is rendered without any JWKS, so it starts
but refuses every call except the health check, and its `JWKSTrusted` condition is `False` with
reason `JWKSUntrusted` (the function is then not `Ready`, and a `Warning` event is recorded).
The zone reports `JWKSConfigMapConflict` at the same time. Remove the ConfigMap and the operator
publishes the zone's own keys and mounts them again on its next check, within ten minutes. The
check runs at each reconcile, not continuously, and an owner reference is a claim that anyone who
can write ConfigMaps in the namespace can make: it protects against a name taken by accident or
left behind by an earlier zone of the same name, not against someone you already trust with write
access to the namespace.

The operator also sets, as plain values:

| Variable | On | Value |
| --- | --- | --- |
| `KNEXT_ZONE_ISSUER` | The zone | `knext:zone:<namespace>/<zone>`, the issuer the zone signs as |
| `KNEXT_TOKEN_ISSUER` | Each function | The same issuer: the only zone whose tokens the function accepts |
| `KNEXT_TOKEN_AUDIENCE` | Each function | `knext:fn:<namespace>/<function>`, so a token minted for one function is refused by another |

Names that start with `KNEXT_TOKEN_` are reserved on a function: a `BackendService` that sets one in
`env` is rejected when you apply it.

If the zone loses its last bound function, the operator stops mounting the key and keeps both
objects, so binding a function again reuses the same key.

### Rotating the key

To rotate, set an annotation on the zone's `NextApp` to any new value:

```bash
kubectl annotate nextapp orders apps.kn-next.dev/rotate-signing-key="$(date +%s)" --overwrite
```

The operator then rotates in this order, so no call fails along the way:

1. It adds the new public key to the JWKS. The zone keeps signing with the old key.
2. It waits 120 seconds, long enough for the kubelet to update the JWKS file in every running
   function, with room to spare.
3. It switches the zone to the new key. The old key stays in the JWKS.
4. After one hour it removes the old key from both objects.

The `ZoneSigningKey` condition on the zone shows where a rotation is: `RotationPropagating`
during step 2, `RotationOverlap` during the hour of step 4, `KeyActive` otherwise. A request made
while a rotation is running starts when that one finishes.

Two operator flags tune this:

| Flag | Default | Meaning |
| --- | --- | --- |
| `--zone-signing-key-propagation-bound` | `2m` (120 seconds) | How long a new public key is published before the zone signs with it. Raise it if your kubelets refresh volumes more slowly; the operator refuses anything below `90s`. |
| `--zone-signing-key-rotation-interval` | `0` (off) | Rotate every zone key this long after it became current, for example `720h`. Must be longer than the bound plus one hour. |

**Why 120 seconds, and why not below 90.** A running function sees the new JWKS only after the
kubelet rewrites the mounted ConfigMap. A default kubelet re-syncs each pod every 60 seconds, and
that interval is stretched by up to half again (so up to 90 seconds) before the update lands. That
worst case is the minimum. The default adds 30 seconds on top, for the ConfigMap change to reach the
kubelet and for the function to re-read the file. On GitHub-hosted test nodes a running function
picked up a new key anywhere from under 5 seconds to about 85 seconds later, so a shorter wait works
most of the time and fails on the slow runs. If a function's refresh lands after the zone switches,
that function refuses the zone's calls (`unauthenticated`) until it catches up, and nothing else
reports it. A rotation takes about 30 seconds longer than a 90-second wait would.

If you set a bound between `90s` and `2m`, the operator accepts it and rotates, and the
`ZoneSigningKey` condition says the bound is below the default for as long as a rotation is
propagating or in its overlap. Raise the bound above `2m` if your kubelets run a longer sync period
(`syncFrequency`), or if you changed how they cache ConfigMaps.

To replace a key at once, for example after you suspect it leaked, delete the Secret. The operator
creates a new key and republishes the JWKS on the zone's next reconcile (within ten minutes). Calls
fail until the zone and its functions have read the new files, so expect up to a minute or two of
refused calls.

If a Secret or ConfigMap with one of these names already exists and the zone's `NextApp` does not
own it, the operator leaves it alone, publishes nothing, and reports `SigningKeySecretConflict` or
`JWKSConfigMapConflict` on the `ZoneSigningKey` condition. Remove the object and the operator
creates its own.

## Network

The function's Knative Service is **cluster-local**: it has no public route. The operator also
writes a `NetworkPolicy` that admits only the Knative data path, which is the activator that wakes
a function from zero and the networking layer's gateway, on the queue-proxy ports. It stops a pod
from dialling the function's pod directly. Because every call arrives through those shared
Knative components, the policy cannot tell your zone from another one; the per-call identity token
is what does that. NetworkPolicy is enforced only by a CNI that supports it (Calico, Cilium);
flannel enforces none.

A bound function stays up a little longer than its zone after its own last call, so a zone that
just called it does not find it cold on the next request.

## Status and metrics

`kubectl get backendservices` shows each function's zone, readiness and served version.

The served version is `status.servedProtoVersion`: the `protoVersion` of the function's latest
Ready revision. It is empty until a revision is Ready, and it is the value the zone receives as
`<NAME>_SERVICE_PROTO_VERSION`.

| Condition | Meaning |
| --- | --- |
| `Bound` | Both halves agree, and the image is the one the zone pinned, if it pinned one. `ZoneNotFound`, `ZoneNotListed`, `BindingImageMismatch` or `ConflictingOwner` otherwise. |
| `SovereigntyCompliant` | Every Secret reference passes the allowlist. `SecretNotAllowed` names the ones that do not, including a reference whose name cannot be a Secret name. `Unknown` (`SecretsUnverified`) when the operator could not read a referenced Secret's metadata: see [When Secrets cannot be verified](#when-secrets-cannot-be-verified). |
| `DatabaseHostLint` | `False` when an env value names another zone's database host. A warning only. |
| `JWKSTrusted` | `True` when the zone controls its JWKS ConfigMap and the function mounts it. `Unknown` (`NotPublished`) while the ConfigMap does not exist yet. `False` (`JWKSUntrusted`) when another object holds the name: nothing is mounted and every call except the health check is refused. |
| `Ready` | Bound, compliant, the function's JWKS is not untrusted, and the function's Knative Service is Ready. `False` (`SecretsUnverified`) while a Secret cannot be verified and the function was never rendered, or its latest spec has not been rolled out. |

### When Secrets cannot be verified

The operator reads each referenced Secret's metadata to check that it belongs to the function's zone. **A failed read
never refuses a function, except a denial that outlasts the hold below.** Refusals come from what the Secret is, and
they apply whatever the state of the API server:

- it is a zone's signing key (a function never mounts a private key);
- it is another zone's database Secret, even if it was re-marked for this zone;
- it is marked for another zone, is not marked for this one, or does not exist;
- the function's zone does not exist, so no Secret is allowed;
- its name cannot be a Secret name;
- a function may also not reference another zone's JWKS ConfigMap.

**What always holds**

- **What is running is re-checked whenever a change cannot roll out.** When the new spec cannot be verified, or cannot be
  rolled out (a webhook or Knative refuses the new Service), the previous template stays up, so the Secrets it already
  mounts are checked against the zone. A Secret that has been re-marked for another zone, or is no longer allowed,
  removes the function in that case, whatever the new spec says. When a valid spec does roll out, the new template
  replaces the old one, so nothing revoked survives it, and a Secret the old template named that has since been deleted
  (a routine rotation: create the new version, point the spec at it, prune the old one) is not a violation: the function
  is updated in place. A rotation that coincides with a failed read or a refused rollout keeps the function running and
  is retried; only a Secret that was positively revoked (re-marked for another zone, no longer carrying this zone's mark,
  another zone's database Secret, a signing key, or a zone that no longer exists) removes it, whatever stopped the
  rollout, and a Secret that is merely gone never does.
- A reference that can never name a Secret (an empty name, `..`, a name containing `/`, upper-case letters, or more than
  253 characters) is not "unverified": it is refused straight away as a violation.
- A volume cannot mount `/`, `/dev` or `/dev/log`, which Knative serving reserves, however the path is spelled with
  repeated or trailing slashes or `.` segments (`/dev/`, `//dev`, `/./dev`). A path such as `/data/` is fine.

**When a read fails**

- **Unknown errors are held.** An API server timeout, throttling, a server error, a connection failure, or any error the
  operator does not recognise leaves the function as it is: a running function is not removed and nothing new is
  rendered, a function that was never rendered stays unrendered, and the operator retries with backoff. It holds for as
  long as the error lasts and never removes a function.
- **A spec change does not roll out while this holds.** `status.observedGeneration` stays at the last generation that
  was rolled out, and `Ready` is `False` with reason `SecretsUnverified`, so `kubectl wait` and GitOps tools do not
  report the new spec as deployed.
- **Denied reads are held for ten minutes from the first denial.** A read the API server answers with Forbidden or
  Unauthorized does not heal by itself, so it is held for ten minutes, counted from the first denied read
  (`status.secretsDeniedSince`; timeouts and server errors before it do not count, and it is cleared as soon as no read is
  denied). After that the function is refused with `SecretNotAllowed` and its Knative Service is removed: an operator that
  cannot read Secrets cannot enforce the allowlist, and keeping the function would freeze revocation for every function.
  It stays refused for as long as the denial lasts, without flipping back and forth. When access returns, the next pass
  renders the function again, as a new revision with a cold start.

If `SecretsUnverified` does not clear on its own:

1. Check the operator's permission to read Secrets:
   `kubectl auth can-i get secrets -n <namespace> --as=system:serviceaccount:<operator-namespace>:<operator-service-account>`
2. Check the API server's health, for example `kubectl get --raw='/readyz?verbose'`.
3. Read the operator's logs for the error it reports for the Secret.

The zone's `BackendBindings` condition is `True` when every `backends` entry is bound. Its
`ZoneSigningKey` condition is present while the zone has a bound function: `True` with
`KeyActive`, `RotationPropagating` or `RotationOverlap`, or `False` with
`SigningKeySecretConflict`, `JWKSConfigMapConflict` or `SigningKeyInvalid`. Neither changes the
zone's `Ready`.

| Series | Meaning |
| --- | --- |
| `knext_backendservice_reconcile_total{result}` | Function reconcile loops, by `success` or `error`. |
| `knext_backendservice_refusals_total{reason}` | Times a function was refused, by reason. Present at 0 from start-up. |
