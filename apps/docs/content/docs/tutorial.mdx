A start-to-finish walkthrough: empty directory → a running Next.js app that **scales to zero** when
idle and wakes on the next request. Roughly 20 minutes, most of it waiting on a container build.

[Getting started](/docs/getting-started) is the reference version of these steps for an app you
already have. This page is the guided one, and it ends by proving the app really does sleep — which
is the part worth seeing.

## What you need first

This tutorial deploys to a **real cluster**. Three things must exist before step 1, and none of them
is knext:

1. **A Kubernetes cluster with Knative Serving**, and the knext operator installed on it — see
   [Install](/docs/install). Without Knative there is nothing to scale to zero.
2. **A container registry** you can push to, and that your cluster can pull from.
3. **An object-storage bucket** on `gcs`, `s3`, `minio`, or `azure`, with that provider's CLI
   (`gsutil` / `aws` / `mc` / `az`) installed **and authenticated** where you run the build. knext
   shells out to it to upload static assets.

<Callout type="warn">
There is no local-only path in this tutorial. Everything below assumes a cluster you can reach with
`kubectl`. If `kubectl get ksvc` fails, stop and fix that first — every later step depends on it.
</Callout>

## 1 · Create the Next.js app

Nothing knext-specific yet. Any Next.js 16 app works; this is just to have something real to deploy.

```bash title="shell"
npx create-next-app@latest my-first-knext-app --ts --app
cd my-first-knext-app
```

## 2 · Add knext

```bash title="shell"
npm i @getknext/core
npx kn-next --version
```

`@getknext/core` is the whole deploy path: the official Next.js adapter, the typed config, and the
`kn-next` CLI. The CLI arrives on your `PATH` through `node_modules/.bin`, so `npx kn-next` works
without a global install.

## 3 · Point Next.js at the adapter

knext is a **Deployment Adapter** on Next.js's official API — not a fork and not a custom runtime.
One line tells Next.js to use it:

```ts title="next.config.ts"
import type { NextConfig } from 'next';

const config: NextConfig = {
  adapterPath: '@getknext/core/adapter',
};

export default config;
```

The adapter sets `output: 'standalone'` for you at build time; you do not need to add it.

<Callout type="info">
On Next.js 16.0.x–16.1.x the option lives under `experimental`
(`experimental: { adapterPath: '@getknext/core/adapter' }`). 16.2+ accepts it at the top level.
</Callout>

## 4 · Add the health route

**Do not skip this one.** The operator points Knative's readiness *and* liveness probes at
`/api/health` by default. `create-next-app` does not generate that route, so without it the probe
404s, the revision never becomes Ready, and step 8 will report `Ready=False` forever with nothing
obviously wrong in your app.

```ts title="app/api/health/route.ts"
export const dynamic = 'force-dynamic';

export function GET() {
  return Response.json({ status: 'ok' });
}
```

That is enough to go Ready. For a real app you want a health check that reports on its dependencies
too — `@getknext/lib` ships `checkShallowHealth()` and `checkDeepHealth()` for exactly that.

<Callout type="info">
Prefer a different path? Set `healthCheckPath` in the config below and the operator points the
probes there instead.
</Callout>

## 5 · Describe the deploy

Create `kn-next.config.ts` next to `next.config.ts`. Only three things are required — `name`,
`registry`, and a `storage` block with `provider`, `bucket`, and `publicUrl`:

```ts title="kn-next.config.ts"
import type { KnativeNextConfig } from '@getknext/core';

const config: KnativeNextConfig = {
  name: 'my-first-knext-app',
  registry: 'registry.example.com/my-first-knext-app',
  storage: {
    provider: 'gcs',
    bucket: 'my-first-knext-app-assets',
    publicUrl: 'https://storage.googleapis.com/my-first-knext-app-assets',
  },
  scaling: { minScale: 0, maxScale: 10 },
};

export default config;
```

`minScale: 0` is the line that makes this a scale-to-zero deployment. Set it to `1` and you have an
ordinary always-on service — useful to know, because it is the single knob that changes the whole
character of the deployment.

Substitute your own registry, bucket and `publicUrl`. The values above are placeholders and will
fail.

## 6 · Preflight before you deploy

```bash title="shell"
npx kn-next doctor
```

`doctor` is read-only. It checks the things that make a first deploy fail for reasons that have
nothing to do with your app: the CRD is present, the operator is Ready, Knative Serving is
installed, the ingress class matches the controller actually serving it, and your local `kubectl` is
recent enough. Fix anything it reports before deploying — the failures it catches are much easier to
read here than they are halfway through a build.

## 7 · Deploy

```bash title="shell"
npx kn-next
```

That one command builds the image, pushes it, uploads static assets to your bucket, and applies a
`NextApp` custom resource to the cluster. The **operator** does the rest — it owns every Knative
object, so the CLI never creates a Service or Route itself.

Expect the first run to be slow: it is a full container build.

## 8 · Check it is up

```bash title="shell"
npx kn-next status
```

This prints the app's conditions and its URL. `status` reports what the cluster actually says — if
something is wrong it tells you so rather than showing a green tick, so read it rather than assuming.

Then hit the URL it gave you:

```bash title="shell"
curl -sSf <the-URL-status-printed>/ > /dev/null && echo OK
```

## 9 · Watch it scale to zero — the part worth seeing

This is what you came for. Leave the app alone and watch its pods:

```bash title="shell"
kubectl get pods -l serving.knative.dev/service=my-first-knext-app -w
```

Give it about **90 seconds** — Knative waits out a 60s stable window and then a 30s grace period
before terminating the pod, so a user watching for "about a minute" concludes it is broken. Then the
list empties: no pod, no container compute for this app. (Your *nodes* keep running and billing
unless a cluster autoscaler independently reclaims them — scale-to-zero reclaims the pod, not the
machine.)

Now make one request:

```bash title="shell"
curl -sSf <the-URL-status-printed>/ > /dev/null && echo "awake"
```

Watch the pod reappear in the other terminal. Knative queued your request, started the pod, and
served it — normally you just get a slower response rather than an error. It is not a guarantee: a
cold wake can still return 503 if the revision or the readiness probe does not come up in time, and
the `-sSf` above will exit non-zero if that happens.

<Callout type="info">
**That first request after idle pays a cold start,** and how long it takes depends on your cluster,
your node sizing, whether the image is already cached on the node, and the app itself. We publish
measured distributions rather than a single headline number, because on a contended cluster the
spread is wide enough that a median would mislead you. See [Scale to zero](/docs/scale-to-zero).
</Callout>

## 10 · When something goes wrong

| Symptom | First thing to run |
|---|---|
| Deploy fails before the build | `npx kn-next doctor` |
| Deploy succeeds, app never becomes Ready | `npx kn-next status` — it reports the real condition |
| Apply is rejected for an unknown field | Your operator is probably older than your CLI. Upgrade the operator first, then the CLI |
| Assets 404 in the browser | Check `storage.publicUrl` matches where the bucket actually serves, and that the provider CLI was authenticated during the build |

## 11 · Clean up

```bash title="shell"
kubectl delete nextapp my-first-knext-app
```

Delete the `NextApp` and the operator removes what it created — and read the next sentence before
you run this against anything you care about.

<Callout type="warn">
**Deleting the `NextApp` also reaps app-scoped external state.** A finalizer clears the object-store
keys under this app's own `<app-name>/` prefix, and the Redis keys under its cache key prefix. If you
have parked anything else under that prefix in the same bucket, it goes too. **Registry images are
not touched** — those remain yours.
</Callout>
