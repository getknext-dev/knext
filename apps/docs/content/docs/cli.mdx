The `knext` binary ships in **`@getknext/core`** (`npm i @getknext/core`), so it is available as
`npx @getknext/core` in any project that depends on it. It is a small dispatcher around one job:
**build → push → apply the `NextApp` CR**. Everything on the cluster is reconciled by the operator;
the CLI's cluster writes are limited to applying or patching the CR (and, with the optional
`@getknext/grpc` package, applying a zone function's `BackendService`), and its diagnostic commands
are strictly read-only.

Use `npx @getknext/core <command>` (or a locally installed `knext`, once `@getknext/core` is a
project dependency) — never bare `npx knext` on its own. The unscoped name `knext` on the public
npm registry belongs to an unrelated package, so outside a project with `@getknext/core` already
installed, `npx knext` runs someone else's code instead of this CLI.

```bash
knext create         # scaffold a new knext-ready app (writes files, no cluster changes)
knext init-ci        # generate a deploy workflow and its scoped RBAC (writes files, no cluster changes)
knext validate       # check knext.config.ts is filled in and valid (no cluster needed)
knext doctor         # cluster-prereq preflight (read-only)
knext [deploy]       # default — build → push → apply the NextApp CR
knext build          # the build + asset-upload steps only, without deploying
knext status         # the NextApp's honest conditions (read-only)
knext rollback       # pin traffic to a prior Knative Revision
knext cleanup        # remove the app from the cluster (deletes its NextApp CR)
knext db bind        # bind an existing Postgres Secret to the CR
knext db migrate     # apply pending migrations against the writer, once
knext gc             # reap old _next/static/<build-id>/ asset prefixes
knext add function   # add a function to this zone: its contract, plus a Go or Rust server project (Beta)
knext deploy function # apply a zone function's BackendService (Beta)
knext generate       # write the server-only clients for this zone's functions (Beta)
knext ffi init       # opt this zone into in-process Rust (Beta, Bun only)
knext ffi generate   # build the zone's Rust crate and write its typed wrapper (Beta)
knext ffi check      # fail if the committed Rust wrapper is out of date (Beta)
```

`knext --help` lists exactly this set, `create` first. `add function`, `deploy function` and
`generate` come from one optional package, and the `ffi` commands from another; see
[`knext add function`](#knext-add-function), [`knext deploy function`](#knext-deploy-function) and
[`knext ffi`](#knext-ffi).

The command is `knext`. If a script still calls the older command name, see
[Upgrading](/docs/upgrading#version-specific-step-the-kn-next-command-is-gone) for what to change.

<Callout type="info">
**Strict parsing, plain errors.** Every command — including the default `deploy` — fails loudly on
unknown flags, dangling values, and stray positionals: a typo'd `--to` or `--wacth`, or a
`knext --namespace prod cleanup` with the command in the wrong place, is a hard error rather than a
silent fall-through to a different (possibly opposite) action. Those errors print as a short message
and exit 1 — no stack traces. `--help` works on every command and always exits without doing any
work, including on destructive ones like `cleanup`.
</Callout>

<Callout type="warn">
**Unknown commands are errors, not deploys.** A first argument that is not one of the commands above
fails with `unknown command: <x>`, a "did you mean" suggestion, and exit 1 — so `knext celanup`
never ships a deployment. The same applies to a command in the wrong slot: `knext -n prod cleanup`
fails with `unexpected argument: cleanup` and tells you the command comes first, rather than
deploying to `prod`. Running the bin with **no** command (`npx @getknext/core`) or with flags only
(`knext --skip-build`) still runs **deploy**, which is the advertised default.

`preview` and `loadtest` are **not** bin subcommands; they ship as separate runnable entries inside
the package (see [Directly runnable entries](#directly-runnable-entries) below).
</Callout>

## `knext create`

Scaffolds a new knext-ready Next.js app into the current directory (or the one you name). It writes
files and makes **no** cluster changes, so it is safe to run and inspect before anything is deployed.

Two of the files it writes are the ones people most often miss when wiring knext into an app by
hand, and both are silent failures rather than loud ones:

- **`src/app/api/health/route.ts`** — the shallow route Knative's readiness *and* liveness probes
  both target. Without it a deployed revision answers 404 there, never reports Ready, and then gets
  restart-looped by liveness while the application logs show nothing wrong. The generated route is
  deliberately shallow: no imports, no I/O, no database. See
  [Configure the deploy](/docs/learn/configure-the-deploy#the-health-route--do-not-skip-this).
- **the server entry that serves `/_next/image`** — `next/image` optimization is handled by knext's
  own runtime entry rather than by the platform, so an app scaffolded without it serves the original
  bytes for every image and nothing reports the difference. See
  [Image caching](/docs/image-caching).

`create` refuses to clobber: an existing file aborts the whole write before anything is touched,
unless you pass `--force`. It also refuses when a config file already present would shadow the one
it writes, rather than emitting a config Next would never read.

By default, `create` scaffolds the **standalone target**: plain `next build` (Turbopack), `output:
'standalone'` in `next.config.ts`, and the official Next.js Deployment Adapter wired through
`adapterPath` — `knext build`/`deploy` stage the matching runtime image automatically, so the
scaffold ships no Dockerfile for it. Pass `--builder vinext` instead to scaffold
the compiled single-executable target — its own `Dockerfile`, `vite.config.ts`, and
`build: 'vinext'` pinned in `knext.config.ts`, plus a `Dockerfile.self-contained` reference
recipe for the optional `--self-contained` single-executable build (see
[Self-contained mode](/docs/build-pipeline#self-contained-mode-experimental)) — the standalone
target never scaffolds that file, since `--self-contained` only applies to the vinext build. See
[the adapter and the compiled build](/docs/official-adapter) for the trade-off between the two.

### The questions `create` asks

Run on a terminal with no flags, `create` asks five questions. Press Enter on each to take the
default: the scaffold described above, with React Compiler turned on. At the end it prints the
equivalent flags, so you can repeat the same scaffold in CI.

| Question | Choices | Default | What changes |
|---|---|---|---|
| Runtime | `bun`, `node` | `bun` | `node` writes `runtime: "node"` to `knext.config.ts` and adds the Node Redis client, `ioredis`, to the app's dependencies. Bun has a Redis client built in, so a Bun app gets nothing extra. |
| Builder | `turbopack`, `webpack`, `vinext` (Beta) | `turbopack` | `webpack` sets the `build` script to `next build --webpack` and writes `build: "webpack"`; `vinext` scaffolds the compiled single-executable shape. |
| ISR / data cache | `none` (in memory, per pod), `redis` | `none` | `redis` writes a `cache` block that reads `REDIS_URL`. |
| Object storage | `none`, `gcs`, `s3`, `minio`, `azure` | `none` | Writes a `storage` block for that provider, with `<placeholders>` for you to fill in. |
| React Compiler | yes / no | **yes** | On `turbopack`/`webpack`: writes `reactCompiler: true` to `next.config.ts` and adds `babel-plugin-react-compiler` to `devDependencies`. On `vinext`: writes `react: { compiler: true }` to the vinext plugin in `vite.config.ts` and adds the four packages it needs. Answer `n`, or pass `--no-react-compiler`, to leave it off. See [React Compiler](/docs/react-compiler). |

With a Redis cache, set `REDIS_URL` when you run `knext deploy`, and keep the value in a Kubernetes
Secret or your CI secrets rather than in the file. `knext deploy` stops with an error while it is
empty. `KN_REDIS_URL` works too, at `knext deploy` and `knext preview`, and overrides `cache.url`
when both are set. With a storage provider, `knext deploy` names any placeholder you have not filled in.

`create` never asks when it cannot expect an answer: with any flag, with `--yes`, when `CI` is set,
or when stdin or stdout is not a terminal, it uses the default for every choice you did not pass.
A pipe or a CI job never waits on a question.

When it finishes, `create` prints the build target and runtime it chose, defaults included, and how
to change them:

```text title="output"
Build target: turbopack (Next.js `next build` with Turbopack)
Runtime: bun (compiled Bun executable)
Pick others when scaffolding with --builder <turbopack|webpack|vinext> and
--runtime <bun|node>, or later with `build` and `runtime` in knext.config.ts.
```

```bash title="shell"
knext create my-app                    # asks the questions on a terminal; defaults elsewhere
knext create my-app --yes              # defaults, no questions
knext create my-app --runtime node --cache redis   # Node + Redis, no questions
knext create my-app --no-react-compiler            # without React Compiler
knext create my-app --builder vinext   # compiled single-executable target
knext create my-app --dry-run          # list the files it would write, write nothing
```

| Flag | Notes |
|---|---|
| `--name <name>` | App name. Defaults to the directory name. |
| `--runtime <bun\|node>` | Server runtime. Default `bun`. |
| `--builder <turbopack\|webpack\|vinext>` | Build target. Default `turbopack`, the standalone shape; `default` is accepted as `turbopack`. `vinext` is the compiled single-executable shape, **Beta** — see [Stability tiers](/docs/stability). |
| `--cache <none\|redis>` | ISR / data cache. Default `none`. |
| `--storage <none\|gcs\|s3\|minio\|azure>` | Object storage for static assets. Default `none`: assets are served from the container image. |
| `--react-compiler`, `--no-react-compiler` | Turn React Compiler on or off. Default on, for every builder. Passing both is an error. |
| `-y`, `--yes` | Ask nothing; use the defaults for every choice not given as a flag. |
| `--force` | Overwrite existing files. |
| `--dry-run` | List the files that would be written and write nothing. |
| `-h`, `--help` | Show the usage help. |

**Exit code:** `0` on success (including `--dry-run` and `--help`); `1` on a usage error (an
unrecognized `--runtime`, `--builder`, `--cache` or `--storage` value, both `--react-compiler`
and `--no-react-compiler`, an unexpected extra argument, or a cancelled question) or a scaffold failure (for example an
invalid app name, or an existing file without `--force`).

The generated `package.json` pins its `@getknext/*` dependencies at the **CLI's own version** — the
CLI and those packages release together, so a published CLI always scaffolds versions that exist on
the registry. If the CLI you ran carries a version that was never published (typically a build from
a source checkout), `create` checks the registry and prints a warning telling you that
`npm install` would fail and what to do instead. The check is best-effort: with no network access,
`create` still scaffolds normally and stays quiet.

## `knext init-ci`

Sets up push-to-deploy against **your** cluster. It writes two files and touches no cluster: a
deploy pipeline (`.github/workflows/` or `.gitlab-ci.yml`, chosen with `--provider`) and a manifest
with a ServiceAccount, Role, and RoleBinding that grant permission to write one kind of object in
one namespace. knext hosts nothing and never holds your credentials. See
[Deploy from GitHub Actions](/docs/github-action) and [Deploy from GitLab CI/CD](/docs/gitlab-ci).

```bash
knext init-ci --namespace my-app
# or, for GitLab:
knext init-ci --namespace my-app --provider gitlab
```

Both providers run the SAME two refusals, in the SAME order, before any cluster-mutating call:
the exec/auth-provider kubeconfig refusal, then the credential-scope + hazard spot-check. On
GitHub that is the composite action's two steps; on GitLab it is two dedicated
pipeline jobs (`kubeconfig-check`, `credential-preflight`) that call `knext doctor --ci-kubeconfig`
and `knext ci-preflight` — the same classifiers, exposed as CLI verbs so the pipeline never
re-derives the rules in shell.

It also prints the exact commands to mint a kubeconfig for that ServiceAccount — a `kubectl create
token`, bound and namespace-scoped, plus the `kubectl config set-*` calls that assemble a
standalone kubeconfig file around it. **You run these yourself**; knext writes nothing to the
cluster. If your own kubeconfig references its certificate authority as a file (or skips TLS
verification), the commands warn you before writing a kubeconfig with an empty CA.

**The minted token expires after one year** (`--duration=8760h`). When it expires, CI can no longer
reach the cluster. Before then, **re-run the whole printed recipe from the top** and push the secret
again (for example with `--push-secret` below) — it removes its own output file first, so the
renewed token replaces the old one. Re-running only the last two lines over an existing file refuses
instead of silently keeping the old token. Change `--duration` to match your rotation policy; your
cluster may cap it lower. To revoke the token early, delete and recreate the `knext-deployer`
ServiceAccount.

Any kubeconfig that instead needs a cloud CLI on the runner (an `exec:` or
`auth-provider:` entry — the `aws`/`gcloud`/`oci`/`az` shape) is refused wherever knext reads one —
here, in the GitHub Action, and in `knext doctor --ci-kubeconfig` — with the same message:

> This kubeconfig needs cloud-account credentials on the runner. Use the knext-deployer
> ServiceAccount token.

Bearer tokens and client certificates are accepted — neither runs anything on the runner.

| Flag | Notes |
|---|---|
| `--namespace <name>` | **Required.** The namespace to deploy into; it bounds what the credential can do. |
| `--provider <name>` | `github` (default) or `gitlab`. Chooses which pipeline file is generated; the RBAC manifest and the mint recipe are identical either way. |
| `--app-dir <path>` | App directory, relative to the repository root (default `.`). |
| `--force` | Overwrite files that already exist. |
| `--push-secret <path>` | Read a kubeconfig from `<path>` and push it as `KNEXT_KUBECONFIG` — via `gh secret set` (github) or `glab variable set --masked --protected` (gitlab). Refuses a kubeconfig that needs cloud-account credentials, same as above. The value is never printed or logged — it is only ever piped to the provider CLI's stdin. With `--provider gitlab` and no `glab` on `PATH`, it prints the manual steps to add the variable in GitLab's UI instead of failing. |
| `-h`, `--help` | Show the usage help. |

**Exit code:** `0` on success (including `--help`); `1` on a usage error (missing `--namespace`, an
unrecognized `--provider`) or a failure pushing `--push-secret` (a missing file, or the provider
CLI's push itself failing).

Re-running it without `--force` never clobbers a file you've edited: it names the exact file and
points you at the flag, e.g. `.github/workflows/knext-deploy.yml already exists — left alone (use
--force to overwrite)`.

## `knext ci-preflight`

The credential-scope + hazard spot-check that `init-ci --provider gitlab`'s generated pipeline runs
before `deploy` — the same check `kn-next-action`'s composite action runs on GitHub, exposed as a
CLI verb so a pipeline with no composite-action equivalent can invoke it through the published CLI
instead of re-deriving the rules in shell. Not typically run by hand.

It asks your cluster what the credential can do (`SelfSubjectRulesReview`) and, because some
clusters (OKE, GKE with IAM) cannot fully answer that, also spot-checks specific hazardous
permissions (`SelfSubjectAccessReview`). Every failure mode — the review cannot be reached, returns
no verdict, or reports the credential can do more than the published Role — refuses rather than
proceeding: a check that passes when it cannot see is not a check.

```bash
knext ci-preflight --namespace my-app
```

| Flag | Notes |
|---|---|
| `--namespace <name>` | **Required.** The namespace the credential is scoped to. |
| `--kubeconfig <path>` | Kubeconfig file to check. Defaults to `$KUBECONFIG`. |
| `-h`, `--help` | Show the usage help. |

**Exit code:** `0` (including `--help`) — prints `preflight: credential is correctly scoped for
namespace "<ns>".` when the credential passes; `1` on a usage error (missing `--namespace`, no
kubeconfig configured) or any refusal, printing the reason — never the kubeconfig's bytes — to
stderr.

## `knext vinext-patches`

Applies the vinext fixes knext bundles ahead of upstream vinext releases to the vinext installed
for this app, so you do not wait for those fixes to ship upstream. An app created with
`knext create --builder vinext` runs it from its `postinstall` script, and `knext build` runs it
again before the vinext build, so it is not typically run by hand.

The fixes are tied to one exact vinext version (the one `knext create` pins). With any other vinext
version installed it changes nothing and says so. Re-running it is safe: fixes that are already in
place are left alone. If a fix neither applies cleanly nor is already present — vinext's files were
modified some other way — it refuses rather than half-applying; reinstall your dependencies and run
it again. Applying is all-or-nothing per fix: if writing any of a fix's files fails (for example a
read-only `node_modules`), the files it already changed are restored and the command exits `1`.

The `postinstall` script skips this step quietly when `@getknext/core` is not installed, as in a
production-only install (`npm ci --omit=dev`), because it is a development dependency.

To turn the bundled fixes off, for example because you patch vinext yourself, set
`KNEXT_VINEXT_PATCHES=0`. Both the `postinstall` step and `knext build` then leave vinext untouched
and print a line saying the fixes were not applied.

If your app has a vinext version other than the one the fixes were checked against, none of them
are applied. By default `knext build` carries on and prints a warning that says how many fixes were
skipped, what the build is missing, and how to fix it (install the expected vinext version and run
`knext vinext-patches`). Set `KNEXT_VINEXT_PATCHES=strict` to make that mismatch an error instead:
`knext build` and `knext vinext-patches` then stop with exit code `1` and the same fix. Use it in CI
when you want a build with missing fixes to fail rather than ship. [`knext doctor`](#knext-doctor)
reports the mismatch too.

```bash
knext vinext-patches          # apply
knext vinext-patches --check  # report only, change nothing
```

| Flag | Notes |
|---|---|
| `--check` | Report whether every fix is applied without changing any file; exit `1` when one is missing. |
| `KNEXT_VINEXT_PATCHES=0` (env) | Skip the bundled fixes entirely, here and in `knext build`. |
| `KNEXT_VINEXT_PATCHES=strict` (env) | Fail, instead of warning, when the installed vinext is not the version the fixes were checked against. |
| `-h`, `--help` | Show the usage help. |

`KNEXT_VINEXT_PATCHES` accepts `0` (or `false`, `off`, `no`), `strict`, or unset; the value is not
case-sensitive and surrounding spaces are ignored. Any other value, such as a misspelling like
`stric`, is treated as unset: `knext vinext-patches`, and `knext build` on the vinext build target,
print a warning that names the value and lists the accepted ones, and the default warn behaviour
applies. Other build targets do not read the variable.

**Exit code:** `0` (including `--help`, when vinext is not installed, and when it is a different
version unless `KNEXT_VINEXT_PATCHES=strict` is set); `1` on a usage error, a fix that conflicts
with the installed vinext, a different vinext version under `KNEXT_VINEXT_PATCHES=strict`, or
`--check` finding a fix not yet applied.

## `knext deploy` (default)

Loads and validates `knext.config.ts`, runs your build (`next build` with standalone output on the
default target), uploads static assets (with object storage configured), builds and pushes the
container image, resolves its **digest**, and applies a digest-pinned `NextApp` CR. On the vinext
build with your own Dockerfile that rebuilds in-image, the assets are extracted from the pushed
image and uploaded from there — see
[Custom Dockerfiles that rebuild in-image](/docs/multi-cloud#custom-dockerfiles-that-rebuild-in-image). After a successful deploy it also runs a
best-effort [asset-retention GC](#knext-gc) — a GC failure never fails a deploy that has already
shipped.

With no `storage` block in the config, the upload and GC steps are skipped and the deploy prints a
notice that static assets are served from the image instead — see [Starting without object
storage](/docs/multi-cloud#starting-without-object-storage).

**After the `NextApp` CR is applied**, deploy waits briefly (up to 15s) for the operator to begin
reconciling THIS apply specifically — not a stale status left over from an earlier one — before
reporting the URL. That holds on a redeploy too: if the operator isn't running, is
`CrashLoopBackOff`, or is watching the wrong namespace, deploy says so plainly instead of quoting the
URL from the last time it actually reconciled: `NextApp applied; no operator reconciled it in 15s.
Check the operator pod: kubectl get pods -n kn-next-operator-system.`

**A held change fails the deploy.** If the operator observes your change but holds it, because the
platform's defaults make the app's effective spec invalid (for example the connection budget is
exceeded), the previous version keeps serving and the app reports not Ready. Deploy then exits `1`
with the operator's message, which names the field, and the remedy: raise the platform budget, or
lower `maxScale` / `poolMax` in `knext.config.ts`, then deploy again.

The same applies when the operator rejects your own spec outright (for example a field that fails
validation, or a footprint over the built-in budget): the previous version keeps serving, deploy exits
`1` with the operator's message naming the field, and the remedy is to fix the spec in
`knext.config.ts` and deploy again.

**Placeholders fail fast.** Before any build step, deploy refuses config values still carrying a
`<...>` placeholder from the scaffold (like `ghcr.io/<your-user>`), with a per-field explanation of
what the value is for and what to put there — so an unfinished config never costs you a
multi-minute build. Values under `env` are exempt: they are your app's own free-text data, where
angle brackets can be perfectly legitimate (an HTML allowlist, a template string). Run [`knext validate`](#knext-validate) to get the same check on its own.
And if the build script cannot find `next` (dependencies not installed yet), deploy tells you to
run `npm install` instead of printing a crash.

| Flag | Notes |
|---|---|
| `-r`, `--registry` | Container registry (overrides config; env fallback `KN_REGISTRY`). |
| `-b`, `--bucket` | Storage bucket (overrides config; env fallback `KN_BUCKET`). Requires a `storage` block in the config — with none, the flag is a hard error rather than a silently-invented storage setup. |
| `-t`, `--tag` | Image tag (default: timestamp; env fallback `KN_IMAGE_TAG`). The tag doubles as the Next.js `BUILD_ID` — see [Skew protection](/docs/skew-protection). |
| `-n`, `--namespace` | Kubernetes namespace (default `default`; env fallback `KN_NAMESPACE`). |
| `--context <ctx>` | kubectl context to target (default: your current-context; env fallback `KN_CONTEXT`). Every cluster call this deploy makes is sent to `<ctx>`, so it never lands on whichever cluster your kubeconfig happens to point at. |
| `--image <ref>` | Deploy a **pre-built** image instead of building one. Applies a `NextApp` CR pointing at `<ref>` and does **no** docker build or push (env fallback `KN_IMAGE`). The ref must be **digest-pinned** (`registry/name@sha256:…`) — a tag-only ref is rejected, matching what the operator's admission accepts. Use it when you already have a published image or have no working `docker buildx`. A pre-built image is the source of truth for **both** its server and the static assets baked into it, so `--image` **implies `--skip-build` and `--skip-upload`**: knext does not re-run `next build` or upload assets, because it cannot know the image's baked `BUILD_ID` and any freshly-uploaded `_next/static/<id>/` prefix would not match what the deployed server serves (see [Skew protection](/docs/skew-protection)). `--registry` has no effect alongside it (the ref is already fully qualified) and is reported as ignored, and a placeholder `registry` in `knext.config.ts` does not block the deploy (other placeholders, such as the storage bucket, still do). With `knext.ffi.json`, the image is expected to carry its Rust library already, so nothing needs to be staged under `native/ffi/` in the checkout; `runtime: 'node'` and the self-contained mode are still refused. |
| `--skip-build` | Skip the `next build` step. With `knext.ffi.json`, `knext ffi build` does not run either, so the Rust library must already be staged under `native/ffi/` for the image's architecture (by an earlier `knext build`); the deploy stops with an error if it is not. This check does not apply with `--image`, which builds nothing from the checkout. |
| `--skip-upload` | Skip the asset-upload step (also skips the post-deploy GC). |
| `--skip-image-lockstep-check` | For a custom in-image-build Dockerfile only (see [Custom Dockerfiles that rebuild in-image](/docs/multi-cloud#custom-dockerfiles-that-rebuild-in-image)): skip the post-build check that the pushed image's server actually embeds `ASSET_PREFIX` and matches the deploy's build id, and the check that every client chunk the image's server references was uploaded (assets are still taken from the image). knext logs a warning every time this is used. Skipping it means a genuinely broken `ASSET_PREFIX`/build-id lock-step (see [Skew protection](/docs/skew-protection)) is no longer caught before the cluster write — use it only when the check misidentifies your Dockerfile's server layout. |
| `--dry-run` | Print the `NextApp` CR without applying it. |
| `-h`, `--help` / `-v`, `--version` | Help / version. |

**Exit code:** `0` on success (including `--help`/`--version`); `1` on a usage error (an unknown
flag, a stray positional), a missing `knext.config.ts`, or a deploy failure at any step (build,
upload, image push, or the CR apply).

<Callout type="info">
**Piping `--dry-run` to `kubectl apply -f -`.** Under `--dry-run`, stdout carries only the rendered
`NextApp` YAML document; every log line goes to stderr. The output pipes or redirects cleanly:

```bash title="shell"
knext deploy --dry-run | kubectl apply -f -
knext deploy --dry-run > nextapp.yaml 2> deploy.log
```

`knext db bind --dry-run` follows the same rule for the patch it prints.
</Callout>

Config validation runs automatically when the config loads. [`knext validate`](#knext-validate) runs
the same checks on their own.

<Callout type="info">
**No `knext.config.ts` in this directory?** That is treated as an expected state, not an error:
the CLI prints a short note explaining what the file is, points you at `knext create` for a new
app, and exits with status 1 — no stack trace.
</Callout>

## `knext build`

The build half of `deploy`, on its own: runs the project's build script (`next build` with
`output: 'standalone'` on the default target), heals the standalone output, and — with object storage configured —
uploads static assets to the bucket (with no `storage` block, the upload is skipped with a notice;
assets ship inside the image). It makes **no** cluster writes.

On the vinext build (`build: 'vinext'`), after compiling the single executable, `build` **boots it
once** and checks the three things the platform depends on: your health path answers `200`, the metrics port serves `/metrics`, and the
process exits cleanly on `SIGTERM`. Those obligations live in your app's server entry, so an entry
that was swapped or broken still compiles — this catches it on your machine instead of on the
cluster, and the error names the obligation that is missing.

The smoke boots a binary built for **your** machine's architecture; the binary that ships in the
image is built for Linux and is verified separately when the image is built.

<Callout type="info">
**The compile step needs Bun.** The CLI runs under plain Node, but compiling the executable for
`runtime: 'bun'` (the default) or the vinext build shells out to `bun` (1.4 or newer) on your PATH.
`runtime: 'node'` on the standalone targets needs no Bun. A missing Bun stops the build with
install guidance; a Bun that is present but cannot report its version stops the build with that
underlying error — the two are never conflated. See [the Bun runtime](/docs/bun-runtime).
</Callout>

**In-process Rust (Beta, Bun only).** When the app has a `knext.ffi.json`, `build` (and `deploy`
and `preview`, which build the same way) first checks the Rust crate's dependencies with
`cargo deny check`, cross-compiles it for the image (`knext ffi build`: Linux musl, release,
`--locked`), refuses a library that links anything the Alpine image lacks, stages it under
`native/ffi/` with a provenance record and an SBOM, and fails if the committed generated wrapper is
out of date (run `knext ffi generate`). The image then ships `native/` beside the executable, with a
checksum manifest the loader verifies. This needs Rust, pinned versions of four cargo tools and zig
on the build machine; see [Building images](/docs/rust-in-process#building-images). Two configurations are refused before any build
work, with a message that says how to fix them: `runtime: 'node'` (Rust is called through
`bun:ffi`, which exists only in Bun) and the self-contained mode. An app without `knext.ffi.json`
builds exactly as before.

| Flag | Notes |
|---|---|
| `--skip-next` | Reuse the existing project build (`.next/`, or `.output/` on the vinext target) instead of running it again. With `knext.ffi.json`, `knext ffi build` does not run either: the Rust library already staged under `native/ffi/` is reused as it is, and the build stops with an error if nothing is staged there for the image's architecture. |
| `--skip-smoke` | Do not boot the compiled executable. For CI that cannot execute it (a foreign-architecture runner). The build prints a loud warning and the artifact ships unverified. |
| `--verbose` | List every compile and closure note. By default they are folded into one line, such as `[knext standalone-compile] 12 notes; rerun with --verbose for details`. Warnings and errors always print in full. |
| `--self-contained` | Opt in to the self-contained single-executable mode, overriding `selfContained` in `knext.config.ts`. Experimental: on the vinext target the binary needs nothing beside it; the other targets do not use it yet, so there it only shows up in the build log and the build output is unchanged. Refused for an app with `knext.ffi.json`. |
| `-h`, `--help` | Show the usage help. |

**Exit code:** `0` on success (including `--help`); `1` on a usage error (an unknown flag), a missing
`knext.config.ts`, or a build/smoke failure.

## `knext cleanup`

Tears down the app named in `knext.config.ts` by issuing exactly **one** cluster write:
`kubectl delete nextapp <name> --ignore-not-found`. Owned resources (Knative Service,
ServiceAccount, PVC) go with it via owner-reference garbage collection, and the operator's finalizer
clears that app's object-store prefix and Redis keyspace — scoped strictly to that app.

Because the command is destructive, a stray positional or an unknown flag is an error rather than an
ignored argument.

| Flag | Notes |
|---|---|
| `--context <ctx>` | kubectl context to target (default: your current-context; env fallback `KN_CONTEXT`). Cleanup deletes on `<ctx>`, never on whichever cluster your kubeconfig happens to point at — so `knext cleanup --context staging` cannot tear down production by mistake. |
| `-h`, `--help` | Show the usage help. |

**Exit code:** `0` on success (including `--help`); `1` on a usage error (any flag or positional
other than `--context`/`-h`/`--help` — destructive commands never silently ignore an argument), a
missing `knext.config.ts`, or a failed delete.

## `knext validate`

Checks `knext.config.ts` **without touching a cluster** — it reads your config file and nothing
else: no kubectl, no docker, no network. It loads the config, runs every schema check, and flags
placeholder values (like `ghcr.io/<your-user>`) that still need real ones, explaining per field
what the value is for and what to put there.

```bash
knext validate          # exit 0 means: ready for knext deploy
```

**Exit code:** `0` when the config is complete and valid; `1` with a plain per-field message
otherwise. `knext deploy` runs the same checks before its first build step, so you never need to
run `validate` first — it exists so you can iterate on the config without paying for a build.

It takes no options beyond `-h`/`--help`.

## `knext doctor`

A **read-only** preflight that checks the cluster prerequisites: the `NextApp` CRD, operator
readiness, the cert-manager-backed admission webhook, the Knative `ingress-class` against the
reconciler that actually serves it, operator-image pullability, Knative Serving itself, and
whether your cluster's CNI can **enforce** the default-on `NetworkPolicy` the operator writes —
on flannel it cannot (the policy is declarative only), and doctor says so plainly rather than
guessing; "cannot determine" is reported as its own outcome, never as "enforced".

**Redis key prefixes.** When any `NextApp` uses a Redis cache, doctor compares the apps' key
prefixes: `cache.keyPrefix`, a `REDIS_KEY_PREFIX` in `env`, or the per-app default the operator
derives. It `WARN`s, naming the apps, when:

- two apps share a prefix: they read each other's entries, and one app's clean-up deletes the
  other's cache;
- one prefix sits inside another's keyspace (`shop` and `shop:cache`), so the outer app's clean-up
  reaches the inner one;
- an app's keys sit under the shared fallback `kn-next:*`, because its prefix is that fallback or
  sits inside it (`kn-next:cache`), even on its own: any app with no prefix lands there too, so that
  keyspace is never cleared after an outage and its stale entries stay until they expire;
- an app's stored `cache.keyPrefix` is one the cluster now refuses (too long, whitespace, a Redis
  pattern character, or the reserved shared fallback `kn-next:*`), whatever its cache provider. Fix it before the
  app's next update; see [what a key prefix may contain](/docs/isr-caching#key-prefix-rules).

The row never fails, because two apps can point at different Redis servers, which doctor cannot see.
A prefix that comes from a Secret (`secrets.envMap`) cannot be read, so doctor names the app as not
verified. No row appears when no app uses Redis and no stored prefix is refused. See
[each app has its own Redis keyspace](/docs/isr-caching#key-prefix).

A few checks are **local** — they read files in the directory you run `knext doctor` from and
never touch the cluster, so they still run even when nothing above is reachable:

- **Static asset mode** — states whether object storage is configured for this app, or assets are
  served from the image.
- **CRD schema coverage** — whether the installed `NextApp` CRD defines every field this CLI can
  emit. An older CRD than your CLI is reported here; `knext deploy` also dry-runs the apply on the
  server before touching the cluster.
- **kubectl strict validation** — a local check that your `kubectl` is v1.25 or newer, because
  `knext deploy` applies the CR with `--validate=strict` so an unknown field is rejected instead of
  silently dropped.
- **Metrics port** — whether Knative's queue-proxy binds `:9091` on your cluster, which matters only
  if you override `METRICS_PORT` (the default is `9464`).
- **App image pullability** — whether each `NextApp`'s image can be pulled, and whether a pull
  credential is attached to the app's ServiceAccount.
- **CI kubeconfig safety** (opt-in, `--ci-kubeconfig <path>`) — checks a kubeconfig FILE, not the
  cluster: refuses one that needs cloud-account credentials on the runner (an `exec:` or
  `auth-provider:` entry), with the same message `init-ci --push-secret` and the GitHub Action use.
  Adds this one row only when the flag is passed.
- **vinext-on-node entry freshness** — if your app uses `build: 'vinext'` with `runtime: 'node'`,
  its `knext-node-entry.mjs` was written once by `knext create` and is never re-rendered by later
  builds or deploys. When a newer `@getknext/core` release changes that entry's runtime behavior
  (for example, adding the deployed `Cache-Control` normalization), an app scaffolded earlier keeps
  running its old copy silently — no error, no crash, just the old behavior. This check compares a
  version marker in your `knext-node-entry.mjs` against the one shipped in the installed
  `@getknext/core` package and `WARN`s with the exact fix when they differ: re-scaffold into a
  throwaway directory with `knext create --force <scratch-dir>` and copy the fresh
  `knext-node-entry.mjs` over yours (diff first if you made local edits). Apps that don't use this
  runtime combination, or that aren't run from their own directory, report `SKIP`.
- **vinext version** — knext bundles fixes for vinext that were checked against one exact vinext
  version. If your app has a different vinext installed, `knext build` skips every one of those
  fixes. This check compares the vinext in your `node_modules` with that version. An **older**
  vinext is a `FAIL`, because the fixes are certainly missing (including the Nitro image optimizer
  and the 404 for unmatched asset requests); a **newer** one is a `WARN`, because that release may
  already include them. Both name the fix: install the version knext expects and run
  `knext vinext-patches`. Apps without vinext get no row, and `KNEXT_VINEXT_PATCHES=0` reports
  `SKIP`.
- **Next.js minor** — whether the Next.js your app resolves is on a minor the official
  compatibility suite has credentialed. A supported but uncredentialed minor is a `WARN`, never a
  failure.
- **Next.js security advisories** — whether that Next.js is affected by a published critical or
  high advisory that has a fix. An affected version is a `FAIL` that names each advisory by its
  GHSA id and the version to upgrade to (for example, anything up to 16.4.0 must move to 16.4.1 or
  later — see [Next.js security upgrades](/docs/upgrading#nextjs-security-upgrades)). Apps with no
  resolvable Next.js get no row.

```bash
knext doctor                                        # human-readable checklist
knext doctor --json                                 # structured results for CI
knext doctor --verbose                              # add the raw kubectl/API diagnostic behind each message
knext doctor --ci-kubeconfig ./deployer.kubeconfig  # check a kubeconfig FILE before wiring it into CI
```

Each check reports `PASS`, `WARN`, `FAIL`, `SKIP`, or `ERROR` — and the distinction is deliberate.
When a probe itself fails, doctor **classifies the failure before mapping it to a result**, so a
flaky network is never reported as a missing CRD:

| Class | Meaning | Hint printed |
|---|---|---|
| not-found | The API server answered: the resource is absent. | Install the missing prerequisite. |
| network | The probe never got an answer (refused / TLS / timeout). | Check network/VPN and retry. |
| auth | Credentials failed (expired token, `Unauthorized`). | Re-authenticate and retry. |
| forbidden | Authenticated but RBAC denied the read. | Ask a cluster admin for `get`/`list` on the resource. |

**One plain sentence, no stack trace.** The messages you're most likely to hit before you have a
cluster wired up are each a single actionable line by default — no raw kubectl output, no jargon:

- **No cluster configured.** Before printing the network hint, doctor looks at your local
  kubeconfig: a missing kubeconfig file, or one with no `current-context`, is reported as
  `No Kubernetes cluster configured. See https://knext-platform.dev/docs/first-cluster.` — whichever of the
  two it is, you get the exact same sentence and the same walkthrough link. A connection refused on
  a local-only address (`127.0.0.1`, `localhost`, `0.0.0.0` — usually a leftover from a local
  cluster that is no longer running) gets its own, differently-worded message. The "check
  network/VPN and retry" hint is reserved for a real, remote cluster that stopped answering.
  `knext doctor --verbose` shows which of the two states it was and where it looked.
- **NextApp CRD not installed.** `NextApp CRD not found. Install the operator: kubectl apply
  --server-side -f <the published install manifest>.`
- **CRD version not served.** Doctor pairs your CLI with the cluster by CRD API version: the
  **NextApp CRD** row reads the versions the installed CRD serves and fails with `this CLI emits
  apps.kn-next.dev/<version>, but the installed nextapps.apps.kn-next.dev does not serve <version>
  … ` when yours is not among them, ending in `upgrade the operator first (operator, then CLI)`
  when the CRD only serves older versions, or `upgrade the CLI to match the operator` when it only
  serves newer ones (both when it is unclear which side is behind). A CRD that serves several
  versions passes as long as one is yours, deprecated or not; a CRD doctor cannot read fails
  rather than passing. The **Operator version** row is informational only — a different operator major
  is not a warning. See [Versioning](/docs/versioning).
- **Operator behind the CLI.** When the installed CRD is missing fields this CLI can emit, doctor
  says so as `operator behind CLI: the installed CRD is missing N field(s) this CLI emits — they
  would be dropped. Upgrade the operator first (operator, then CLI).` — the full field list (for
  filing a ticket or debugging) is available with `--verbose`.
- **CRD predates an optional feature.** If the only missing fields are ones the CLI emits just
  for a specific feature, doctor warns instead of failing and names the feature — for example
  `spec.security.writeFree — needed for write-free pods when `knext deploy` builds the image;
  upgrade the operator to use it`, or `spec.networking — needed for private apps`. Deploys that
  don't use those features are unaffected; one that does is refused before anything is uploaded.
- **Registry auth failure.** When an app's image can't be pulled anonymously and no credential is
  attached, doctor names the missing Secret/`imagePullSecrets` fix directly in the check's line,
  with a pointer to [private registries](/docs/private-registries).

**Exit code:** `1` on any hard `FAIL` **or** probe `ERROR` (the cluster state could not be
verified); `WARN`/`SKIP` never fail. A fully unreachable cluster degrades to all-`SKIP` and exits
`0` — doctor reports what it could verify, it does not guess.

## `knext status`

Renders the operator-reported truth from the `NextApp` CR — URL, image, and the conditions
`Ready`, `Degraded`, `Reconciling`, and `DatabaseReady` — with the operator's reason and guidance
verbatim when something is wrong (e.g. `IngressNotProgrammed`, `PinnedRevisionNotFound`).
Conditions an older operator does not report render as `not reported`.

```bash
knext status acme                 # one-shot
knext status acme --json          # structured subset (absent conditions are explicit nulls)
knext deploy && knext status --watch  # CI gate: poll until Ready=True
```

| Flag | Notes |
|---|---|
| `<app>` | Positional, optional — defaults to `name` from `knext.config.ts`. |
| `-n`, `--namespace` | Namespace (default `default`). |
| `--context <ctx>` | kubectl context to target (default: your current-context; env fallback `KN_CONTEXT`). Reads the `NextApp` CR on `<ctx>`, never on whichever cluster your kubeconfig happens to point at. |
| `--json` | One-shot only — rejected in combination with `--watch` (a 5s poll would emit concatenated JSON documents; poll `status --json` from your script instead). |
| `--watch` | Poll every 5s until `Ready=True`. Bounded at 10 minutes (exit `1` on timeout); tolerates up to 3 consecutive transient `kubectl` failures. |

**Exit code:** `1` **iff** the `Ready` condition is present with status `False` — a missing
condition is "not reported", not a failure. This makes `knext deploy && knext status --watch`
a usable CI gate.

## `knext rollback`

Shifts serving traffic to a prior Knative Revision by patching **only** the `NextApp` CR's
`spec.traffic` (one `kubectl` merge-patch); the operator renders the Knative traffic split. See
[Rollback & traffic split](/docs/rollback) for the full semantics.

```bash
knext rollback acme --to acme-00002              # pin 100% to a prior revision
knext rollback acme --to acme-00002 --canary 20  # 20% to latest-ready, 80% pinned
knext rollback acme                                    # clear the pin — back to latest-ready
```

| Flag | Notes |
|---|---|
| `--to <revision>` | Prior Knative Revision to pin. Omit to clear any pin. |
| `--canary <n>` | Integer **1–99** only: percent sent to **latest-ready**; the remainder goes to the pinned revision. `0` and `100` are rejected (omit the flag, or don't pin). Requires `--to`. |
| `-n`, `--namespace` | Namespace (default `default`). |
| `--context <ctx>` | kubectl context to target (default: your current-context; env fallback `KN_CONTEXT`). |

Because the bare form (`knext rollback <app>`) *clears* the pin, argument parsing is
deliberately strict: a dangling `--to`, an unknown flag, or an extra positional is a hard error —
never a silent un-pin when you asked to pin.

**Exit code:** `0` on success (including `--help`); `1` on a usage error (a dangling `--to`, an
unknown flag, an extra positional) or a failed patch.

## `knext db bind`

Binds an **existing** Postgres Secret to the app as `DATABASE_URL` (and optionally a read-only DSN
as `DATABASE_URL_RO`) by setting `spec.database.secretRef` on the `NextApp` CR — exactly one
cluster write. The operator wires the env injection. See
[Operator & the NextApp CRD → Databases](/docs/operator#databases-specdatabase).

```bash
knext db bind acme --secret acme-db
knext db bind acme --secret acme-db --ro-secret acme-db   # same Secret, both keys
knext db bind acme --secret acme-db --dry-run                   # print the patch, write nothing
```

| Flag | Notes |
|---|---|
| `--secret <name>` | **Required.** Secret carrying the `DATABASE_URL` DSN. |
| `--key <key>` | Key inside `--secret` (default `DATABASE_URL`). |
| `--ro-secret <name>` | Secret carrying a read-only DSN → `DATABASE_URL_RO`. |
| `--ro-key <key>` | Key inside `--ro-secret` (default `DATABASE_URL_RO`). |
| `-n`, `--namespace` | Namespace (default `default`). |
| `--context <ctx>` | kubectl context to target (default: your current-context; env fallback `KN_CONTEXT`). |
| `--dry-run` | Print the CR merge-patch YAML without applying it. |
| `--dsn <dsn>` / `--secret-file <path>` | Local-only inputs for the connection-contract check (never sent to the cluster). |

The command validates the binding against the live CR first (`spec.database` owns `DATABASE_URL`,
so a conflicting `envMap` entry is rejected), and after patching it **re-reads the CR**
— on a cluster whose operator predates the `spec.database` schema the field would be silently
pruned, so the CLI fails loudly and tells you to upgrade the operator bundle instead of logging a
false success.

**Exit code:** `0` on success (including `--dry-run`/`--help`); `1` on a usage error (an unknown
`db` subcommand, a missing app name, a missing `--secret`) or a failed patch/verification —
including the operator-too-old case above.

## `knext db migrate`

Applies pending [drizzle-kit-generated migrations](/docs/data-sdk#migrations) against the
**writer**, once, out of the request path.

```bash
knext db migrate                       # apply ./drizzle against DATABASE_URL
knext db migrate --dir ./migrations    # custom migrations directory
knext db migrate --url "$WRITER_DSN"   # explicit writer DSN override
```

| Flag | Notes |
|---|---|
| `--url <dsn>` | Writer DSN override (default: `DATABASE_URL`). |
| `--dir <path>` / `--migrations <path>` | Migrations directory (default `./drizzle`). |

- **Writer-only.** It refuses a read-replica DSN — running migrations on a replica is always a
  bug.
- **Idempotent, fail-loud.** Applied migrations are recorded, so a re-run is a no-op; a migration
  error exits non-zero so a CI step or Job fails instead of shipping a half-applied schema.
- Run it as a CI step or a one-shot Kubernetes Job — **not** on pod boot. The
  [Data SDK page](/docs/data-sdk#migrations) has the full Job recipe.

**Exit code:** `0` on success; `1` on a usage error (an unknown flag, an unexpected positional) or a
failed migration (fail-loud by design — see above).

## `knext gc`

Reaps old `_next/static/<build-id>/` asset prefixes from the object store under the skew-protection
retention rule: keep the newest `storage.assetRetention` build-ids (default 3) **plus** every
build-id currently **serving traffic** (resolved read-only from `NextApp.status.currentTraffic`).
The same logic runs automatically after every deploy; the standalone command exists for scheduled
or manual runs.

```bash
knext gc                          # prune using the config's app + retention
knext gc --build-id 20260711-1    # treat this build-id as the newest
knext gc --dry-run                # print the full reap/keep plan, delete nothing
```

| Flag | Notes |
|---|---|
| `--build-id <id>` | Build-id to treat as the newest (e.g. a tag just deployed). |
| `-n`, `--namespace` | Namespace of the `NextApp` (default `default`). |
| `--context <ctx>` | kubectl context to target (default: your current-context; env fallback `KN_CONTEXT`). |
| `--dry-run` | Compute and print the full reap/keep plan; issue **zero** deletes. Composes with `--build-id` and `-n`. |
| `-h`, `--help` | Show the usage help. |

With no `storage` block there is nothing to reap: `knext gc` says
`no object storage configured — nothing to reap` and exits 0.

**Fail-safe: over-keep, never over-delete.** If any live revision cannot be resolved to a
build-id, the GC skips entirely — the only possible failure mode is keeping assets too long.
Shared, content-hashed directories (`chunks/`, `css/`, `media/`) are never treated as build-id
prefixes, and the bare `<app>/` prefix is never a prune target. See
[Skew protection](/docs/skew-protection).

**Exit code:** `0` once a run completes — including the no-storage notice above and every
fail-safe skip (keeping assets too long is never treated as a failure); `1` on a usage error or a
missing `knext.config.ts`.

## `knext add function`

<Callout type="warn">
**Beta, and not published yet.** `knext add function` and `knext generate` are provided by the
optional `@getknext/grpc` package, which is not on npm yet. Until it is installed in your app, both
commands print how to install it and exit 1; `--help` still exits 0. Once installed, its version
must match your `@getknext/core`, and a mismatched pair is refused with both versions named.
</Callout>

Adds a zone function to your app: its **contract**, and the server project that implements it, in
Go or Rust. Your Next.js zone calls it over Connect, and it scales to zero like the zone itself.
Writes files only; nothing is deployed.

```bash
knext add function orders --lang go
```

It writes `proto/orders/v1/orders.proto` (one read and one write RPC to start from, each marked
`AUTH_USER`), the knext options contract that file imports, a `buf.yaml` if the app has none, the
function's entry in `knext.grpc.json`, and, if the app has none yet, an `authorize()` hook in
`src/knext/authorize.ts` that refuses every call until you write it (see
[generated queries, actions and streams](#generated-queries-actions-and-streams)). The name is a
lowercase DNS label; the zone reads the function's address from `ORDERS_SERVICE_URL` at call time.
It also scaffolds the function's server project at `functions/orders/`: the token-verifying server,
the health check and a Dockerfile, renamed to your function, with its code generated.

- `--lang go` copies the [Go function template](/docs/go-functions). It needs the Go toolchain on
  your `PATH`, and `--module <path>` sets the Go module path (default `example.com/orders`).
- `--lang rust` copies the [Rust function template](/docs/rust-functions), with the crate named
  after the function. It needs the Rust toolchain (`cargo`, via `rustup`) on your `PATH`, and a
  network connection the first time: the first run on a machine downloads the code generators'
  crates and compiles them, which takes a few minutes. Later runs reuse them from the knext cache
  directory, `$XDG_CACHE_HOME/knext/rust-codegen` (`~/.cache/knext/rust-codegen` when
  `XDG_CACHE_HOME` is unset). `XDG_CACHE_HOME` is ignored unless it is an absolute path.
  `KNEXT_RUST_CODEGEN_DIR` puts the cache somewhere else; it must be an absolute path, and a
  relative one is refused. The scaffolded code is formatted with `cargo fmt` before it is written.

If generating the code fails, nothing is written.

Two options at the top of every contract matter:

- `option (knext.v1.function) = "orders";` names the function that serves the file.
- `option (knext.v1.contract_version) = "1.0.0";` is the contract version. Raise it with every
  change to the file.

**Roll out the function first, then the zone.** A function must serve a contract version greater
than or equal to the one its zone was generated against: a newer function still answers every
call an older zone makes, but an older function may not know an RPC or a field a newer zone sends.
Every call carries the zone's contract version in a `knext-contract-version` header, so a function
can tell when it is older than its caller.

**Exit code:** `0` on success; `1` if the function already exists (nothing is changed) or on a
usage error.

## `knext deploy function`

<Callout type="warn">
**Beta, and not published yet.** Provided by the optional `@getknext/grpc` package, like
`knext add function`; without it the command prints how to install it and exits 1 (`--help` still
exits 0).
</Callout>

Applies a zone function's `BackendService` to the cluster. The function's image must already be
built and pushed; the command neither builds nor pushes it, and it never runs Knative's own `func`
or `kn` tools. The operator does the rest.

```bash
knext deploy function orders \
  --zone shop \
  --image registry.example.com/shop/orders@sha256:<digest>
```

- `--zone` names the `NextApp` that owns the function, in the same namespace.
- `--image` must be pinned by digest; a tag-only reference and `:latest` are refused.
- The function's language comes from `knext.grpc.json`, where `knext add function` recorded it.
- Optional: `--namespace`, `--context`, `--port`, `--proto-version`, `--no-wake-ahead`,
  `--min-scale`, `--max-scale`, `--container-concurrency`.
- `--dry-run` prints the resource and applies nothing, so it pipes into `kubectl apply -f -`.

It applies the way `knext deploy` applies a `NextApp`. First a server-side dry run checks the
resource under strict validation, before anything changes: if the cluster's `BackendService` CRD
does not know a field this CLI sends, the run stops and names the field. Upgrade the operator (and
its CRDs) first, then the CLI. Then the apply itself passes `--validate=strict`, so an unknown field
is rejected rather than silently dropped, whatever your `kubectl` defaults to.

The function runs only once the zone also lists it: add `{ name: "orders" }` to `backends` in the
zone's `knext.config.ts` and run `knext deploy`, which sends the list on the zone's `NextApp`. See
[Zone functions](/docs/zone-functions#binding-a-function-to-its-zone). After a successful apply the
command prints the exact entry to paste, with the digest of the spec it applied as the optional
`specDigest` pin, for example `{ name: 'orders', specDigest: 'sha256:...' }`. That digest covers the
function's image, `env`, `envFrom` and `volumes`: with the pin, the operator refuses the function if
any of them is ever changed without the zone changing the pin too. It also prints the weaker `image`
pin (the image digest alone, `{ name: 'orders', image: '@sha256:...' }`) for zones that want only that.
See [Pin the function's spec](/docs/zone-functions#pin-the-functions-spec). This command does not edit
the zone's `NextApp`.

**Exit code:** `0` on success; `1` on a usage error, a failed preflight, or a failed apply.

## `knext generate`

Writes the TypeScript a zone uses to call its functions, from the contracts in `proto/`:

```bash
knext generate                                        # lint, then write the generated code
knext generate --check                                # fail if the committed code is out of date
knext generate --check --against ".git#branch=main,subdir=proto"   # also fail on a breaking change
```

It runs `buf lint` first, and with `--against` it runs `buf breaking` against a baseline: a
directory, an image file, or a git reference. A removed or renumbered field is a breaking change
and fails the run. Run `knext generate --check` in CI so generated code can never drift from its
contract. The output goes to `src/generated/grpc` (set `out` in `knext.grpc.json` to move it), and
is the same bytes on every run; mark that directory as generated for your formatter. `out` must be
a subdirectory of your app: the app root itself, anything outside it, and anything under
`node_modules` are refused. knext records the files it wrote in `.knext-generated.json` in that
directory, and only ever removes files listed there that the contracts no longer produce, so other
files in the directory, including ones generated by other tools, are left alone. Generated code
is never written through a symlink: if a generated file is a symlink, or a directory on its path
(the output directory included) leads outside it, the run stops before writing anything and names
the path to replace.

`buf` comes with the package as a pinned binary whose checksum is verified before it runs; nothing
is downloaded at generate time.

Each generated client is server-only (`import "server-only"`) and follows one policy:

- **A deadline on every call**, shorter than the zone's request timeout. The defaults are a
  10-second deadline inside a 300-second request timeout; set `deadlineMs` and
  `gatewayTimeoutSeconds` in `knext.grpc.json` to match your app. A deadline that is not shorter
  than the request timeout is refused.
- **Only reads are retried.** An RPC marked `option idempotency_level = NO_SIDE_EFFECTS;` is a
  read, and is retried up to three times if the function is unavailable, within the one deadline.
  Every other RPC is a write and is never retried, since a retry across a cold start can apply a
  write twice. `IDEMPOTENT` still counts as a write.
- **Every write needs an idempotency key**, passed as `{ idempotencyKey }` and sent as the
  `idempotency-key` header, so your function can recognise a write it has already applied. Reuse
  the key when re-submitting the same write.
- **The endpoint is read at call time** from `<NAME>_SERVICE_URL` (never baked into the code). On a
  Node server, calls use HTTP/2 cleartext (h2c) by default. On a Bun server they use HTTP/1.1 by
  default, because Bun's HTTP/2 client is not yet verified with Connect; unary and
  server-streaming calls both work over HTTP/1.1. Setting `ORDERS_SERVICE_HTTP_VERSION` to `2` or
  `1.1` chooses for that one function on either runtime. The server logs the transport it chose
  once per function, for example
  `knext: orders function: transport HTTP/1.1, falling back from h2c on a Bun gateway (...)`.

**Exit code:** `0` on success; `1` on a lint failure, a breaking change, out-of-date generated code
(with `--check`), or a usage error.

### Generated queries, actions and streams

Next to each client, `knext generate` writes the code your pages call. Every RPC maps to one
shape:

| RPC | Generated as | Where you call it |
|---|---|---|
| Unary, `option idempotency_level = NO_SIDE_EFFECTS;` | A cached **query** in `<file>_knext_server.ts` | Server Components, route handlers, Server Actions |
| Any other unary RPC | A **Server Action** in `<file>_knext_actions.ts` (`'use server'`) | Forms and Client Components |
| Server-streaming | An **async generator** in `<file>_knext_server.ts`, never cached | Server Components and route handlers |

Both modules import `server-only`. A streaming RPC is never generated as a Server Action.

**Every RPC states who may call it**, with an option from the options contract:

```proto
rpc GetItem(GetItemRequest) returns (GetItemResponse) {
  option idempotency_level = NO_SIDE_EFFECTS;
  option (knext.v1.auth) = AUTH_USER;    // a signed-in user
}
```

- `AUTH_USER` — your `authorize()` hook must return a verified user before the call is made.
  `knext add function` writes it on every RPC it scaffolds.
- `AUTH_PUBLIC` — anyone, without a user. Allowed only on a `NO_SIDE_EFFECTS` read.

There is no public write. For an anonymous write (sign-up, a contact form), use `AUTH_USER` and
have `authorize()` return an anonymous principal, but only after your own check (CAPTCHA, rate
limit, CSRF) has passed.

**`authorize()`** is your code: set `"authorize"` in `knext.grpc.json` to the module that exports
it (`knext add function` writes `src/knext/authorize.ts`, which refuses every call until you
write it). It receives the function, service, method and kind of the call, and returns
`{ sub }` (your session's stable user id) or throws, for example a redirect to sign-in. Each
generated query, action and stream runs it first, outside any cache. The module must export it by
name, for example `export async function authorize(ctx) { ... }` or `export { check as authorize }`.
A default export or an `export *` re-export is not enough, and `knext generate` refuses the module.

**Queries need Cache Components.** A generated query is a `'use cache'` function, and Next.js runs
`'use cache'` only with Cache Components on, so set `cacheComponents: true` in your
`next.config.ts`. knext does not turn it on for you; without it, Next.js refuses to build a page
that imports a generated query. The knext build backs `'use cache'` with your app's Redis, so an
entry is shared by every replica: see
[`'use cache'` is shared across pods](/docs/isr-caching#use-cache-is-shared-across-pods).

**Cached reads are per user.** A query's `'use cache'` entry is keyed on the verified `sub`, the
contract version the function serves, and the request, so two users never share an entry. Entries
expire within an hour, and every write to the same service refreshes every user's cached reads of
it, on every replica. A write that fails after its request was sent (a reset connection, a
deadline, a lost response) refreshes them too, because it may have been applied. A write refused
before anything was sent (by `authorize()`, an invalid request, or missing configuration)
refreshes nothing.

The function's served contract version comes from `<NAME>_SERVICE_PROTO_VERSION`. The operator
renders it into the zone, beside `<NAME>_SERVICE_URL`, once the zone's binding to the function is
reconciled. Until then every call fails closed: it is refused before it leaves the zone, as it is
when the function serves an older contract than the zone was generated against.

**Requests carry only the contract's fields.** A Server Action is a public endpoint, so the
generated code rebuilds each request from the fields its message defines. Anything else in the
arguments, including protobuf's own `$typeName` and `$unknown` properties, is dropped before the
call, and a value of the wrong type is refused as `INVALID_ARGUMENT`.

**Calls carry an identity token.** Every generated call sends a token in its `authorization`
header, minted for that one call and never part of a cache key, and the function checks it before
your code runs. The token names the calling zone, the one function and the one RPC it is for, and
the user `authorize()` returned (empty for an `AUTH_PUBLIC` read). It expires 60 seconds after it
is minted. The user comes only from `authorize()`: no field of a request can set it, whatever it is
called.

The token is signed with your zone's own key. The operator creates the key, mounts it into the zone
(and no other workload) at `/var/run/knext/signing-key`, and sets `KNEXT_ZONE_ISSUER`, the zone's
identity, once the zone is bound to a function. The key is read from that mount, never from an
environment variable, and when the operator rotates it the zone signs with the new key from the
first call after the kubelet updates the mounted files, without a restart. The function is
identified from `<NAME>_SERVICE_URL`, which must be the cluster-local address the operator renders
(`http://<function>.<namespace>.svc.cluster.local`). A call is refused before it leaves the zone,
with `FAILED_PRECONDITION`, while the key or `KNEXT_ZONE_ISSUER` is missing, when the address is
anything else, or when the function is in another namespace than the zone.

The function checks the token against the zone's public keys, which the operator mounts into it at
`/var/run/knext/jwks/jwks.json`, and against `KNEXT_TOKEN_ISSUER` (the zone) and
`KNEXT_TOKEN_AUDIENCE` (the function), which the operator also sets. See
[Identity and the JWKS](/docs/zone-functions#identity-and-the-jwks) for the objects, the variables
and how to rotate the key.

A token works once. Each one carries a random id, and a function remembers the ids it has accepted
until the token expires and refuses a second use, so a copy taken from a log or the network is
refused by the function that served the original. The memory is per pod: the copy can still be
replayed once to another replica of the function, or after the pod restarts or scales to zero, for as
long as the token lives (about a minute). Treat anything that records the `authorization` header of
calls to your functions, such as request logs or traces, as sensitive.

Because a token is single-use, the generated client asks for a fresh one on every attempt: a read
that is retried after the function accepted its token (for example when the function then answered
`UNAVAILABLE`) sends a new token, never the same one again. In the client runtime, the `token` call
option takes either a string, sent as given, or a function that returns a token (a token source),
which is called once per attempt. A stream is never retried and takes a string only.

A function accepts only the keys the operator publishes for the zone, so a token signed with any
other key is refused by every function. To read the zone's own key from another directory, for
example in a local run, register a signer in `instrumentation.ts`. A signer you register in place of
the default (a custom minter) must return a fresh token on every call, because a function refuses a
token it has already accepted; a minter that caches and reuses one token has every call after the
first refused. The default signer does this; to point it at another key directory:

```ts
import { createZoneTokenSigner, registerTokenMinter } from "@getknext/grpc/runtime";

export function register() {
  registerTokenMinter(createZoneTokenSigner({ keyDir: "/etc/zone-key" }));
}
```

`knext generate` refuses, and writes nothing, when an RPC does not state its auth (or states
anything but `AUTH_USER` or `AUTH_PUBLIC`), when `AUTH_PUBLIC` is on an RPC that is not
`NO_SIDE_EFFECTS`, for client-streaming and bidirectional-streaming RPCs, when two RPCs in one file
would export the same name, and when `authorize` is not set, names a file that does not exist, or
names a module that does not export `authorize` by name.
Each refusal names the RPC and the fix. An options contract copied before the auth option existed
is refused with the path of the current one to copy.

## `knext ffi`

<Callout type="warn">
**Beta, and not published yet.** `knext ffi` is provided by the optional `@getknext/ffi` package,
which is not on npm yet. Until it is installed in your app, every `knext ffi` command prints how to
install it and exits 1; `--help` still exits 0. Once installed, its version must match your
`@getknext/core`, and a mismatched pair is refused with both versions named. In-process Rust runs
only on Bun; see [In-process Rust](/docs/rust-in-process) for the whole feature.
</Callout>

Call Rust functions from a Server Action or route handler **in the zone's own process**, through
Bun's `bun:ffi`, with a typed, server-only wrapper generated from the Rust library. Every run
except `--help` first prints one line on standard error:

```
knext ffi: in-process Rust is Beta — it calls Rust through bun:ffi, which Bun marks experimental, and runs only on Bun.
```

```bash
knext ffi init       # write knext.ffi.json and a starter rust/ crate
knext ffi generate   # build the crate for this machine and write the typed wrapper
knext ffi check      # the same, but fail if the committed wrapper is out of date (CI)
knext ffi build --target x86_64-unknown-linux-musl --native-dir native   # run by knext build
```

**`knext ffi init`** writes `knext.ffi.json` (the Rust crate's directory, `crate`, defaults to
`rust`; the generated module's directory, `out`, to `src/generated/ffi`) and a `rust/` crate:
`Cargo.toml` (a `cdylib` that depends on the
`knext-ffi` crate by git, pinned to the full commit the installed `@getknext/ffi` records),
`rust-toolchain.toml`, `src/lib.rs` with a `greet` function, and `deny.toml`, the dependency
policy `knext ffi build` checks with `cargo deny`. It refuses to overwrite: if
`knext.ffi.json` or `rust/` exists, nothing is written. It also writes nothing if the installed
`@getknext/ffi` records no `knext-ffi` commit.

**`knext ffi generate`** reads `knext.ffi.json`, builds the crate for this machine
(`cargo build --release`), reads the exported functions from the built library, and writes
`index.ts` and `.knext-generated.json` to `out`. Commit both. It needs Rust
([rustup.rs](https://rustup.rs)). It refuses a Rust name that cannot be a TypeScript name, naming
it (see [Reserved names](/docs/rust-in-process#reserved-names)). Like `knext generate`, it removes
only files it recorded in `.knext-generated.json` and never writes through a symlink.

**`knext ffi check`** does the same build and compares instead of writing. Run it in CI.

**`knext ffi build`** is run for you by `knext build`, `knext deploy` and `knext preview` when
`knext.ffi.json` exists; you do not usually run it by hand. It runs `cargo deny check` on the
crate's dependencies (with `rust/advisory-allowlist.json` for accepted advisories), cross-compiles
the crate for the image with `cargo auditable zigbuild` (musl, release, `--locked`), refuses a
library that links anything the Alpine image lacks (a glibc `libc.so.6`, say), stages it as
`<native-dir>/ffi/<target>/lib<name>.so` with a `provenance.json` and a CycloneDX `sbom.cdx.json`,
and fails if the committed wrapper is not what `knext ffi generate` renders from that library. It
needs Rust, a committed `Cargo.lock`, and these exact tool versions: cargo-zigbuild 0.23.4,
cargo-deny 0.20.2, cargo-auditable 0.7.7 and cargo-cyclonedx 0.5.9 (each installed with
`cargo install --locked --version <version> <crate>`), and zig 0.17.0, which knext downloads and
verifies when no zig is on `PATH`. See [Building images](/docs/rust-in-process#building-images) and
[Supply chain](/docs/rust-in-process#supply-chain).

| Flag | Notes |
|---|---|
| `--target <triple>` | `build` only, required, repeatable: `x86_64-unknown-linux-musl` or `aarch64-unknown-linux-musl`. |
| `--native-dir <dir>` | `build` only, required: the app's `native/` directory. Only its `ffi/` subdirectory is replaced. |
| `-h`, `--help` | Show the help for `knext ffi` or for one command. |

`init`, `generate` and `check` take no other flags; an unknown flag is a usage error.

**Exit code:** `0` on success, when `check` finds the wrapper up to date, and for `--help`; `1` on
a usage error (an unknown command or flag, a missing or invalid `knext.ffi.json`), when `init` finds
`knext.ffi.json` or `rust/` already there, when `check` finds the wrapper out of date, on a missing
tool or one at another version than its pin, when a supply-chain check refuses a dependency, on a
failed Rust build, when `build` refuses the library or finds the wrapper out of date, and
when the package is missing or does not match this `@getknext/core`.

## Directly runnable entries

Some entries ship in the package as directly runnable scripts rather than bin subcommands:

- **preview** (`dist/cli/preview.js`) — **(experimental)** deploy/destroy per-PR ephemeral
  [preview environments](/docs/previews) (`preview deploy --pr <n> --branch <ref>` /
  `preview destroy --pr <n>`). Flags and output may change in a minor release.
- **loadtest** (`dist/cli/loadtest.js`) — **(experimental)** generate and apply an ephemeral
  k6 load-test Job against a deployed service. An operability tool, not part of the deploy
  path. Accepts `--url`, `--type`, `-n`/`--namespace`, and `--context <ctx>` (kubectl context
  to target; default: your current-context; env fallback `KN_CONTEXT`). The k6 Job is applied
  to `<ctx>`, never to whichever cluster your kubeconfig happens to point at. Flags and output
  may change in a minor release.

```bash
node node_modules/@getknext/core/dist/cli/preview.js deploy --pr 42 --branch my-branch
node node_modules/@getknext/core/dist/cli/loadtest.js --type smoke
node node_modules/@getknext/core/dist/cli/loadtest.js --type smoke --context staging
```

**Exit codes:** both exit `0` on success and `1` on a usage error (a missing `--pr`/`--branch`, an
unrecognized `preview` subcommand, a missing `--url` or an invalid `--type` for `loadtest`) or a
failed run. Neither accepts `-h`/`--help` today — a bare invocation with no recognizable subcommand
(`preview`) or a missing required flag (`loadtest`) is how you reach the usage message. `loadtest`
does not reject an unrecognized flag (it parses permissively); `preview` does.

`build` and `cleanup` also still ship as `dist/cli/build.js` / `dist/cli/cleanup.js`, but prefer
the `knext build` / `knext cleanup` subcommands above.
