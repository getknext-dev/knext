<Callout type="warn">
**Beta.** The function serves a call only when it carries a valid identity token from its own
zone. Until the zone's public keys are mounted into the function and its issuer and audience are
set, it refuses every call except its health check: it fails closed rather than serve calls it
cannot authenticate.
</Callout>

A zone function is a Go or Rust service that a Next.js zone calls like a local function,
scaling to zero like the zone itself. The contract between the two is a `.proto` file, and both
sides are generated from it. This page covers the Rust side: the template your function's server
starts from. The [Go template](/docs/go-functions) is the same function in Go.

## What the template gives you

- **A connect-rust server** for your contract, answering the Connect, gRPC and gRPC-Web protocols
  on one port, over HTTP/2 cleartext (h2c) — what the zone uses — or HTTP/1.1.
- **A token check on every call** (see [Security](#security)).
- **The standard gRPC health check**, `grpc.health.v1.Health/Check`, served without a token so
  probes and the zone's wake-up call work.
- **OpenTelemetry**: a span per call, with the caller's W3C trace context linked, refused calls
  included. A handler reads the span's context from the request extensions
  (`ctx.extensions().get::<opentelemetry::Context>()`) to continue the trace on its own calls.
- **Panic recovery**: a panicking handler returns `internal` and the process keeps running.
- **Request limits**: 4 MiB per request message, as sent and once decompressed, so a small
  gzip body cannot inflate into gigabytes. A request body longer than 4 MiB and 64 KiB is cut off
  rather than read to the end, on streaming calls too, and a request body that stops arriving is
  cut off after 30 seconds. That limit is on sending the request, not on the call: a handler may
  take longer.
- **Connection limits**: a connection that does not start a request within 10 seconds is
  closed, and an idle connection, with no call in flight, is closed within 2 minutes.
- **Graceful shutdown**: on `SIGTERM` the function stops accepting connections and in-flight
  calls get up to 25 seconds to finish.
- **A distroless image**: a static binary, no shell, running as a non-root user.

## Start a Rust function

1. In your zone, add the function's contract:

   ```bash
   knext add function orders --lang rust
   ```

   This writes the contract (`proto/orders/v1/orders.proto` and the options contract it imports)
   and the server project at `functions/orders/`: the template below, with its example service
   renamed to `OrdersService`, the crate named `orders`, and the Rust code already generated. It
   needs the Rust toolchain on your `PATH` and, on the first run on a machine, a network
   connection and a few minutes to download and compile the code generators (they are cached in
   `$XDG_CACHE_HOME/knext/rust-codegen`, or `KNEXT_RUST_CODEGEN_DIR` when you set it to an
   absolute path). If generation fails, nothing is written. See
   [`knext add function`](/docs/cli#knext-add-function).

2. Write your handlers where `functions/orders/src/items.rs` is. The service is already
   registered in `src/rpc/mod.rs`.

3. After a change to the contract, copy the changed `proto/orders/v1/orders.proto` over
   `functions/orders/proto/orders/v1/orders.proto`, then regenerate (this needs `buf` on your
   `PATH`):

   ```bash
   cd functions/orders
   ./codegen.sh      # writes gen/ — commit it
   ```

4. Test and build:

   ```bash
   cargo test
   docker build -t <registry>/orders-fn:<tag> .
   ```

The template itself lives in the knext repository at `templates/rust`. The scaffold leaves out its
repository-only files: its maintainer README, its conformance and kind test harnesses, and the
tests that read knext's shared token vectors.

The template's own example service has one read (`GetItem`) and one write (`PutItem`), the shape
`knext add function` starts every contract with.

## Security

The function is **cluster-local**: it has no public route, and only workloads inside the
cluster can reach it. Inside the cluster, the **token is the control**, not the network: a
NetworkPolicy is defense in depth, and some CNIs (flannel, which OKE and OrbStack use) do not
enforce NetworkPolicy at all.

Every call except the health check must carry `Authorization: Bearer <token>`: an identity
token the zone signs for that one call. The check runs before the request body is read. The token
is a JWT signed with Ed25519 (`alg` `EdDSA`), and the function checks:

- **the signature**, against the zone's public keys, a JWK Set mounted as a volume at
  `/var/run/knext/jwks/jwks.json`. A token signed by any other key, another zone's included, is
  refused. A key in the set that is not a valid Ed25519 public key (a non-canonical encoding, a
  point off the curve, or a small-order point, which would accept forged signatures) is ignored.
- **`iss` and `aud`**: the token must name the function's own zone and the function itself, as
  given by the function's `KNEXT_TOKEN_ISSUER` (`knext:zone:<namespace>/<zone>`) and
  `KNEXT_TOKEN_AUDIENCE` (`knext:fn:<namespace>/<function>`) environment variables.
- **`method`**: the RPC being called, so a token for one RPC cannot call another.
- **`iat` and `exp`**: at most 60 seconds apart, with 5 seconds of allowance for clock skew.
- **`sub`** on an RPC whose `(knext.v1.auth)` option is `AUTH_USER`: the zone must name a
  user. An `AUTH_PUBLIC` read still needs the zone's token, but no user.

connect-rust does not carry method options at run time, so the template lists each RPC's
`(knext.v1.auth)` option in `src/auth/policy.rs`. When you add an RPC, add its line there: a
test compares the table with your `.proto` files and fails on a missing or different entry, and
an RPC that is not in the table is refused.

It fails closed:

| Situation | Result |
|---|---|
| No `Authorization` header, or not a `Bearer` token | refused, `unauthenticated` |
| No public keys mounted for the zone | refused, `unauthenticated` |
| The mounted key set holds private key material (`d`, `k` or an RSA private member) | refused, `unauthenticated` |
| `KNEXT_TOKEN_ISSUER` or `KNEXT_TOKEN_AUDIENCE` not set | refused, `unauthenticated` |
| A token that fails any check above | refused, `unauthenticated` |
| An RPC that states no `(knext.v1.auth)` option | refused, `unauthenticated` |
| A token that passes every check | served |
| Health check (`grpc.health.v1.Health/Check`) | served, no token needed |

There is no setting that turns the check off. At start-up the function logs a warning when no
keys are mounted or the issuer or audience is not set.

A refused call returns HTTP 401 on the Connect protocol and `grpc-status` 16 on gRPC and gRPC-Web.

### The user a handler acts for

Take the user from the verified token, never from the request. `auth::Caller::of(&ctx)` returns the
verified caller: `subject`, the user the zone vouched for, and `zone`, the zone that signed the
token. A user id in a request body or header is never trusted.

### Key rotation

The function re-reads the mounted keys when the file changes, and at least every 10 seconds, so a
running function picks up a new key without a restart. During a rotation the key set holds both
the old and the new key, and tokens signed by either verify; once the old key is removed from the
set, its tokens are refused. A token signed by a key the function has not received yet is refused
too, which is why a rotation publishes the new key, waits for it to reach every function, and only
then signs with it.

A token can be used once. Each one the zone signs carries a random id, and the function remembers
the ids it has accepted until the token expires and refuses a second use, so a copy of a token taken
off the network is refused by the function that already served the original. Two limits remain:

- The memory is per pod. A copy can still be replayed once to a different replica of the same
  function, or after the pod restarts or scales to zero, for as long as the token lives (about a
  minute). Make writes idempotent; the zone sends an `idempotency-key` header with each one for that
  reason.
- The token does not cover the request body. A copy that reaches the function before the original is
  served with whatever body its sender chose.

The memory is bounded: it holds 65,536 tokens by default, which is about 1,000 verified calls a second
on one pod, and about 10 MiB when full. A pod that is busier than that refuses new tokens, and logs a
warning, rather than forgetting one it has seen. `seen_capacity` in the scaffolded `main` raises the
limit.

When a pod is over that ceiling it refuses the new token with `ResourceExhausted` (HTTP 429 on Connect),
not `unauthenticated`: the caller did nothing wrong and may retry, and a replay of a token already seen
is still `unauthenticated`. Those refusals are answered at once, so they do not add the in-flight
concurrency Knative scales on: the autoscaler gets no signal from them and does not add pods by itself.
If one function must serve more than about 1,000 verified calls a second per pod, raise the capacity or
split the load across functions.

A token with no id is refused, so upgrade the zone before its functions (the reverse of the usual order).

## Generated code and the contract

The `.proto` file is the source of truth. `gen/` holds the Rust message types and service stubs,
written by `buf generate` with the connect-rust and buffa protoc plugins. `codegen.sh` installs
those plugins at pinned versions with `cargo install --locked` into the template's `.codegen/`
directory and runs `buf generate`, so every machine generates with the same plugins. Run it after
every contract change and commit `gen/`; a CI step that regenerates and fails on a diff keeps the
two in step.

Roll out the function **before** the zone that calls a new version of its contract: a function
must serve a contract version greater than or equal to the zone's.

## connect-rust is pre-1.0

The template uses connect-rust, which has not reached 1.0. Its version is pinned to the 0.9 line
in `Cargo.toml` and exactly in `Cargo.lock`, and knext's CI runs the Connect conformance suite —
every server test, on the Connect, gRPC and gRPC-Web protocols — against the locked version. When
you upgrade connect-rust in your function, upgrade the codegen plugin in `codegen.sh` with it and
regenerate.

## Supply chain

knext's CI builds the template image, writes an SBOM (SPDX) and runs Trivy, failing on any
fixable HIGH or CRITICAL finding. The binary is built with `cargo auditable`, which embeds its
dependency list, so the SBOM and the scan see every crate compiled into it. `cargo deny`
(advisories, licenses, sources) and `cargo audit` run over `Cargo.lock`. knext does not publish a
prebuilt template image yet: build it from the template.

That covers the template. An image you build from it is your own: run your scanner on it in your
pipeline. The Rust release in `rust-toolchain.toml` and the `rust` builder image in the
`Dockerfile` move together.

## Limits

- **Beta.** Zone functions are not covered by knext's compatibility credential.
- A zone identity token is single-use on the pod that accepted it, but can be replayed once to another replica or after a restart (see [Key rotation](#key-rotation)).
- A compressed request must use gzip.
- The template's example store is in memory: per pod, and lost when the function scales to zero.
  Keep real data in your zone's own database, through the `DATABASE_URL` the zone binds; a
  function never reads another zone's database.
