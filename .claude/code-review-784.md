## Findings

1. **`tests/precompile-closure-gate-ci.test.ts:27,120,130-131` — the "any future publish lane is covered" claim is stronger than the scanner. Why it matters: this is the one criterion that is supposed to hold for jobs that do not exist yet, and it is the claim repeated in `ci.yml:1085-1093`, the PR body, and `docs/security/threat-model.md`.**
   The scan reads **only `.github/workflows/ci.yml`** (`CI_YML` at :27, `workflow()` at :32-39) and matches step text against `/build\.sh|test:image|docker build/`. Two ways a real vinext build lane escapes it silently:
   - a lane in **any other workflow file** (`release.yml`, `supply-chain.yml`, a new `publish-vinext.yml`) — completely invisible to the scan;
   - a lane in ci.yml that compiles via **`bun run build`** (the `examples/bun-exec/package.json:8` alias for `./build.sh`) or a reusable-workflow `uses:` — the step text contains neither `build.sh` nor `test:image` nor `docker build`.
   Today the claim happens to hold: I confirmed only `ci.yml` mentions `bun-exec`, and of its two example jobs `bun-exec-hardcap` runs `bun run test`, whose `vitest.config.ts` excludes `*.docker-e2e.test.ts` and therefore compiles nothing. So this is an over-claim, not a live hole. Fix: glob `.github/workflows/*.yml` and add `bun run build`/`npm run build`-in-`examples/bun-exec` to the regex — or soften the three comments to "in ci.yml, for jobs that name the build script".

2. **`scripts/lib/precompile-closure.mjs:23,46` · `scripts/precompile-closure-audit.mjs:19-20` · `.github/workflows/ci.yml:1076` · `docs/security/threat-model.md` — the "408 packages in the installed tree" / "~500 packages on disk" figures are not what the gate's own walker measures.** Measured in this worktree: `installedPackages('examples/bun-exec/node_modules')` → **210**; syft → **409** npm components (it catalogues nested non-root `package.json` files — `find … -name package.json` returns 527). So the headline "60 packages vs 408 in the installed tree" compares trivy's package count against **syft's component count**, not against the tree. The conclusion is unaffected (trivy's 60 still missed the nanoid HIGH, and coverage is genuinely 100%/0 uncovered — I reproduced `{ok:true, npm:409, installed:210, coverage:100, missingAnchors:[]}`), but `MIN_INSTALLED_PACKAGES = 100` has ~2× headroom, not the ~5× the comment claims. In a repo whose standing rule is "re-read your own claims against the current tree", a measured number that is 2× off in the file justifying a floor is worth correcting.

3. **`scripts/lib/precompile-closure.mjs:202-223` — `readAllowlist` throws on malformed *known* keys but silently ignores *unknown* ones.** An entry `{id, justification, added, "expiress": "2020-01-01"}` is accepted and **never expires**, while reading as though it does. `security/precompile-closure-allowlist.json:2` promises "a malformed entry makes the gate THROW", and the whole point of the expiry is that it forces re-justification. A key-allowlist reject (`Object.keys(entry)` ⊄ `{id,justification,added,expires,note}` → throw) closes the last silent-weakening path in this file. Low severity, cheap fix.

4. **`security/precompile-closure-allowlist.json:6,12` — the justification's premise ("transitive build-time dependency") is factually wrong, though its conclusion survives.** `examples/bun-exec/bun.lock:632` shows `image-size` is a **direct, exactly-pinned (`"image-size": "2.0.2"`) dependency of `vinext`**, and it is imported **server-side** at `node_modules/vinext/dist/server/metadata-route-build-data.js:5,31` — i.e. it is inlined into the compiled binary, not confined to build time. The acceptance still stands, and for a better reason than the one written down: the buffer it parses comes from `fs.readFileSync(route.filePath)` on repo-owned metadata images (`icon`/`opengraph-image`), never from a request. Also, entry 1's description ("zero-valued size fields") does not match GHSA-5p2g-fcmc-qvqq's actual subject ("JXL and HEIF parsers … infinite loops"). Rewrite both justifications to the real reachability argument, since that is what a reader at the 2026-11-19 expiry will be re-judging.
