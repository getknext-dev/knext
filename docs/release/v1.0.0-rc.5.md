# knext v1.0.0-rc.5

**This is a release-candidate, not the final v1.0.** rc.5 is a cold-start release: four
independent fixes that each shrink part of a scale-from-zero wake, plus one upgrade note you
should read before updating a running cluster.

## Faster cold starts

Each of these was measured on its own, one change at a time, under pre-pulled images (no image
pull on the wake being timed). **They do not simply add up** — several shrink the same CPU-bound
window, so the combined effect on your own app and cluster will be smaller than the sum below.
Measure your own app before and after upgrading if cold-start latency matters to you.

- **The tracing-client import is now skipped when tracing is off.** Every scaffolded app's
  `instrumentation.ts` used to pull in its full tracing client library unconditionally, before the
  server could answer its first request — even with tracing turned off, where none of that code
  does anything. Measured on GKE `e2-standard-4` nodes, a 1-CPU limit, pre-pulled images: **about
  0.9 s faster on Bun, about 0.8 s faster on Node**, per cold wake. Tracing is off by default in a
  scaffolded app, so this applies out of the box; it does not help an app that has tracing on.

- **A stale network-neighbour entry on some clusters no longer stalls the first request.** On at
  least one cluster using the flannel CNI network plugin, a wake could stall for several seconds
  after the app was already listening — traffic from outside the node couldn't reach the pod until
  the pod sent its own first outbound packet. The runtime now sends one best-effort outbound packet
  at process start to correct this immediately. On the affected node this measured a median wake
  time dropping from about **10.2 seconds to about 2.4 seconds**; on a healthy node in the same
  cluster it made no measurable difference. It is on by default and a no-op where the pattern
  doesn't occur; opt out with `KNEXT_ARP_PRIMER=0`.

- **Two SDK clients now load on first use instead of at import time.** The Cerbos and MinIO
  clients in `@getknext/lib`'s shared client module were previously loaded eagerly whenever that
  module was imported, whether or not either client was ever used. They now load lazily, on first
  call. Measured on GKE `e2-standard-4` nodes with tracing on (10 wakes per arm, pre-pulled images),
  this cut roughly **0.5 s** per cold wake on both Bun and Node: the cost that an app with
  tracing on (or one that imports the client module directly) paid at startup; an app that never
  calls either client no longer pays to load either SDK.

- **No default scratch disk volume.** A standalone app with no object storage configured no
  longer gets an unconditional scratch (`emptyDir`) volume under the read-only root filesystem —
  provisioning it cost pod-sandbox setup time on every wake whether or not anything was ever
  written to it. Measured on GKE `e2-standard-4` nodes (11 wakes per arm, pre-pulled images) at
  roughly **0.36 s** faster per wake. `readOnlyRootFilesystem` stays on
  by default.

## Upgrade note (important): read before upgrading a running cluster

Standalone apps no longer get a writable `/tmp` or `.next/cache` directory by default.

**If your app code writes to `os.tmpdir()`, or anywhere else at runtime that isn't your database
or object storage, set `spec.security.writableCache: true` on your `NextApp` before upgrading.**
Without it, a write to that path will fail against a read-only filesystem after you upgrade.

Two shapes keep their previous writable-path behavior automatically, with nothing to change:

- Apps with `spec.storage` configured keep a writable `.next/cache` (Next's image-optimization
  cache directory).
- Single-executable (`build: vinext` / `selfContained: true`) builds keep a writable `/tmp`.

The default CPU **limit** is unchanged (1 CPU limit, 250m request) — raising it was evaluated for
this release and **not** shipped, because a higher limit against the unchanged default request is
a ratio some clusters' resource governance rejects at pod admission. A higher limit remains
available as a per-app opt-in; see
[Tuning cold start](https://knext.dev/docs/tuning-cold-start) for the recipe.

## Operator first, then CLI

The upgrade order is unchanged, and matters more than usual this release: **upgrade the knext
operator (and its CustomResourceDefinition) first, then the CLI.** This release adds one new,
additive, optional CRD field (`spec.security.writableCache`). The CLI doesn't set it; you set it
on your `NextApp` yourself (with `kubectl` or your GitOps tooling), and the operator's
CustomResourceDefinition must include it before you apply a `NextApp` that uses it. Applying a
resource with a field your installed CRD doesn't know fails with an error like:

```
strict decoding error: unknown field "spec.security.writableCache"
```

If you see that error, upgrade the operator first, then retry:

```sh
kubectl apply -f https://github.com/getknext-dev/knext/releases/download/operator-latest/install.yaml
```

An operator that is *ahead* of your CLI version is always safe.

## Credential: the window restarts on rc.5

v1.0 needs 14 consecutive green nightly runs of the official Next.js compatibility suite, against
Next.js `16.3.6`, for each supported runtime x builder combination:

- Node runtime x Turbopack builder
- Node runtime x Webpack builder
- Bun runtime x Turbopack builder
- Bun runtime x Webpack builder

The credential is measured against one specific release tag, so once the windows move to rc.5 the
count restarts from zero for all four combinations — including nights already accumulated on
rc.4. Treat rc.5 as not yet credentialed until those runs accumulate.

## What's in this release

`@getknext/core`, `@getknext/lib`, `@getknext/db`, and the `kn-next` bin all move to `1.0.0-rc.5`
together — they are published as a set and always carry the same version number. Each package's
changelog gains an rc.5 entry.

## Known limits in this release candidate

- **v16.3.6 is not yet a completed compatibility credential** — see above.
- **The compiled single-executable Bun build target is experimental** and outside this window's
  verification scope.
- This is a **release candidate**: expect the version number to change again before the final v1.0
  tag, and do not treat rc.5 as a long-term-support release.
