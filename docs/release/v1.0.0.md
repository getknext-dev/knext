# knext v1.0.0

knext v1.0.0 is the first **stable** release: from this version on, the public API, the
`knext.config.ts` schema and the core CLI follow semver — a patch or minor release does not break
them, and a breaking change requires a new major version. The stability tiers below say exactly
which features that promise covers.

**The official Next.js compatibility credential is in progress, not complete.** v1.0.0 ships before
the 14-night credential finishes; it does not claim verified-adapter status. See
[The compatibility credential](#the-compatibility-credential-in-progress) below for what that means
and where to follow it.

## What's new since 0.4.x

v1.0.0 is built on the **official Next.js Deployment Adapter API**, on two build systems
(Turbopack, Webpack) and two runtimes (Node, Bun). The highlights below were delivered across the
`1.0.0-rc.1` through `1.0.0-rc.6` release candidates; each release candidate's notes have the full
detail.

- **Security: new apps scaffold with Next.js `16.3.8`.** Next.js `16.0.0` through `16.3.7` have a
  high-severity server-side request forgery in Image Optimization
  ([GHSA-cjq9-62q9-8jv4](https://github.com/advisories/GHSA-cjq9-62q9-8jv4)), and `16.2.0` through
  `16.3.5` also have a critical remote-code-execution vulnerability in `next/og`'s `ImageResponse`
  ([GHSA-vcvr-r3jv-pc5j](https://github.com/advisories/GHSA-vcvr-r3jv-pc5j)). Both are fixed in
  `16.3.8`. If you scaffolded an app from a release candidate, upgrade it:

  ```sh
  npm install next@16.3.8
  ```

  (or a later `16.3.x`). Your app's own `next` dependency is yours to bump; upgrading the knext
  packages does not change it.
- **Cache key upgrade note.** Next.js `16.3.7` and later scope every cached entry to its source
  route, so cache keys now start with `/route-cache/`. The knext cache handler treats every key as
  an opaque string and needs no change. After upgrading an existing app, Redis entries written
  under the old key shape are never read again and stay until their TTL expires; the affected
  pages regenerate on first request.
- **Fix: intermittent 500 on `dynamicParams = false` routes.** On Next.js before `16.4.0`, a route
  with `dynamicParams = false` could answer a burst of concurrent prefetches for a parameter outside
  `generateStaticParams` with a 500 instead of a 404 whenever an adapter was configured. `knext
  build`, `deploy` and `preview` now clear `adapterPath` from the standalone server's runtime
  configuration when the installed Next.js is older than `16.4.0` (the adapter only works during
  `next build`, so nothing at runtime depends on it). Those requests become plain 404s, each logging
  `Error: Internal: NoFallbackError`. On Next.js `16.4.0` or later the workaround removes itself.
- **Config file renamed to `knext.config.ts`** (was `kn-next.config.ts`). No dual-read — see
  "Breaking changes" below.
- **Request body cap on every build target.** Request bodies are capped in-process on the
  standalone build (Turbopack or Webpack, Node or Bun) as well as the compiled single-executable
  build. Default cap: 8 MiB per request, configurable via `KNEXT_MAX_REQUEST_BYTES`.
- **`knext` is the canonical CLI name.** The older `kn-next` name keeps working as a deprecated
  alias.
- **GitLab CI support** in `knext init-ci --provider gitlab`, alongside the existing GitHub
  Actions generator.
- **Experimental surfaces marked explicitly.** The `selfContained` config key / `knext build
  --self-contained` flag, and the directly-runnable `preview`/`loadtest` CLI entries, are called
  out as experimental and excluded from the v1.0 semver commitment — see the public API reference
  on the docs site.
- Build-reliability and compile-cache fixes for apps whose home route (or another route on the
  warm boot path) redirects or is rewritten by middleware.
- **Fix: on-demand cache invalidation (`revalidateTag`/`revalidatePath`) now evicts statically
  rendered and ISR-cached pages**, not only fetch-cache entries, from the Redis cache handler.
- **Cold-start reductions** on standalone builds, each measured on its own (the effects do not
  simply add up): the tracing-client import is skipped when tracing is off; a stale
  network-neighbour entry on affected network plugins no longer stalls the first request after a
  wake; two `@getknext/lib` SDK clients (Cerbos, MinIO) load lazily instead of at import time; apps
  with no object storage configured no longer get an unconditional scratch volume.
- **New, additive, optional CRD field: `spec.security.writableCache`.** Read the upgrade note
  below before upgrading a running cluster — standalone apps no longer get a writable `/tmp` or
  `.next/cache` by default.

The package changelogs (`@getknext/core`, `@getknext/lib`, `@getknext/db`, `kn-next`) carry the
complete, versioned list.

## Same bytes as 1.0.0-rc.6

`@getknext/core`, `@getknext/lib`, `@getknext/db` and the `kn-next` bin move to `1.0.0` together.
The `1.0.0` tarballs differ from the published `1.0.0-rc.6` tarballs **only in version fields** —
the package `version` and the matching `@getknext/*` sibling ranges. That was checked file by file
against the published rc.6 tarballs before this release, and the same check runs again in the
release pipeline before anything is published. Everything else is rc.6's code, unchanged.

## Installing

`1.0.0` is published to the `latest` dist-tag:

```sh
npm install -D @getknext/core@latest
```

A later minor release (1.1 and up) will take over `latest`. To stay on the 1.0 line after that,
install a semver range — `npm install -D @getknext/core@1.0` resolves to the newest `1.0.x` — or use
the `latest-1.0` dist-tag, which points at the newest `1.0.x` release.

## Upgrade order: operator/CRD first, then CLI

**Always upgrade the knext operator (and its CustomResourceDefinition) in your cluster before
upgrading to this `@getknext/core` release.** A newer CLI version can describe an application
using a field an older operator's CRD does not know about yet. `knext` applies its resources with
strict validation, so upgrading the CLI first can surface an error like:

```
strict decoding error: unknown field "spec.…"
```

If you see that error, upgrade the operator first, then retry:

```sh
kubectl apply -f https://github.com/getknext-dev/knext/releases/download/operator-latest/install.yaml
```

An operator that is *ahead* of your CLI version is always safe — the only ordering constraint is
that the CLI must never be newer than the installed operator. There is no CRD change between
`1.0.0-rc.6` and `1.0.0`.

## Breaking changes

### Config file renamed to `knext.config.ts`

The config file has a new name: `knext.config.ts` (was `kn-next.config.ts`). **There is no
dual-read** — the CLI reads `knext.config.ts` only, and does not fall back to the old filename.

If your app still has the pre-rename config file, rename it before running any `knext` command:

```sh
mv kn-next.config.ts knext.config.ts
```

Running any `knext` command in a directory that still has the old filename (and no
`knext.config.ts`) fails fast with one actionable error naming this exact rename — never a silent
fallback read. `knext create` scaffolds `knext.config.ts` for new apps.

### Request body cap now applies to the standalone build too

If your app accepts uploads larger than 8 MiB through a route handler on the default (standalone)
build target, raise the cap before upgrading — set `KNEXT_MAX_REQUEST_BYTES` (in bytes) in the
`env` map of `knext.config.ts`, or in `spec.env` on the `NextApp` custom resource. Setting it to
`0` removes the cap entirely. See the request-hardening guide on the docs site for the full detail.

### Builder and runtime defaults

`knext create`'s default build target is the **standalone** shape (`output: 'standalone'`, the
official Next.js Deployment Adapter wired via `adapterPath`), built with **Turbopack**. The
compiled single-executable ("vinext") target is opt-in via `--builder vinext`. Within the
standalone target, the default `runtime` is **`bun`**; `runtime: "node"` runs the same standalone
server under Node's own V8 compile cache instead. All four `node`/`bun` x `turbopack`/`webpack`
combinations are in the compatibility credential (see below); confirm which combination your app
is on before upgrading if you rely on non-default settings.

### Standalone apps no longer get a writable `/tmp` or `.next/cache` by default

**Read this before upgrading a running cluster.** If your app code writes to `os.tmpdir()`, or
anywhere else at runtime that isn't your database or object storage, set
`spec.security.writableCache: true` on your `NextApp` before upgrading, or the write will fail
against a read-only filesystem. Two shapes keep their previous writable-path behavior with nothing
to change: apps with `spec.storage` configured keep a writable `.next/cache`, and single-executable
(`build: vinext` / `selfContained: true`) builds keep a writable `/tmp`. This field is additive and
optional on the CRD — see the upgrade-order section above; an operator older than this field does
not know it and will reject a `NextApp` that sets it with a strict-decoding error.

## The compatibility credential (in progress)

knext's compatibility credential is **14 consecutive green nightly runs** of the official Next.js
compatibility suite, for each of the four runtime x builder combinations (Node/Bun x
Turbopack/Webpack), against one frozen Next.js release — currently `vercel/next.js` `v16.3.8`. Each
nightly run spreads the suite across 16 parallel shards per combination.

**The credential is in progress.** The nights run against the `1.0.0-rc.6` release tag, whose
bytes this release ships unchanged apart from version fields (see
[Same bytes as 1.0.0-rc.6](#same-bytes-as-100-rc6)). The window restarted on rc.6 on 2026-10-08;
when this release was prepared, each of the four combinations stood at **0 of 14** credential
nights. Follow the live count, with run links, on the
[compatibility matrix](https://knext-platform.dev/docs/compat-matrix). Verified status will be
announced when all four combinations complete their 14 consecutive nights — until then, treat v1.0.0 as stable in its
API and semver promise, and **not yet credentialed** against the official suite.

Dispatched confirmation runs at Next.js `v16.3.8` before this release (evidence, not credential
nights — they do not count toward the 14):

| combination | result |
|---|---|
| Node x Turbopack | 1101 of 1101 passed |
| Bun x Turbopack | 1101 of 1101 passed |
| Node x Webpack | dispatched 2026-10-08, result pending when these notes were written |

## Stability tiers

Not every part of knext carries the same promise. A feature is **Stable** only when a red-on-fail
check covers it. The docs site's [Stability tiers](https://knext-platform.dev/docs/stability) page is
the canonical list; in summary:

- **Stable:** the four default-target runtime x builder combinations (Node/Bun x
  Turbopack/Webpack on the standalone build target — their official-suite credential is in
  progress, see above); the `knext.config.ts` schema and the public TypeScript types; the core CLI
  verbs (`create`, `build`, `deploy`, `status`, `doctor`) and their exit codes; the `NextApp`
  custom resource at `v1alpha1` (additive-only); image optimization; graceful shutdown on
  `SIGTERM`; the in-process request body cap on the standalone build target; the default
  `NetworkPolicy` — **enforced only where your cluster's network plugin supports NetworkPolicy**
  (see "What this release does not cover" below).
- **Beta** (shipped and usable, may still change with notice): `knext init-ci`, `knext db-bind`,
  ISR/Redis caching and authenticated cache invalidation, object storage on `gcs`, `s3`, `minio`
  and `azure`, metrics and observability wiring, the 0.4.x → 1.0 upgrade path, and the opt-in
  `vinext` build target (`build: 'vinext'`) on **both** runtimes — the compiled Bun single
  executable (`runtime: 'bun'`) and the Node server with a baked V8 compile cache
  (`runtime: 'node'`).
- **Experimental** (outside the v1.0 semver and compatibility commitment, may change in a minor
  release): the `selfContained` config key / `--self-contained` flag, and the directly-runnable
  `preview`/`loadtest` CLI entries.

**vinext stays Beta.** It ships as an opt-in build option, implemented and tested, but it is not
in the compatibility credential and is not on the path to Stable. The Bun runtime's most recent
measured official-suite result is 728 of 778 tests passing (38 failed, 12 quarantined); the
[compatibility matrix](https://knext-platform.dev/docs/compat-matrix) has the current numbers and
conditions for each runtime.

## What this release does not cover

- **The official Next.js compatibility credential is not complete** (see above). v1.0.0 does not
  claim verified-adapter status.
- **The vinext / compiled single-executable build target** is Beta, outside the compatibility
  credential, and not planned for Stable.
- **No edge middleware or Partial Prerendering (PPR) / Cache Components support.** These are
  architecturally tied to infrastructure the official Next.js Deployment Adapter API does not yet
  standardize for self-hosted deployments; closing this gap is gated on upstream Next.js, not
  solely on knext.
- **No global edge network or CDN.** knext deploys to the Kubernetes cluster(s) you run; it does
  not provide a global point-of-presence network.
- **NetworkPolicy enforcement depends on your network plugin.** The operator reconciles a
  default-on, internal-only `NetworkPolicy` from every `NextApp`, but some common network plugins
  (for example flannel, which both OKE's GA default and OrbStack run) ship no NetworkPolicy
  controller — on those clusters the policy object exists but nothing enforces it. Verify your
  cluster's network plugin supports NetworkPolicy before relying on this for isolation.

## Known issues

Both of these ship in `1.0.0` (they were present in every release candidate) and have fixes
planned for `1.0.1`.

- **Scaffolded apps set `containerConcurrency: 100`, which together with the 8 MiB request-body
  cap can OOM-kill a 1Gi pod under concurrent large uploads.** Every app created by `knext create`
  in this release has `scaling.containerConcurrency: 100` in its `knext.config.ts` — five times the
  operator's default of `20`, which is the concurrency the 8 MiB cap (see "Request body cap now
  applies to the standalone build too" above) is sized for. At `100`, a pod can buffer far more
  concurrent request-body bytes than its memory limit allows. **Delete that line** (the operator's
  default of `20` then applies), or set it to `20` or lower.

- **On the Node runtime with `cache.provider: redis`, the ISR/data cache silently runs in-memory
  per pod instead of Redis.** This affects the **standalone build on the Node runtime**
  (`runtime: 'node'`) only — the **Bun runtime is unaffected** (Bun's own standalone build, and the
  vinext compiled executable, both use a different client). The cache handler's Redis client is a
  real dependency of `@getknext/core`, but `next build`'s output-file-tracing does not discover it —
  it is loaded through a deliberately non-literal import, chosen so a `bun build --compile` bundle
  does not try to follow it — so the module never lands in the standalone output's `node_modules`
  on this one runtime/build combination. The app still serves 200s: it falls back to the same
  per-pod in-memory cache a missing `cacheHandler` block produces (see "Deleting this block does
  not fail the build" in the [ISR & the Redis cache](https://knext-platform.dev/docs/isr-caching)
  guide), so every pod renders independently, cached pages do not survive scale-to-zero, and
  `redis-cli KEYS` against your provisioned Redis stays empty. **Workarounds, in order of
  preference:**
  - **Use the Bun runtime** (`runtime: 'bun'`), the default — it is not affected by this issue.
  - **Accept a per-pod cache until 1.0.1** if you must stay on the Node runtime: correctness is
    unaffected (each pod still renders valid pages), but ISR entries are not shared across pods and
    do not survive scale-to-zero, so expect more cache misses and more regeneration work than a
    shared Redis cache would produce.
  - There is no supported Dockerfile or config change to add the missing client to the Node image
    today — the recipe that builds this image is internal to `@getknext/core` and is not emitted
    into your project, so there is nothing in your own app to safely edit.
