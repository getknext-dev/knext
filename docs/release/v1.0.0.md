# knext v1.0.0

**DRAFT — not published.** Do not tag, publish, or announce from this file. It is the working
draft for the final v1.0.0 release notes and will be finalized once the compat credential (below)
completes and the founder signs off on the release.

## What's new since 0.4.x

knext v1.0.0 is the first release built and verified against the **official Next.js Deployment
Adapter API**, across two build systems (Turbopack, Webpack) and two runtimes (Node, Bun) — four
combinations run nightly against a frozen, pinned Next.js reference as part of the compatibility
credential described below.

Highlights carried forward from the `1.0.0-rc.1` through `1.0.0-rc.5` release candidates (see
`docs/release/v1.0.0-rc.1.md` through `docs/release/v1.0.0-rc.5.md` for the full detail on each):

- **Config file renamed to `knext.config.ts`** (was `kn-next.config.ts`). No dual-read — see
  "Breaking changes" below.
- **Request body cap on every build target.** Request bodies are capped in-process on the
  standalone build (Turbopack or Webpack, Node or Bun) as well as the compiled single-executable
  build — previously only the compiled target enforced this. Default cap: 8 MiB per request,
  configurable via `KNEXT_MAX_REQUEST_BYTES`.
- **`knext` is the canonical CLI name.** The older `kn-next` name keeps working as a deprecated
  alias.
- **GitLab CI support** in `knext init-ci --provider gitlab`, alongside the existing GitHub
  Actions generator.
- **Experimental surfaces marked explicitly.** The `selfContained` config key / `knext build
  --self-contained` flag, and the directly-runnable `preview`/`loadtest` CLI entries, are called
  out as experimental and excluded from the v1.0 semver commitment — see the public API reference
  on the docs site.
- Build-reliability and compile-cache fixes for apps whose home route (or another route on the
  warm boot path) redirects or is rewritten by middleware.
- **Security: Next.js pinned to `16.3.6`.** Fixes a critical remote-code-execution vulnerability
  in `next/og`'s `ImageResponse` (GHSA-vcvr-r3jv-pc5j) present in Next.js `16.2.0`–`16.3.5`. If you
  scaffolded an app from an earlier `1.0.0-rc.x`, run `npm install next@16.3.6` (or later `16.3.x`)
  before going to production.
- **Fix: on-demand cache invalidation (`revalidateTag`/`revalidatePath`) now evicts statically
  rendered and ISR-cached pages**, not only fetch-cache entries, from the Redis cache handler.
- **Cold-start reductions** (standalone builds, measured independently per change — see
  `docs/release/v1.0.0-rc.5.md` for the measurement conditions and why the effects do not simply
  add up): the tracing-client import is skipped when tracing is off; a stale network-neighbour
  entry on affected CNIs no longer stalls the first request after a wake; two `@getknext/lib` SDK
  clients (Cerbos, MinIO) load lazily instead of at import time; apps with no object storage
  configured no longer get an unconditional scratch volume.
- **New, additive, optional CRD field: `spec.security.writableCache`.** Read the upgrade note
  below before upgrading a running cluster — standalone apps no longer get a writable `/tmp` or
  `.next/cache` by default.

See `packages/kn-next/CHANGELOG.md`, `packages/lib/CHANGELOG.md`, and `packages/db/CHANGELOG.md`
for the complete, versioned changelog.

## Upgrade order: operator/CRD first, then CLI

**Always upgrade the knext operator (and its CustomResourceDefinition) in your cluster before
upgrading to this `@getknext/core` release.** A newer CLI version can describe an application
using a field an older operator's CRD does not know about yet. `knext` applies its resources with
strict validation, so upgrading the CLI first can surface an error like:

```
strict decoding error: unknown field "spec.…"
```

If you see that error, upgrade the operator first, then retry:

```sh
kubectl apply -f https://github.com/getknext-dev/knext/releases/download/operator-latest/install.yaml
```

An operator that is *ahead* of your CLI version is always safe — the only ordering constraint is
that the CLI must never be newer than the installed operator.

## Breaking changes

### Config file renamed to `knext.config.ts`

The config file has a new name: `knext.config.ts` (was `kn-next.config.ts`). **There is no
dual-read** — the CLI reads `knext.config.ts` only, and does not fall back to the old filename.

If your app still has the pre-rename config file, rename it before running any `knext` command:

```sh
mv kn-next.config.ts knext.config.ts
```

Running any `knext` command in a directory that still has the old filename (and no
`knext.config.ts`) fails fast with one actionable error naming this exact rename — never a silent
fallback read. `knext create` scaffolds `knext.config.ts` for new apps.

### Request body cap now applies to the standalone build too

If your app accepts uploads larger than 8 MiB through a route handler on the default (standalone)
build target, raise the cap before upgrading — set `KNEXT_MAX_REQUEST_BYTES` (in bytes) in the
`env` map of `knext.config.ts`, or in `spec.env` on the `NextApp` custom resource. Setting it to
`0` removes the cap entirely. See the request-hardening guide on the docs site for the full detail.

### Builder and runtime defaults

Verified against `packages/kn-next/src/config.ts`: `knext create`'s default build target is the
**standalone** shape (`output: 'standalone'`, the official Next.js Deployment Adapter wired via
`adapterPath`) — the compiled single-executable ("vinext") target is opt-in via `--builder vinext`.
Within the standalone target, the default `runtime` is **`bun`**; passing `runtime: "node"` runs
the same standalone server uncompiled under Node's own V8 compile cache instead. Both
`node`/`bun` x `turbopack`/`webpack` combinations are part of the v1.0 compatibility credential
(see below); confirm which combination your app is on before upgrading if you rely on
non-default settings.

### Standalone apps no longer get a writable `/tmp` or `.next/cache` by default

**Read this before upgrading a running cluster.** If your app code writes to `os.tmpdir()`, or
anywhere else at runtime that isn't your database or object storage, set
`spec.security.writableCache: true` on your `NextApp` before upgrading, or the write will fail
against a read-only filesystem. Two shapes keep their previous writable-path behavior with nothing
to change: apps with `spec.storage` configured keep a writable `.next/cache`, and single-executable
(`build: vinext` / `selfContained: true`) builds keep a writable `/tmp`. This field is additive and
optional on the CRD — see the upgrade-order section above; an operator older than this release does
not know the field and will reject a `NextApp` that sets it with a strict-decoding error.

## The v1.0 compatibility credential

v1.0 is gated on **14 consecutive green nightly runs** of the official Next.js compatibility
suite, for each of the four runtime x builder combinations (Node/Bun x Turbopack/Webpack), against
one frozen Next.js release reference. Each nightly run exercises the suite across **16 parallel
shards** per combination. The reference is currently `vercel/next.js` **v16.3.6** (moved there in
rc.4 for the security fix above); the credential window restarts from zero on every release
candidate that changes the frozen set, so nights accumulated on an earlier rc do not carry
forward. See `docs/compat-matrix.md` for the continuously-updated, evidence-gated status of each
cell, including exact pass/fail counts and run IDs — that file is the live source of truth; this
document does not restate a count that would go stale before GA.

## Stability tiers

Not every part of knext carries the same evidence behind it. A feature is **Stable** only if a
**red-on-fail check** covers it. Below, each item names which kind, verified against this
repository's actual branch-protection required-status-context list (not assumed from a job's
presence in `ci.yml`):

- **Stable, nightly-scheduled:** the four credentialed cells above (node/bun x turbopack/webpack
  standalone build, `test-e2e-deploy.yml`); the default-on `NetworkPolicy`
  (`networkpolicy-enforcement.yml`) — **enforced only where your cluster's CNI supports a
  NetworkPolicy controller** (see "What this release does not cover" below).
- **Stable, required-to-merge PR/merge-queue check:** the `knext.config.ts` schema and public CLI
  types (the API-surface-type guard, which runs inside the required **`Lint & Test`** context);
  ISR/Redis caching and authenticated on-demand invalidation (also inside **`Lint & Test`**);
  image optimization (the required **`Prod image next/image optimization`** context); graceful
  shutdown on `SIGTERM` and the standalone request-body cap, for the node/legacy-supervisor path
  (the required **`SIGTERM drain (legacy standalone supervisor)`** context); `gcs`/`s3`/`minio`
  storage backends (inside **`Lint & Test`**).
- **Stable, red-on-fail PR/merge-queue check, but not required-to-merge:** the core CLI verbs
  (`create`, `build`, `deploy`, `status`, `doctor`) with their frozen exit-code manifest (the
  `Ratchet floors never lowered` check); the `NextApp` CRD `v1alpha1` additive-only schema diff
  (the `NextApp CRD schema — additive-only vs. last v* tag` check); graceful shutdown on `SIGTERM`
  for the bun-standalone image path (the `SIGTERM drain (shipped standalone-on-bun image)`
  check). These run and go red on every PR and merge-queue entry, but — unlike the items above —
  are not on this repository's required-status-context list, so a maintainer could in principle
  merge past a red run on one of them; a red run has not been observed to be waved through.
- **Beta** (implemented and tested, not yet behind a red-on-fail check at this depth):
  `knext init-ci`, `knext db-bind`, the `azure` storage backend, metrics/observability wiring, the
  0.4.x → 1.0 upgrade path itself, and — as of the founder decision recorded below — the opt-in
  `vinext` build target (`build: 'vinext'`) on **both** runtimes: the compiled Bun single
  executable (`runtime: 'bun'`) and the Node server with a baked V8 compile cache
  (`runtime: 'node'`).
- **Experimental** (not part of the v1.0 semver or compatibility commitment, may change in a minor
  release): the `selfContained` config key / `--self-contained` flag, and the directly-runnable
  `preview`/`loadtest` CLI entries.

**2026-10-02, founder decision:** `vinext` moves from Experimental to Beta on both runtimes. It
ships as an opt-in build option, implemented and tested — proven against the published
`1.0.0-rc.5` package on a clean install, building and booting on each runtime to a live
response — but it is still **not credentialed**: it carries no 14-consecutive-night compatibility
gate of its own. The Bun runtime's measured official-suite result is 728 of 778 tests passing (38
failed, 12 quarantined, see `docs/compat-matrix.md`); the Node runtime has not been run through
that suite. `vinext` stays Beta in every release; it is not on the path to Stable, and
it is exercised by a scheduled check that publishes a measured pass/fail count.

## What this release does not cover

Being explicit about scope is part of the credential, not a caveat tacked on:

- **The vinext / compiled single-executable build target** is Beta (see above), not Stable, and
  outside the v1.0 compatibility credential's scope, and no Stable promotion is planned for it.
- **No edge middleware or Partial Prerendering (PPR) / Cache Components support.** These are
  architecturally tied to infrastructure the official Next.js Deployment Adapter API does not yet
  standardize for self-hosted deployments; closing this gap is gated on upstream Next.js, not
  solely on knext.
- **No global edge network or CDN.** knext deploys to the Kubernetes cluster(s) you run; it does
  not provide a global point-of-presence network.
- **NetworkPolicy enforcement is CNI-dependent.** The operator reconciles a default-on,
  internal-only `NetworkPolicy` from every `NextApp`, but some common CNIs (for example flannel,
  which both OKE's GA default and OrbStack run) ship no NetworkPolicy controller — on those
  clusters the policy object exists but nothing enforces it. Verify your cluster's CNI supports
  NetworkPolicy before relying on this for isolation.

## Known issues

- **Scaffolded apps set `containerConcurrency: 100`, which together with the 8 MiB request-body
  cap can OOM-kill a 1Gi pod under concurrent large uploads.** Every app created by `knext create`
  before 1.0.1 has `scaling.containerConcurrency: 100` in its `knext.config.ts` — five times the
  operator's default of `20`, which is the concurrency the 8 MiB cap (see "Request body cap now
  applies to the standalone build too" above) is sized for. At `100`, a pod can buffer far more
  concurrent request-body bytes than its memory limit allows. **Delete that line** (the operator's
  default of `20` then applies), or set it to `20` or lower. Fixed at the scaffold level in 1.0.1 —
  apps created with 1.0.1 or later will not set this line.

- **On the Node runtime with `cache.provider: redis`, the ISR/data cache silently runs in-memory
  per pod instead of Redis.** This affects the **standalone build on the Node runtime**
  (`runtime: 'node'`) only, and only when the app's cache reaches the Redis-backed handler at all —
  the **Bun runtime is unaffected** (Bun's own standalone build, and the vinext compiled
  executable, both use a different client). The cache handler's Redis client is a real dependency
  of `@getknext/core`, but `next build`'s output-file-tracing does not discover it — it is loaded
  through a deliberately non-literal import, chosen so a `bun build --compile` bundle does not try
  to follow it — so the module never lands in the standalone output's `node_modules` on this one
  runtime/build combination. The app still serves 200s: it falls back to the same per-pod in-memory
  cache a missing `cacheHandler` block produces (see "Deleting this block does not fail the build"
  in the [ISR & the Redis cache](https://knext-platform.dev/docs/isr-caching) guide), so every pod
  renders independently, cached pages do not survive scale-to-zero, and `redis-cli KEYS` against
  your provisioned Redis stays empty. **Workarounds, in order of preference:**
  - **Use the Bun runtime** (`runtime: 'bun'`), the default — it is not affected by this issue.
  - **Accept a per-pod cache until 1.0.1** if you must stay on the Node runtime: correctness is
    unaffected (each pod still renders valid pages), but ISR entries are not shared across pods and
    do not survive scale-to-zero, so expect more cache misses and more regeneration work than a
    shared Redis cache would produce.
  - There is no supported Dockerfile or config change to add the missing client to the Node image
    today — the recipe that builds this image is internal to `@getknext/core` and is not emitted
    into your project, so there is nothing in your own app to safely edit. Fixed in 1.0.1.
