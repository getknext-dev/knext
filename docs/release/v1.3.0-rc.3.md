# knext v1.3.0-rc.3

**This is a release candidate on a separate line, published to the npm dist-tag `next`.** It does
not replace `1.0.0-rc.5`: the `rc` dist-tag stays on `1.0.0-rc.5`, `latest` is unchanged, and the
v1.0 compatibility credential keeps running against `1.0.0-rc.5`. The v1.0 schedule is unchanged
by this release.

This release fixes the two problems end-to-end testing found in the published `1.3.0-rc.2` (a
vinext build failure after `npm install`, and slow vinext cold starts on some clusters), adds
**private apps**, and bundles more vinext fixes. Apart from private apps, which any app can opt
into, and the `--image` lockfile fix, the changes are specific to the vinext build target.

## What's new since 1.3.0-rc.2

### Private apps: deploy an app with no public route

A new `networking.visibility` option in `knext.config.ts`, and a matching `knext deploy --private`
flag, deploy an app whose route is reachable only from inside the cluster. Use it for an app whose
mutating endpoints (uploads, deletes, admin actions) have no authentication of their own. Leaving
`networking` unset keeps today's behaviour exactly: a public route.

`--private` applies to one run; it is not saved. So a later plain `knext deploy` with no flag now
**refuses** to make a currently-private app public again, and names the new
`knext deploy --public` flag as the only way to confirm that change. `knext preview deploy` has the
same guard. Previews have no `--public` flag, so to make a private preview public you change
`knext.config.ts` on that pull request's branch.

The new field needs an operator (and CRD) that supports it. Upgrade the operator first, or the
deploy is rejected with a schema error. See the "Private apps" docs page for how to deploy a
private app and how to reach it afterwards. **Read the known issue about custom domains below
before you add one to a private app.**

### Fixed: `knext deploy --image` required a lockfile

`knext deploy --image <ref>` deploys a pre-built, digest-pinned image and skips the build, but it
still refused to run without a lockfile in the current directory. It no longer checks for one.

### Fixed: vinext + Node image build failed after `npm install`

With `build: 'vinext'` and `runtime: 'node'`, `knext build` and `knext deploy` could not stage
sharp's native addon into the image unless the app also had a `bun.lock`. An app installed with
plain `npm install`, which is the normal case for a Node app, failed during the image build with
sharp's "Could not load the sharp module using the linuxmusl-x64 runtime". The staging step now
also reads npm's `package-lock.json`, so `npm install` is enough. Rebuild and redeploy to pick up
the fix.

### Fixed: vinext cold starts took about 10 s on some clusters

On some clusters, apps built with `build: 'vinext'` (both the compiled single executable and the
Node runtime) woke from zero several seconds slower than the standalone target. The networking
mitigation described in the scale-to-zero docs, which sends one best-effort outbound packet as
early as possible at process start, was not wired into this build target. It now is, as on every
other knext runtime. No configuration change is needed. Set `KNEXT_ARP_PRIMER=0` to opt out.

On the cluster where `1.3.0-rc.2` was measured at 10 to 16 s per wake, the median wake with this
fix was about 2.3 s. That is one cluster, with the image already cached on the node. It is not a
general performance claim.

### Fixed: `next/og` answered a 500 error in the compiled vinext executable

`next/og`'s `ImageResponse` (for example a dynamic `opengraph-image` route) failed with `ENOENT` in
a `bun build --compile --bytecode` single executable. The compiled binary looked for the image
renderer's WebAssembly and fallback-font files at a path that only existed on the build machine.
`ImageResponse` now works the same compiled as uncompiled.

### `knext create --builder vinext` pins `@vercel/og`

`vinext` 1.0.1 installs `@vercel/og` 1.0.3, whose published package is missing one of its
WebAssembly files. In this build `@vercel/og` stays an external package, which bypasses vinext's
own workaround, so `next/og` answers a 500 error, compiled or not. New apps created with
`knext create --builder vinext` now pin `@vercel/og` to `0.11.1` with an `overrides` entry in
`package.json`. An existing vinext app adds the same entry by hand:

```json
{
  "overrides": {
    "@vercel/og": "0.11.1"
  }
}
```

Remove the entry once a `vinext` release ships a working `@vercel/og`. Other builders are
unchanged.

### vinext: a server action's `redirect()` now answers 200 to client-side requests

When a server action calls `redirect()` and the request comes from the client-side router (a
fetch, not a plain `<form>` submission), the response now always answers HTTP `200`, matching
current Next.js. It previously fell back to `303` in most cases. Only the status code changes: the
redirect target still reaches the browser through the `x-action-redirect` header, and no
`Location` header is set before or after this fix. A no-JavaScript `<form>` submission still
answers `303`. This fix is bundled ahead of its upstream release (`cloudflare/vinext#3689`).

## What this release does not claim

- **No new credentialed combinations.** knext's compatibility credential (14 consecutive green
  nightly runs of the official Next.js compatibility suite) covers four combinations: Node and Bun,
  each with Turbopack and webpack. That credential is **still in progress**, and it is being earned
  on `1.0.0-rc.5`, not on this release.
- **No vinext compatibility claim.** The vinext target is Beta and not credentialed. Any
  compatibility-suite run against the vinext target under this release is a targeted check of the
  fixes above, not a full measurement.
- **No general cold-start claim.** The 2.3 s figure above is one cluster's median, given to show
  the regression is fixed, not a benchmark.

## Install

```sh
npm i @getknext/core@next
```

`@getknext/lib` and `@getknext/db` are installed at the same version through `@getknext/core`'s
dependencies. To run the CLI without installing:

```sh
npx -p @getknext/core@next knext --help
```

To stay on the v1.0 line instead, install `@getknext/core@rc` (`1.0.0-rc.5`).

## Upgrade notes

- **Upgrade the operator (and its CRD) first, then the CLI.** This release adds one more additive,
  optional `NextApp` field (`spec.networking.visibility`) on top of rc.2's
  `spec.security.writeFree`. A CLI that sets either field against an older CRD fails the deploy
  preflight with an `unknown field` error, before anything reaches the cluster. The CLI emits
  `spec.networking.visibility` only for a private app; a public or unconfigured app gets the same
  `NextApp` as before.
- **Existing vinext apps** pick up the bundled redirect fix the next time they run `knext build`.
  To fix `next/og`, they also need the `@vercel/og` override above.
- **Default-target apps (`turbopack`/`webpack`)** see no behaviour change unless they opt into
  private apps.
- **The `next` dist-tag moves.** Later releases on this line will also publish to `next`. Pin an
  exact version (`@getknext/core@1.3.0-rc.3`) if you need the install to stay fixed.

## Package delta against 1.3.0-rc.2

Derived from the source diff between the two release commits. It has not yet been checked by
comparing the packed tarballs file by file.

- **`@getknext/lib`, `@getknext/db`, `kn-next`:** no code change beyond the version bump.
- **`@getknext/core`:**
  - **New files:** one vinext fix patch under `templates/vinext-patches/`, plus its manifest
    entry; the compiled executable's asset-anchoring helper (the `next/og` fix); the visibility
    guard in the CLI.
  - **New package export:** `./internal/arp-primer`, used by the vinext entry to load the cold-start
    networking mitigation. It is internal: the name says so, and it is not a supported API.
  - **Changed templates:** the vinext `package.json` scaffold (the `@vercel/og` override) and the
    vinext Node entry (loads the networking mitigation).
  - **Changed code:** the CLI (`networking.visibility` in config validation and the `NextApp` it
    emits; `--private`/`--public` and the downgrade guard in `deploy` and `preview`; the `--image`
    lockfile fix; npm lockfile support when staging sharp), and the vinext compile step (`next/og`
    asset handling, and embedding the networking mitigation in the compiled executable).

## Known issues

- **A custom domain makes a private app public.** Private apps only mark the app's Knative
  Service as cluster-local. A Knative `DomainMapping` that points at that service is still routed
  through the public load balancer, even if the `DomainMapping` itself is labelled cluster-local.
  So adding a custom domain to a private app silently publishes it. Do not add a `DomainMapping`
  to a private app. To reach one from outside the cluster, put an identity-aware proxy or tunnel in
  front of the internal ingress, as the Private apps page describes for port-forwarding.
- **`knext build` with `cache: redis` requires `REDIS_URL` at build time,** although the scaffold
  says to set it at deploy. Workaround: export any placeholder value when building, for example
  `REDIS_URL=redis://localhost:6379`.
- **`knext doctor` against a v1.0 operator** reports the CRD as missing fields the 1.3 CLI can
  emit. That is the operator-first upgrade order above showing up early; upgrade the operator.
- **The "Edge Runtime is deprecated" warning does not yet match Next.js** on the vinext target.
  Next.js's own test for that warning still fails, so treat it as not yet fixed.
- **`images.loaderFile` is not yet supported on the vinext target.** A custom loader set through
  `next.config.ts`'s `images.loaderFile` is parsed but ignored; only the per-component `loader`
  prop is honoured. Fixing it needs a change inside vinext's own build pipeline.
- **The vinext shebang fix from `1.3.0-rc.2` has two known limits:**
  - A byte-order mark (BOM) before the shebang line is not detected, so such a file still fails to
    build.
  - Source maps for a file whose shebang was stripped and reattached are one line off, which can
    point a debugger or stack trace at the wrong line for that file.
- **Patched Bun toolchain (experimental, opt-in `compile.bun: 'knext-patched'`):** unchanged from
  `1.3.0-rc.1`. There is no cluster-deploy proof yet, each binary's SBOM records only the file and
  its digest, the binaries are compiled on a shared build service account, and the compile step is
  about 4–5% slower than stock Bun.
