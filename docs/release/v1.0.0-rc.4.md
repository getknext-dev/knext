# knext v1.0.0-rc.4

**This is a release-candidate, not the final v1.0.** rc.4 ships a security fix and a cache-handler
correctness fix; it is not credentialed yet (see below).

## Security: Next.js 16.3.6

Next.js versions `16.2.0` through `16.3.5` have a **critical** remote code execution vulnerability
in `next/og`'s `ImageResponse` (GHSA-vcvr-r3jv-pc5j), fixed in `16.3.6`. New apps scaffolded from
rc.4 pin `16.3.6` by default (the vinext builder template moves from `16.3.3`; the default template
moves from `16.3.5`). **If you scaffolded an app from an earlier release candidate, upgrade it:**

```sh
npm install next@16.3.6
```

(or a later `16.3.x`). The v1.0 compatibility credential now runs against Next.js `16.3.6`.

Separately, `@getknext/lib` depends on `@grpc/grpc-js` (through `@cerbos/grpc`) with a range that
already admits the patched `1.14.5` (GHSA-m9gg-hp2v-232j), so a fresh install resolves the fix on
its own — this package is transitive and was never in the bytes `@getknext/lib` ships; nothing in
knext's own published code references it directly. If your lockfile still holds `@grpc/grpc-js`
`1.14.4` or older, update it.

## Fix: on-demand invalidation now evicts cached pages

`revalidateTag` and `revalidatePath` previously returned success without evicting statically
rendered or ISR-cached pages from the Redis cache handler — Next.js stores those pages' tags
(including the implicit path tags `revalidatePath` relies on) in a response header rather than the
cache-write context, and the handler was not reading it. On-demand invalidation now refreshes those
pages on the next request, the same way it already refreshed fetch-cache entries.

## What's in this release

`@getknext/core`, `@getknext/lib`, `@getknext/db`, and the `kn-next` bin all move to `1.0.0-rc.4`
together — they are published as a set and always carry the same version number. Each package's
changelog gains an rc.4 entry.

## The credential window restarts on rc.4

v1.0 needs 14 consecutive green nightly runs of the official Next.js compatibility suite, now
against Next.js `16.3.6`, for each supported runtime x builder combination:

- Node runtime x Turbopack builder
- Node runtime x Webpack builder
- Bun runtime x Turbopack builder
- Bun runtime x Webpack builder

The credential is measured against one specific release tag, so once the windows move to rc.4 the
count restarts from zero for all four combinations — including nights already accumulated on
rc.3. Treat rc.4 as not yet credentialed until those runs accumulate.

## Upgrading: install the operator before the CLI

The upgrade order is unchanged: if you run your own cluster, **upgrade the knext operator (and its
CustomResourceDefinition) first, then the CLI.** This release makes no operator or CRD change, but
the rule still applies if you are coming from an older release. A CLI newer than your installed
operator can fail with an error like:

```
strict decoding error: unknown field "spec.…"
```

If you see that error, upgrade the operator first, then retry:

```sh
kubectl apply -f https://github.com/getknext-dev/knext/releases/download/operator-latest/install.yaml
```

An operator that is *ahead* of your CLI version is always safe.

## Known limits in this release candidate

- **v16.3.6 is not yet a completed compatibility credential** — see above.
- **The compiled single-executable Bun build target is experimental** and outside this window's
  verification scope.
- This is a **release candidate**: expect the version number to change again before the final v1.0
  tag, and do not treat rc.4 as a long-term-support release.
