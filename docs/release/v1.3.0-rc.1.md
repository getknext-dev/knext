# knext v1.3.0-rc.1

**This is a release candidate on a separate line, published to the npm dist-tag `next`.** It does
not replace `1.0.0-rc.5`: the `rc` dist-tag stays on `1.0.0-rc.5`, `latest` is unchanged, and the
v1.0 compatibility credential keeps running against `1.0.0-rc.5`. The v1.0 schedule is unchanged
by this release.

1.3.0-rc.1 is `1.0.0-rc.5` plus changes to the opt-in vinext build target and one docs-domain
change. The default build targets (`turbopack` and `webpack`, on Node or Bun) get no intended
behaviour change. What reaches them is the docs domain in help text, hints and READMEs (see
[Docs domain](#docs-domain-knext-platformdev)) and a refactor of a compile-verification helper the
Bun executable build shares with the vinext target. The exact package delta against `1.0.0-rc.5`
is listed at the end.

## What's new since 1.0.0-rc.5

### The vinext build target, as an opt-in Beta

`build: 'vinext'` compiles your app with [vinext](https://vinext.dev), a Vite-based
implementation of the Next.js framework, instead of `next build`. It is **opt-in** — nothing
changes unless you set it — and it is in the **Beta**
[stability tier](https://knext-platform.dev/docs/stability): shipped and tested on both runtimes,
but not covered by a compatibility credential (see
[What this release does not claim](#what-this-release-does-not-claim)).

It runs on both runtimes:

- **Bun** (the default for this target): the app is compiled into a single executable with
  bytecode caching.
- **Node** (`runtime: 'node'`): a plain Node server, with the V8 compile cache baked into the
  image at build time.

The target itself is not new in this release; it was already selectable in `1.0.0-rc.5`. What
changes on this line is the vinext version it uses, the fixes bundled for it, one build fix, and
two experimental compile options, all below.

### vinext pinned to its first stable release, 1.0.1

Apps scaffolded with `knext create --builder vinext` now pin `vinext` `1.0.1`, vinext's first
stable release, instead of `1.0.0-beta.12`. Peer ranges are unchanged. Existing apps are not
changed for you; see the [upgrade notes](#upgrade-notes).

### Bundled fixes

knext 1.3 ships six vinext fixes that are not in a vinext release yet, so you do not wait on an
upstream release. They are applied to the vinext installed for your app by a new command,
`knext vinext-patches`. A vinext app created by `knext create` runs it from its `postinstall`
script, and `knext build` applies the fixes again before building on the vinext target, so an app
created earlier is covered too. They target the exact vinext version `knext create` pins (`1.0.1`);
with a different vinext version installed they are skipped, with a message saying so. Set
`KNEXT_VINEXT_PATCHES=0` to turn them off. `knext vinext-patches --check` reports without changing
anything. Each fix is removed from knext once a vinext release includes it.

| Upstream | Fix |
|---|---|
| cloudflare/vinext#3472 | Pages Router `/_next/data` requests: `getServerSideProps` sees the original data URL as `req.url` |
| cloudflare/vinext#3423 | `require()` of CommonJS deps resolves the `require` export condition even for packages Vite would externalize |
| cloudflare/vinext#3226 | `turbopack.resolveExtensions` without `.mjs` no longer hides Nitro's preset entry (build failure) |
| cloudflare/vinext#3424 | RSC dependencies are bundled under Nitro so `react-server` export conditions apply |
| cloudflare/vinext#3241 | Web Worker bundles get `process.env.NEXT_DEPLOYMENT_ID` inlined |
| cloudflare/vinext#3436 | `outputFileTracingIncludes`/`Excludes` reach Nitro's dependency trace |

Not bundled: cloudflare/vinext#3480 (knext's own cache adapter is not affected by it),
cloudflare/vinext#3429 (deferred: the fix is a larger refactor than could be validated for this
release), and cloudflare/vinext#3479 (documentation only).

### Fixed: `knext build` on glibc Linux for vinext apps that use `sharp`

On a glibc-based Linux build machine (most Linux CI runners, including GitHub-hosted ones, and
most Linux desktops), `knext build` on the vinext target with the default Bun runtime failed with
`Unknown build arch 'linux-x64-gnu'` for any app depending on `sharp`. Every app that
`knext create --builder vinext` scaffolds depends on `sharp` for image optimization, so this hit
the scaffolded app by default. macOS build machines were not affected.

The failure was in the build's own boot check (`knext build` boots the compiled executable once
to confirm it serves and drains before finishing), not in the shipped executable. That check now
stages a native `sharp` addon that matches the build machine, in its own directory, so it no
longer overwrites the addon packaged for the image.

### Experimental: `compile.include` for the compiled vinext executable

`compile: { include: ['plugins/*.js'] }` in `knext.config.ts` embeds the matching
JavaScript/TypeScript modules in the compiled vinext executable, on stock Bun. Each module lands at
`/$bunfs/root/<path relative to the app root>` and loads on its first `import()` — not at startup,
and with nothing beside the binary. The build fails, naming the culprit, on an absolute or `..`
pattern, a match whose real path is outside the app root, a glob match that looks like a secret
(`.env*`, `*.pem`, `*.key`, `id_*`; naming that exact file is allowed), a pattern that matches
nothing, a non-module match, or a native addon (`.node`, `.so`, `.dylib`, `.dll`). Directory
patterns never embed `node_modules`. It is accepted only for `build: 'vinext'` on `runtime: 'bun'`.
Without a `compile` block the build is unchanged. See
[Including extra files in the compiled executable](https://knext-platform.dev/docs/build-pipeline#including-extra-files-in-the-compiled-executable-experimental).

### Experimental, opt-in: a patched Bun toolchain for the compile step

`compile: { bun: 'knext-patched' }` runs the vinext compile step with a knext-published build of
**Bun 1.4.2 plus `--compile --include`** (`bun-patched-1.4.2-knext.2`), an option that is not in a
Bun release yet. The default (`bun: 'stock'`, or no `bun` key) is the Bun on your `PATH`, unchanged.
`compile.include` keeps its meaning and every check above: knext expands and checks the patterns
the same way, and hands only the resulting files (never your raw globs) to the patched Bun, at the
same `/$bunfs` paths. If the compiler does not embed a listed module, the build fails.

**How it is verified.** `knext build` downloads the toolchain into a local cache and checks its
sha256 against a value pinned in the `@getknext/core` version you installed. A mismatch, an HTTP
error or a network error fails the build; it never falls back to stock Bun, and nothing unverified
is cached. A cached copy is re-hashed on every build. The toolchain release is published only after
its own gates pass (checksums, a smoke test on x64 and on a real arm64 machine, and an end-to-end
`knext build` that boots the image and loads an included module). Its checksum file is signed with
cosign (keyless, by the knext release workflow), and each binary has a GitHub build-provenance
attestation. `knext build` does not check the signature or the attestation — the pinned sha256 is
the binding check — but you can; the commands are in
[Optional patched Bun toolchain](https://knext-platform.dev/docs/build-pipeline#optional-patched-bun-toolchain-experimental).

It runs the compile step only: the executable you ship still runs on stock Bun's linux-musl base.
It is published for **Linux glibc build machines, x64 and arm64**; on musl (Alpine), macOS or
Windows build machines the build stops with an error that says so, and it is rejected on any build
target other than vinext.

**Known limits:**

- **No cluster-deploy proof yet.** It is tested by building the real container image with it,
  booting that image and loading an included module, on x64 and arm64 build machines. A full
  `knext deploy` to a Kubernetes cluster with this toolchain has not been run.
- **Thin SBOM.** Each binary's SBOM records only the file and its digest, with no component list.
  The separate source SBOM lists the Bun source tree's components but does not record the added
  patch.
- **Build identity.** The binaries are compiled on Google Cloud Build under the project's default
  build service account, not a dedicated least-privilege one. The signature and attestation cover
  the release workflow's checks and publication, not that build machine.
- **A slower compiler.** It is not built with link-time optimisation, so the compile step runs
  about 4–5% slower than stock Bun. The executable you ship is unaffected.

### Docs domain: knext-platform.dev

knext's docs site is **https://knext-platform.dev**. Every user-facing docs URL in the CLI (help
text, `knext doctor` and missing-config hints, the scaffolded `knext.config.ts` comments, the
asset-upload hint) and in the package READMEs now points there. Kubernetes label keys and API
group names are unchanged; they are identifiers, not links.

## What this release does not claim

- **No new credentialed combinations.** knext's compatibility credential (14 consecutive green
  nightly runs of the official Next.js compatibility suite) covers four combinations: Node and Bun,
  each with Turbopack and webpack. That credential is **still in progress**, and it is being earned
  on `1.0.0-rc.5`, not on this release.
- **vinext is not credentialed.** The vinext target is Beta, and `compile.include` and the patched
  Bun toolchain are experimental: tested in knext's own CI, but not behind the compatibility suite.
  Do not read this release as a compatibility claim for any of them.
- **No cold-start or performance claims** beyond those already published with `1.0.0-rc.5`.

## Install

```sh
npm i @getknext/core@next
```

`@getknext/lib` and `@getknext/db` are installed at the same version through `@getknext/core`'s
dependencies. To run the CLI without installing:

```sh
npx -p @getknext/core@next knext --help
```

To stay on the v1.0 line instead, install `@getknext/core@rc` (`1.0.0-rc.5`).

## Upgrade notes

- **From 1.0.0-rc.5: no CRD or operator change.** Same CRD `apiVersion` (`v1alpha1`) and the same
  operator bundle. The usual order still applies: upgrade the operator/CRD first, then the CLI.
- **Default-target apps (`turbopack`/`webpack`) see no behaviour change.** There is no reason to
  move a default-target app to this line other than to try the vinext target.
- **Existing vinext apps keep the vinext version in their own `package.json`.** To move to
  `1.0.1`, change `"vinext": "1.0.0-beta.12"` to `"vinext": "1.0.1"`, reinstall, and rebuild. The
  bundled fixes apply only to vinext `1.0.1`. `knext build` applies them on the vinext target
  either way; to also apply them on install, as new apps do, run `knext vinext-patches` from your
  app's `postinstall` script (a newly scaffolded vinext app shows a version that also tolerates a
  production install without `@getknext/core`).
- **The `sharp` fix takes effect at build time.** Rebuild with this CLI to pick it up; images you
  already built are not affected by it either way.
- **The `next` dist-tag moves.** Later releases on this line will also publish to `next`. Pin an
  exact version (`@getknext/core@1.3.0-rc.1`) if you need the install to stay fixed.

## Package delta against 1.0.0-rc.5

Measured by packing this release with `npm pack` (the publish tool) and comparing it file by file
with the `1.0.0-rc.5` tarballs downloaded from the npm registry, after substituting the version
string on both sides. Source maps (`.map`) follow their `.js` files and are not listed.

- **`@getknext/lib`, `@getknext/db`, `kn-next`:** `README.md` only (the docs domain). No code
  change.
- **`@getknext/core`:**
  - **New files:** `templates/vinext-patches/` (the manifest and the six fix patches) and the
    `vinext-patches` CLI chunk.
  - **Changed templates:** `package.json.vinext.hbs` (vinext `1.0.1`, the `postinstall`
    step), `knext.config.ts.hbs` and `knext.config.ts.vinext.hbs` (docs domain in comments),
    `.dockerignore.hbs` and `gitignore.hbs` (exclude the build check's temporary `sharp` directory).
  - **Changed code:** the CLI (`dist/cli/*`: the new `vinext-patches` verb; the `compile` option in
    `build`, `deploy` and `preview`; the `sharp` build-check fix; docs-domain URLs in help text and
    hints), config types and validation (`dist/config.d.ts`, `dist/validate-public.js`: the
    experimental `compile` block), and `dist/adapters/vinext-compile.js`.
  - **Shared code also used by the default Bun target:** `dist/adapters/standalone-compile.js`
    differs because it bundles the compile-embed and bytecode-verification helpers, which were
    extended for `compile.include`. The functions the standalone build calls keep their checks; the
    bytecode scan was factored into a shared helper. No option or default of the standalone build
    changed.
  - **Renamed bundle chunks:** 16 `dist/chunk-*.js`-style files were replaced by 17 with new
    content hashes (the bundler's naming), plus the new `vinext-patches` chunk.
  - **`package.json`:** the version, and the `vinext` devDependency `1.0.0-beta.12` → `1.0.1`
    (devDependencies are not installed by consumers).
