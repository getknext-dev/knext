# knext v1.3.0-rc.2

**This is a release candidate on a separate line, published to the npm dist-tag `next`.** It does
not replace `1.0.0-rc.5`: the `rc` dist-tag stays on `1.0.0-rc.5`, `latest` is unchanged, and the
v1.0 compatibility credential keeps running against `1.0.0-rc.5`. The v1.0 schedule is unchanged
by this release.

Unlike `1.3.0-rc.1`, several of this release's fixes reach **default-target apps** (`turbopack`
and `webpack`, on Node or Bun) as real behaviour changes, not just docs or vinext-only changes —
see each section below and [Upgrade notes](#upgrade-notes).

## What's new since 1.3.0-rc.1

### Cold start: apps with object storage, and vinext apps, no longer need a writable volume

Each writable scratch volume the operator mounts costs pod-sandbox setup time on every
scale-from-zero wake. Two app shapes that previously got one by default no longer need it:

- **Standalone apps with `storage` configured.** The knext adapter now sets Next's official
  `images.customCacheHandler` option when the app uses the knext cache handler, so optimized
  `next/image` variants are stored through the cache handler instead of on local disk: on the Bun
  runtime with Redis configured, in Redis (shared across pods, kept across scale-to-zero).
  Otherwise they go in a per-pod in-memory cache capped at 32 MiB
  (`KNEXT_IMAGE_CACHE_MEMORY_BYTES`). That includes the Node runtime for now, which falls back to
  the memory cache and re-optimizes variants after each scale-to-zero. Set
  `KNEXT_IMAGE_CACHE_HANDLER=0` at build time to keep Next's disk cache.
- **vinext apps built as a disk-mode binary** (the default) — the image optimizer's native
  addon loads from the executable's read-only bundle, so nothing is written at runtime.

`knext deploy` now sets a new optional `NextApp` field, `spec.security.writeFree: true`, for an
image it built in the same run when that image writes nothing to local disk. The operator then
renders no writable volume at all, with `readOnlyRootFilesystem` still on. The CLI sets it only
when it changes the result, so a standalone app without storage gets the same `NextApp` as
before. It is never set for `--image`/`--skip-build` deploys or for self-contained vinext
binaries, which still unpack their native addon into `/tmp`. `spec.security.writableCache: true`
still mounts both writable paths.

**Upgrade order:** upgrade the operator (and its CRD) before the CLI. A CLI that sets
`spec.security.writeFree` against an older CRD fails the deploy preflight with
`unknown field "spec.security.writeFree"`.

### Fixed: the Node runtime's ISR/data cache silently fell back to memory

On the standalone Node runtime, the image did not include a Redis client. When Redis was
configured, the cache handler fell back to an in-memory store without saying so: cache entries
were not shared between pods and were lost on every scale-to-zero. The Bun runtime was not
affected — Bun has a Redis client built in.

The cache handler now has one entry per runtime, and `knext build`, `knext deploy` and
`knext preview` pick the entry that matches your configured runtime. On Node it uses `ioredis`,
which the build now copies into the image. On Bun it uses Bun's built-in Redis client. If Redis
is configured but its client cannot be loaded, the handler now logs one error at startup,
starting with `Redis client unavailable`, instead of quietly running from memory.

### `knext create` now asks for your setup

Running `knext create` on a terminal with no flags now asks for the runtime (`bun` or `node`),
builder (`turbopack`, `webpack` or `vinext`), ISR/data cache (`none` or `redis`), object storage
provider, and React Compiler. Each question has a matching flag (`--runtime`, `--builder`,
`--cache`, `--storage`, `--react-compiler`), and `--yes` skips them all. With any flag set, `CI`
set, or no terminal attached, `knext create` asks nothing and uses the same defaults as before,
scaffolding the same app as before.

Choosing `node` adds `ioredis` to the scaffolded app's dependencies, at the same range
`@getknext/core` uses. A Bun app gets nothing extra. `--builder` now accepts `turbopack` and
`webpack` explicitly; `default` still works and still means `turbopack`.

**New apps now have React Compiler turned on by default, on every builder.** On `turbopack`/
`webpack`, the scaffold adds `reactCompiler: true` to `next.config.ts` plus
`babel-plugin-react-compiler`. On `vinext`, it adds `react: { compiler: true }` to
`vite.config.ts` plus the packages that option needs. Pass `--no-react-compiler` (or answer `n`
at the prompt) to leave it off, which scaffolds the same app as before this release.

### Scaffolds no longer set `containerConcurrency: 100`

`knext create` no longer writes `scaling.containerConcurrency: 100` into new apps' `knext.config.ts`
(both the standalone/turbopack-or-webpack and vinext templates). The operator's default of `20`
now applies instead — the concurrency the 8 MiB request-body cap is sized for. At `100`,
concurrent large uploads could buffer enough bytes to OOM-kill a 1Gi pod.

Apps created before this release that still carry `containerConcurrency: 100` in their
`knext.config.ts` are unaffected by this change; delete the line, or set it to `20` or lower,
to pick up the safer default.

### vinext target fixes

One regression fix to an `1.3.0-rc.1` bundled fix, plus six more small fixes, for the opt-in,
Beta vinext build target, on top of the six bundled in `1.3.0-rc.1`:

- A regression in one of the `1.3.0-rc.1` bundled fixes (the port of upstream
  cloudflare/vinext#3424, which bundles a route's RSC dependencies so a package's
  `react-server` export condition is honoured under the compiled-executable build target) is
  fixed: the blanket bundling also swept packages that must stay external — including `sqlite3`'s
  native-addon helper and `typescript` — into the compiled binary. Those packages now stay
  external, matching the non-Nitro RSC branch's behaviour, so the original fix no longer bundles
  packages that are not safe to inline.
- `experimental.lightningCssFeatures.include`'s `custom-media-queries` entry now also turns on
  lightningcss's custom-media parser flag, so a stylesheet using `@custom-media` builds instead of
  failing to parse.
- App Router: a GET/HEAD request for an unmatched path whose destination is a non-HTML
  subresource (image, font, script, manifest, …) now gets the same plain-text 404 an invalid
  `_next/static/*` request already gets, instead of compiling and rendering the full custom
  not-found page.
- A route whose resolved runtime is `edge`/`experimental-edge` now prints the "Edge Runtime is
  deprecated" warning once per build/dev session, matching Next.js.
- A bare `//` (literal or percent-encoded, with nothing after it) in a request path is no longer
  treated as an open-redirect shape and 404'd; it now serves the index route, matching Next.js.
- A `next.config.js`/`.ts` exported as a function now receives the same defaults Next.js itself
  would pass it (previously an empty object), so a config that reads a field off its second
  argument — for example appending a custom page extension by reading
  `defaultConfig.pageExtensions` — no longer throws at build time (`cloudflare/vinext#3687`).
- A source file that starts with a shebang line (`#!/usr/bin/env node`) and also uses CommonJS
  syntax (`module.exports`, `require(...)`) now builds instead of failing with an invalid-syntax
  error. The shebang is preserved at the top of the built output (`cloudflare/vinext#3688`).

All of these are runtime-agnostic (they also help a future vinext-on-Node lane, not just
vinext-on-Bun).

### Fixed: `next/image` on the vinext target ignored `trailingSlash`, and a custom `loader` lost its responsive `srcSet`

Two more vinext image-optimization fixes, bundled the same way as the others above:

- With `trailingSlash: true`, the image optimization endpoint now requests
  `/_next/image/?url=...` (matching Next.js) instead of always `/_next/image?url=...`. This
  affected both the App Router `next/image` component and the legacy `next/legacy/image`
  wrapper.
- A custom `loader` function passed to `next/image` now gets the same per-breakpoint `srcSet`
  treatment the built-in loader gets — called once per responsive width, with `quality` passed
  through as given — instead of being called once at the raw intrinsic width with `quality`
  forced to `75` and no `srcSet` produced.

## What this release does not claim

- **No new credentialed combinations.** knext's compatibility credential (14 consecutive green
  nightly runs of the official Next.js compatibility suite) covers four combinations: Node and Bun,
  each with Turbopack and webpack. That credential is **still in progress**, and it is being earned
  on `1.0.0-rc.5`, not on this release.
- **No new vinext compatibility measurement for this release.** The vinext target is Beta and not
  credentialed. The fixes above were validated in knext's own test suite; a fresh run of the
  compatibility suite against the vinext target under this release has not happened yet, and
  this document makes no claim about its result.
- **No cold-start or performance claims** beyond those already published with `1.0.0-rc.5` and
  `1.3.0-rc.1`.

## Install

```sh
npm i @getknext/core@next
```

`@getknext/lib` and `@getknext/db` are installed at the same version through `@getknext/core`'s
dependencies. To run the CLI without installing:

```sh
npx -p @getknext/core@next knext --help
```

To stay on the v1.0 line instead, install `@getknext/core@rc` (`1.0.0-rc.5`).

## Upgrade notes

- **From 1.3.0-rc.1: no CRD or operator change.** Same CRD `apiVersion` (`v1alpha1`) and the same
  operator bundle. The usual order still applies: upgrade the operator/CRD first, then the CLI —
  this release adds one new, additive, optional `NextApp` field (`spec.security.writeFree`), and
  a CLI that sets it against an older CRD fails the deploy preflight rather than the running app.
- **Default-target apps (`turbopack`/`webpack`) DO see behaviour changes in this release**, unlike
  `1.3.0-rc.1`: the Redis cache-client fix (Node runtime apps with Redis configured now actually
  use Redis instead of silently falling back to memory), the write-free cold-start change for
  apps with object storage configured, the dropped `containerConcurrency: 100` default in newly
  scaffolded apps, and the new `knext create` prompts with React Compiler on by default for new
  apps. None of these change an *existing* app's behaviour without a new build/deploy; rebuild and
  redeploy to pick them up.
- **Existing vinext apps** pick up the three additional bundled fixes the next time they run
  `knext build` on the vinext target (the fixes are re-applied at build time regardless of what
  `knext vinext-patches` was run at install time).
- **The `next` dist-tag moves.** Later releases on this line will also publish to `next`. Pin an
  exact version (`@getknext/core@1.3.0-rc.2`) if you need the install to stay fixed.

## Package delta against 1.3.0-rc.1

Measured by packing this release with `npm pack` (the publish tool) and comparing it file by file
with the `1.3.0-rc.1` tarballs downloaded from the npm registry (`next` dist-tag), after
substituting the version string on both sides.

- **`@getknext/lib`, `@getknext/db`, `kn-next`:** no code change beyond the version bump.
- **`@getknext/core`:**
  - **New files:** seven new vinext fix patches under `templates/vinext-patches/`, plus their
    manifest entries.
  - **Changed files:** the existing RSC-dependency-bundling patch's content (the regression fix
    above) and its manifest entry's pristine sha256.
  - **Changed templates:** the `create` scaffold templates (removed `containerConcurrency: 100`,
    Redis cache handler wiring, React Compiler wiring) and the interactive-prompt flow in
    `knext create` itself.
  - **Changed code:** the CLI (the new interactive prompts and their flags; the per-runtime cache
    handler selection in `build`/`deploy`/`preview`; the `spec.security.writeFree` wiring in
    `deploy`), the Next.js adapter (`images.customCacheHandler` wiring), and the image cache-sync
    helper (stands down when images are stored through the cache handler).

## Known issues

- **`images.loaderFile` is not yet supported on the vinext target.** A custom loader supplied
  through `next.config.ts`'s `images.loaderFile` is parsed but ignored; only the per-component
  `loader` prop (fixed above) is honoured. Wiring `images.loaderFile` needs a change inside
  vinext's own build pipeline (how it resolves the loader module), rather than a dist-level patch
  like the other bundled fixes, so it stays open pending that upstream change.
- **The shebang fix above has two known limits:**
  - A byte-order-mark (BOM) before the shebang line is not detected, so a file saved as
    `#!/usr/bin/env node` with a leading BOM still fails to build the same way it did before this
    fix.
  - Source maps for a file that had its shebang stripped and reattached are offset by one line
    relative to the original source, which can point a debugger or stack trace at the wrong line
    for that file.
- **Patched Bun toolchain (experimental, opt-in `compile.bun: 'knext-patched'`) — unchanged from
  1.3.0-rc.1:**
  - No cluster-deploy proof yet: verified by building and booting the image on x64 and arm64 build
    machines, not by a full `knext deploy` to a Kubernetes cluster.
  - Thin SBOM: each binary's SBOM records only the file and its digest, with no component list.
  - Build identity: the binaries are compiled on a shared-project Cloud Build service account, not
    a dedicated least-privilege one.
  - A slower compiler: the compile step runs about 4–5% slower than stock Bun; the shipped
    executable is unaffected.
