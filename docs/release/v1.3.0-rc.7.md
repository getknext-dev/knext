# knext v1.3.0-rc.7

**This is a release candidate on a separate line, published to the npm dist-tag `next`.** It does
not replace `1.0.0-rc.5`: the `rc` dist-tag stays on `1.0.0-rc.5`, `latest` is unchanged, and the
v1.0 compatibility credential keeps running against `1.0.0-rc.5`. The v1.0 schedule is unchanged
by this release.

This release fixes seven problems found on `1.3.0-rc.6`, all on the vinext target or in the
scaffold: `images.loaderFile` was ignored, Pages Router apps had no `/_next/image` route on Node,
`<style jsx>` pages crashed, a rewrite to a file in `public/` returned the 404 page, text before a
`next/dynamic` component rendered an extra marker, the compiled executable only embedded sibling
files for `@vercel/og`, and new apps declared an older `sharp` floor. It also adds an operator
status condition for pods the cluster refuses to create. Everything else in `1.3.0-rc.6` is
unchanged.

## What's new since 1.3.0-rc.6

### Fixed: `images.loaderFile` works on the vinext target

`images.loaderFile` in `next.config` now makes `next/image` render through your custom loader
instead of silently using the built-in `/_next/image` endpoint. A missing loader file, or a
`loader` other than `default` or `custom` set next to it, fails the build as in Next.js, and
`images.loader: 'custom'` without a loader throws Next.js's missing-loader error.

### Fixed: Pages Router apps serve `/_next/image` on vinext

A Pages Router app on the vinext target now serves `/_next/image` instead of answering 404, so
images left on the built-in optimizer load, including ones a `loaderFile` loader sends to
`/_next/image/`. A `url` that points back at `/_next/image` is rejected with a 400, as in Next.js.

### Fixed: `<style jsx>` pages render on vinext

Pages that use `<style jsx>` no longer fail with an "Invalid hook call" error. The Nitro build now
traces `react` and `react-dom`, so styled-jsx shares the server's single React copy, on both the
Node build and the compiled single executable.

### Fixed: rewrites to files in `public/` on vinext

A `next.config` rewrite (or a middleware rewrite) whose destination is a file in `public/` now
serves that file instead of the 404 page. This covers the Pages Router in all three rewrite phases
(`beforeFiles`, `afterFiles`, `fallback`) and the App Router's `beforeFiles` and middleware
rewrites. Middleware still does not run for a direct request to a file in `public/` on this target.

### Fixed: text before a `next/dynamic` component on vinext

Text followed by a `next/dynamic` component now server-renders like Next.js: there is no extra
`<!-- -->` marker between the text and the component's Suspense boundary. The component's preload
hints are still emitted.

### Fixed: the compiled executable embeds sibling files from any package

The vinext Bun single executable now embeds a file that any dependency reads from beside its own
code (`readFileSync(new URL('./x.wasm', import.meta.url))`, directly or through `fileURLToPath`).
Before, only `@vercel/og` was covered, so another package with the same pattern failed with
`ENOENT` once the binary left the build machine. File reads are embedded; `new Worker(...)`,
`fetch(...)` and dynamic `import(...)` URLs are left unchanged. The build log lists each embedded
file.

### Changed: bundled vinext fixes follow the upstream maintainers' latest versions

Repeated slashes and backslashes in a request path redirect (`308`) like Next.js, a custom
`next/image` loader also serves `fill` images and skips inline sources,
`outputFileTracingIncludes` and `outputFileTracingExcludes` follow Next.js route and glob matching,
and `x-nextjs-cache: MISS` on `/_next/image` is sent only with the image bytes. Two bundled fixes
were dropped because vinext 1.0.1 already behaves that way or upstream declined them.

### Changed: new apps declare `sharp` `^0.35.5`

Apps and zones scaffolded by `knext create` now declare `sharp` `^0.35.5`, the first release with
the fix for GHSA-wq5f-xc86-pv6w. The old `^0.35.2` range already resolved to a fixed version at
install time; the declared floor now excludes the vulnerable releases too.

### Added: the operator reports pods the cluster refuses to create

When a namespace `LimitRange` or `ResourceQuota` rejects the app's pods, the operator now sets a
`PodCreationBlocked` condition on the `NextApp` (reason `LimitRangeRejected` or `QuotaExceeded`)
with the admission message and the revision name, and emits one Warning event per change. The
condition clears when the revision recovers or a new one appears. This needs an operator built from
this line; the published operator images do not include it yet.

## What this release does not claim

- **No new credentialed combinations.** knext's compatibility credential (14 consecutive green
  nightly runs of the official Next.js compatibility suite) covers four combinations: Node and Bun,
  each with Turbopack and webpack. That credential is **still in progress**, and it is being earned
  on `1.0.0-rc.5`, not on this release.
- **No vinext compatibility claim.** The vinext target is Beta and not credentialed.
- **No compatibility-count claim** is made for this release.

## Install

```sh
npm i @getknext/core@next
```

`@getknext/lib` and `@getknext/db` are installed at the same version through `@getknext/core`'s
dependencies. To run the CLI without installing:

```sh
npx -p @getknext/core@next knext --help
```

To stay on the v1.0 line instead, install `@getknext/core@rc` (`1.0.0-rc.5`).

## Upgrade notes

- **Upgrade the operator (and its CRD) first, then the CLI, once an operator release from this line
  exists (see Known issues).** This release adds no new `NextApp` field.
- **The `PrivateExposure` warning (added in `1.3.0-rc.5`) needs an operator built from the 1.3
  line.** The published operator images do not include it; upgrade the operator before relying on
  the warning.
- **The `next` dist-tag moves.** Later releases on this line will also publish to `next`. Pin an
  exact version (`@getknext/core@1.3.0-rc.7`) if you need the install to stay fixed.

## Package delta against 1.3.0-rc.6

Derived from the source diff between the two release commits. It has not been checked by
comparing the packed tarballs file by file.

- **`@getknext/lib`, `@getknext/db`, `kn-next`:** no code change beyond the version bump.
- **`@getknext/core`:** the vinext compile step and its new sibling-asset analysis (two new
  files), the bundled vinext patches and their manifest, the `KNEXT_VINEXT_PATCHES` handling in the
  CLI, and the scaffold templates (`sharp` floor). New runtime dependency: `acorn`, used to analyse
  which URLs a dependency reads as files.
- **Operator (not an npm package):** a new `PodCreationBlocked` status condition and a read grant
  on revisions already held; no new `NextApp` field.

## Known issues

- **No published operator release supports this line's two new `NextApp` fields yet.** The
  operator releases (`operator-latest`, and the rolling `operator-edge`) are built from the v1.0
  line, whose CRD has neither `spec.networking.visibility` (`1.3.0-rc.4`) nor
  `spec.security.writeFree` (`1.3.0-rc.2`). A deploy that sets either field fails the deploy
  preflight with an `unknown field` error, before anything reaches the cluster. Against those
  operators:
  - **private apps cannot be deployed** (`networking.visibility: "cluster-local"` or `--private`);
  - **a vinext app in its default (not self-contained) mode fails `knext deploy`** when the CLI
    builds the image in the same run, which is the normal case, on either runtime, because the
    CLI then sets `spec.security.writeFree`;
  - **a standalone app with `storage` configured fails `knext deploy`** when the CLI builds the
    image in the same run. The preflight runs before the build and assumes the field, so building
    with `KNEXT_IMAGE_CACHE_HANDLER=0` does not avoid it. Standalone self-contained executables
    fail the same way.

  Other standalone apps deploy as before. What to do until an operator release from
  this line is published:
  - **standalone apps with `storage` or a self-contained executable:** stay on `1.0.0-rc.5`
    (`@getknext/core@rc`). On `1.0.0-rc.5`, a Node app with `cache: redis` silently uses an
    in-memory cache instead of Redis (fixed in `1.3.0-rc.2`);
  - **vinext on Bun:** use `1.3.0-rc.1`, which sets neither field. `1.0.0-rc.5` does not work for
    a vinext app created on this line, because its scaffold runs `knext vinext-patches` on install
    and that command does not exist before `1.3.0-rc.1`;
  - **vinext on Node, and standalone apps with `storage` that need this line:** there is no tested
    workaround yet.

- **A custom domain makes a private app public.** Private apps only mark the app's Knative
  Service as cluster-local. A Knative `DomainMapping` that points at that service is still routed
  through the public load balancer, even if the `DomainMapping` itself is labelled cluster-local.
  So adding a custom domain to a private app silently publishes it. Do not add a `DomainMapping`
  to a private app (an operator from this line warns about it; the published operator images do
  not yet). To reach one from outside the cluster, run a tunnel to the cluster's internal
  gateway that rewrites the `Host` header, behind an identity-aware proxy.
- **The "Edge Runtime is deprecated" warning does not yet match Next.js** on the vinext target.
  Next.js's own test for that warning still fails, so treat it as not yet fixed.
- **The vinext shebang fix from `1.3.0-rc.2` has two known limits:**
  - A byte-order mark (BOM) before the shebang line is not detected, so such a file still fails to
    build.
  - Source maps for a file whose shebang was stripped and reattached are one line off, which can
    point a debugger or stack trace at the wrong line for that file.
- **Patched Bun toolchain (experimental, opt-in `compile.bun: 'knext-patched'`):** unchanged from
  `1.3.0-rc.1`. There is no cluster-deploy proof yet, each binary's SBOM records only the file and
  its digest, the binaries are compiled on a shared build service account, and the compile step is
  about 4–5% slower than stock Bun.
