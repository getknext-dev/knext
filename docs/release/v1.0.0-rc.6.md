# knext v1.0.0-rc.6

**This is a release-candidate, not the final v1.0.** rc.6 is a security and correctness release:
a high-severity Next.js security update for newly scaffolded apps, and a workaround for an
intermittent 500 on routes that opt out of dynamic params. Neither changes the CRD or the
operator.

## Security: Next.js 16.3.8

New apps now scaffold with Next.js **16.3.8** (the default and vinext builder templates move from
16.3.6). Next.js 16.0.0 through 16.3.7 have a high-severity server-side request forgery in Image
Optimization ([GHSA-cjq9-62q9-8jv4](https://github.com/advisories/GHSA-cjq9-62q9-8jv4)), fixed in
16.3.8. Every app scaffolded from an earlier release candidate pins a vulnerable Next.js.

**If you scaffolded an app from an earlier release candidate, upgrade it:**

```sh
npm install next@16.3.8
```

(or a later 16.3.x). Your app's own `next` dependency is yours to bump; upgrading the knext
packages does not change it.

**Cache upgrade note.** Next.js 16.3.7 and later scope every cached entry to its source route, so
cache keys now start with `/route-cache/`. The knext cache handler treats every key as an opaque
string, so it needs no change. After upgrading an existing app, entries written to Redis under the
old key shape (by Next.js before 16.3.7) are never read again and stay in Redis until their TTL
expires; the affected pages are regenerated on first request.

## Fix: intermittent 500 on `dynamicParams = false` routes

On Next.js before 16.4.0, a route with `dynamicParams = false` could answer a burst of concurrent
prefetches for a parameter outside `generateStaticParams` with a **500 instead of a 404**, whenever
an adapter was configured. Next.js fixed this in 16.4.0 and did not backport it.

`knext build`, `deploy` and `preview` now clear `adapterPath` from the standalone server's runtime
configuration (`server.js` and `.next/required-server-files.json`) when the installed Next.js is
older than 16.4.0, before the Bun executable is compiled, so both runtimes ship the fix. The
adapter only works during `next build`, so nothing at runtime depends on it. Those requests become
plain 404s, as on a standalone server without an adapter, and each one logs
`Error: Internal: NoFallbackError`. On Next.js 16.4.0 or later nothing changes: the workaround is
gated on the installed Next.js version and removes itself there. It is intended to be retired once
Next.js 16.4 (or a 16.3.x backport) is the credentialed version.

## Operator first, then CLI

The upgrade order is unchanged: **upgrade the knext operator (and its CustomResourceDefinition)
first, then the CLI.** This release makes **no CRD change** and no operator change, so there is no
new field to wait for; keep the order anyway, since an operator that is *ahead* of your CLI version
is always safe.

## Credential: the window restarts on rc.6

v1.0 needs 14 consecutive green nightly runs of the official Next.js compatibility suite, now
against Next.js `16.3.8`, for each supported runtime x builder combination:

- Node runtime x Turbopack builder
- Node runtime x Webpack builder
- Bun runtime x Turbopack builder
- Bun runtime x Webpack builder

The credential is measured against one specific release tag, so once the windows move to rc.6 the
count restarts from zero for all four combinations, including nights already accumulated on rc.5.
Treat rc.6 as not yet credentialed until those runs accumulate.

Dispatched confirmation runs at Next.js `v16.3.8` passed on the cells below, every test passing:

nights will exercise them. These runs are evidence, not a substitute for the 14-night window.

## What's in this release

`@getknext/core`, `@getknext/lib`, `@getknext/db`, and the `kn-next` bin all move to `1.0.0-rc.6`
together. They are published as a set and always carry the same version number. Each package's
changelog gains an rc.6 entry.

## Known limits in this release candidate

- **v16.3.8 is not yet a completed compatibility credential.** See above.
- **The compiled single-executable Bun build target is experimental** and outside this window's
  verification scope.
- The `adapterPath` workaround turns the affected 500s into 404s that log a `NoFallbackError`; it
  does not restore the adapter's runtime behaviour on Next.js before 16.4.0, because nothing at
  runtime depends on it.
- This is a **release candidate**: expect the version number to change again before the final v1.0
  tag, and do not treat rc.6 as a long-term-support release.
