# knext v1.3.0-rc.9

**This is a release candidate on a separate line, published to the npm dist-tag `next`.** It does
not replace `1.0.0-rc.5`: the `rc` dist-tag stays on `1.0.0-rc.5`, `latest` is unchanged, and the
v1.0 compatibility credential keeps running against `1.0.0-rc.5`. The v1.0 schedule is unchanged
by this release.

This release moves new apps to Next.js 16.3.8 (a security fix), supports an app in a workspace
monorepo, quiets the default build log, adds a workaround for a Next.js bug that affects Next.js
before 16.4.0, and fixes more vinext problems. Everything else in `1.3.0-rc.8` is unchanged.

## What's new since 1.3.0-rc.8

### Security: new apps scaffold with Next.js 16.3.8

Next.js 16.0.0 through 16.3.7 have a high-severity server-side request forgery in Image
Optimization (GHSA-cjq9-62q9-8jv4), fixed in 16.3.8. The default and vinext scaffold templates now
pin Next.js 16.3.8, up from 16.3.6. An app scaffolded from an earlier release candidate is not
changed: upgrade it with `npm install next@16.3.8` (or a later 16.3.x).

The Next.js cache handler now follows Next.js 16.3.7 and later, which scope cached entries to their
source route (cache keys now start with `/route-cache/`). The revalidate window handed back to
Next.js after a scale-to-zero wake is filed under that exact key, so ISR pages generated at
request time still read fresh after a wake. After upgrading, cache entries written under the old
key shape (before Next.js 16.3.7) stay unread in Redis until their TTL expires.

### Added: an app in a workspace monorepo

Set `outputFileTracingRoot` and `turbopack.root` in the app's `next.config` to the workspace root
and `knext build` and `knext deploy` follow Next.js's nested layout,
`.next/standalone/<app path>/server.js`, everywhere they look for the server: the build, the bun
export heal, the compiled Bun executable, the generated Dockerfile and its build context (the
workspace root), and the runtime image. Only an explicit setting enables this. A tracing root that
Next.js merely inferred from a parent lockfile still stops `knext build` with an error that names
the lockfile, and that error now says how to opt in. The flat layout is unchanged byte for byte,
including the generated Dockerfile. This replaces the "not supported yet" limit stated in
`1.3.0-rc.8`.

### Changed: a quieter default build, and `knext create` names its choices

A default `knext build` no longer prints a dozen multi-line compile notes. They are folded into one
line, such as `[knext standalone-compile] 12 notes; rerun with --verbose for details`.
`knext build --verbose` (or `KNEXT_VERBOSE=1`) lists them all, and the same applies to the
`[knext compile]` lines of the vinext target. Warnings, errors and strict-mode failures still print
in full. `knext create` now names the build target and runtime it chose, defaults included, and how
to change them with `--builder` and `--runtime` or the `build` and `runtime` keys in
`knext.config.ts`.

### Fixed: a Next.js bug before 16.4.0 turned some 404s into 500s

On Next.js before 16.4.0, a route with `dynamicParams = false` could answer a burst of concurrent
prefetches for a parameter outside `generateStaticParams` with a 500 instead of a 404 whenever an
adapter was configured. Next.js fixed it in 16.4.0 and did not backport it. `knext build`,
`deploy` and `preview` now clear `adapterPath` from the standalone server's runtime configuration
(`server.js` and `.next/required-server-files.json`) when the installed Next.js is older than
16.4.0, before the Bun executable is compiled, so both runtimes ship the workaround. The adapter
only works during `next build`, so nothing at runtime depends on it. Those requests become plain
404s, as on a standalone server without an adapter, and each one logs
`Error: Internal: NoFallbackError`. On Next.js 16.4.0 or later nothing changes: the workaround is
gated on the installed Next.js version and removes itself there.

### Fixed: more vinext behaviour matches Next.js

Each of the following is a vinext patch bundled with knext until a vinext release includes it. The
upstream pull request is linked.

- **Scroll and focus after a client navigation** follow Next.js 16.3: focus stays on the link you
  clicked, the page is measured against the root `scroll-padding-top` so a sticky header no longer
  hides the top of it, a stylesheet React hoists into `<head>` no longer stops the scroll to the
  top, and an intercepted route (a modal in a parallel slot) no longer scrolls or blurs the page
  underneath ([cloudflare/vinext#3768](https://github.com/cloudflare/vinext/pull/3768)).
- **An absolute-URL `assetPrefix` with a path**, such as `https://cdn.example.com/assets`, works
  on the vinext target with both runtimes. The app also serves its client bundles at
  `/assets/_next/static/...` on its own origin, as `next start` does. Before, those requests
  returned 404 ([cloudflare/vinext#3766](https://github.com/cloudflare/vinext/pull/3766)).
- **Middleware runs before a file in `public/`** that its `matcher` covers, as with `next start`,
  with both runtimes. The file is served only if the middleware lets the request continue.
  Middleware without a `matcher` runs for every file in `public/`. Before, the server returned
  such files directly and the middleware never saw the request
  ([cloudflare/vinext#3769](https://github.com/cloudflare/vinext/pull/3769)).
- **A Pages route that returns `notFound` in an app with both `app/` and `pages/`** now renders
  `app/not-found`, as Next.js does, instead of `pages/404`. The 404 keeps the Pages route's
  `Cache-Control` ([cloudflare/vinext#3771](https://github.com/cloudflare/vinext/pull/3771)).
- **New vinext apps pin `h3` to `2.0.2`** (npm, Bun, pnpm and Yarn overrides). The `h3` that Nitro
  pins answered a malformed path such as `/%2/` with a 500 or an uncaught error; the pinned
  release answers 400.

## What this release does not claim

- **No new credentialed combinations.** knext's compatibility credential (14 consecutive green
  nightly runs of the official Next.js compatibility suite) covers four combinations: Node and Bun,
  each with Turbopack and webpack. That credential is **still in progress**, and it is being earned
  on `1.0.0-rc.5`, not on this release.
- **No vinext compatibility claim.** The vinext target is Beta and not credentialed.
- **No compatibility-count claim** is made for this release.

## Install

```sh
npm i @getknext/core@next
```

`@getknext/lib` and `@getknext/db` are installed at the same version through `@getknext/core`'s
dependencies. To run the CLI without installing:

```sh
npx -p @getknext/core@next knext --help
```

To stay on the v1.0 line instead, install `@getknext/core@rc` (`1.0.0-rc.5`).

## Upgrade notes

- **Upgrade the operator (and its CRD) first, then the CLI, once an operator release from this line
  exists (see Known issues).** This release adds no new `NextApp` field.
- **The `PrivateExposure` warning (added in `1.3.0-rc.5`) needs an operator built from the 1.3
  line.** The published operator images do not include it; upgrade the operator before relying on
  the warning.
- **The `next` dist-tag moves.** Later releases on this line will also publish to `next`. Pin an
  exact version (`@getknext/core@1.3.0-rc.9`) if you need the install to stay fixed.

## Package delta against 1.3.0-rc.8

Derived from the source diff between the two release commits. It has not been checked by
comparing the packed tarballs file by file.

- **`@getknext/lib`, `@getknext/db`, `kn-next`:** no code change beyond the version bump.
- **`@getknext/core`:** the scaffold templates (Next.js 16.3.8, the vinext `h3` pin, the
  file-tracing root), the cache handler's route-cache key, the monorepo layout handling in the
  build and deploy paths, the quieter build log, the `adapterPath` workaround, and the bundled
  vinext patches. One new internal export subpath,
  `@getknext/core/internal/standalone-adapter-path`, which is not public API. The Next.js
  development dependency moves from 16.3.6 to 16.3.8; the peer range (`>=16.0.0`) is unchanged. No new runtime dependency: `acorn` was added in
  `1.3.0-rc.7` and is unchanged.
- **Operator (not an npm package):** no operator change in this release, and no new `NextApp`
  field.

## Known issues

- **No published operator release supports this line's two new `NextApp` fields yet.** The
  operator releases (`operator-latest`, and the rolling `operator-edge`) are built from the v1.0
  line, whose CRD has neither `spec.networking.visibility` (`1.3.0-rc.4`) nor
  `spec.security.writeFree` (`1.3.0-rc.2`). A deploy that sets either field fails the deploy
  preflight with an `unknown field` error, before anything reaches the cluster. Against those
  operators:
  - **private apps cannot be deployed** (`networking.visibility: "cluster-local"` or `--private`);
  - **a vinext app in its default (not self-contained) mode fails `knext deploy`** when the CLI
    builds the image in the same run, which is the normal case, on either runtime, because the
    CLI then sets `spec.security.writeFree`;
  - **a standalone app with `storage` configured fails `knext deploy`** when the CLI builds the
    image in the same run. The preflight runs before the build and assumes the field, so building
    with `KNEXT_IMAGE_CACHE_HANDLER=0` does not avoid it. Standalone self-contained executables
    fail the same way.

  Other standalone apps deploy as before. What to do until an operator release from
  this line is published:
  - **standalone apps with `storage` or a self-contained executable:** stay on `1.0.0-rc.5`
    (`@getknext/core@rc`). On `1.0.0-rc.5`, a Node app with `cache: redis` silently uses an
    in-memory cache instead of Redis (fixed in `1.3.0-rc.2`);
  - **vinext on Bun:** use `1.3.0-rc.1`, which sets neither field. `1.0.0-rc.5` does not work for
    a vinext app created on this line, because its scaffold runs `knext vinext-patches` on install
    and that command does not exist before `1.3.0-rc.1`;
  - **vinext on Node, and standalone apps with `storage` that need this line:** there is no tested
    workaround yet.

- **A custom domain makes a private app public.** Private apps only mark the app's Knative
  Service as cluster-local. A Knative `DomainMapping` that points at that service is still routed
  through the public load balancer, even if the `DomainMapping` itself is labelled cluster-local.
  So adding a custom domain to a private app silently publishes it. Do not add a `DomainMapping`
  to a private app (an operator from this line warns about it; the published operator images do
  not yet). To reach one from outside the cluster, run a tunnel to the cluster's internal
  gateway that rewrites the `Host` header, behind an identity-aware proxy.
- **The "Edge Runtime is deprecated" warning does not yet match Next.js** on the vinext target.
  Next.js's own test for that warning still fails, so treat it as not yet fixed.
- **The vinext shebang fix from `1.3.0-rc.2` has two known limits:**
  - A byte-order mark (BOM) before the shebang line is not detected, so such a file still fails to
    build.
  - Source maps for a file whose shebang was stripped and reattached are one line off, which can
    point a debugger or stack trace at the wrong line for that file.
- **Patched Bun toolchain (experimental, opt-in `compile.bun: 'knext-patched'`):** unchanged from
  `1.3.0-rc.1`. There is no cluster-deploy proof yet, each binary's SBOM records only the file and
  its digest, the binaries are compiled on a shared build service account, and the compile step is
  about 4–5% slower than stock Bun.
