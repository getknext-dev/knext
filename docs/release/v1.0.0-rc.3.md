# knext v1.0.0-rc.3

**This is a release-candidate, not the final v1.0 — and it contains no changes to package code.**
rc.3 exists only so the v1.0 compatibility credential can be measured against a release reference
whose test harness works on every runtime x builder combination.

## Why rc.3 exists

The compatibility credential runs the official Next.js test suite nightly against a frozen release
tag, and it reads its test harness from that same tag. On the first night of the rc.2 window, both
Bun combinations failed before any test ran: Next.js v16.3.5 ships a newer version of `sharp`
(the image library) than the Bun lane's test harness had pinned native build inputs for, and the
credential mode correctly refuses to fall back to an unpinned, non-reproducible build. The Node
combinations were unaffected.

The fix is entirely inside the test harness. Because the harness is read from the release tag,
the only way to put the fixed harness in front of the credential runs is a new tag — so rc.3 is a
re-cut of rc.2 with that fix, and nothing else.

## What's in this release

`@getknext/core`, `@getknext/lib`, `@getknext/db`, and the `kn-next` bin all move to `1.0.0-rc.3`
together — they are published as a set and always carry the same version number.

The published package contents are byte-identical to rc.2 apart from version fields — the
`version` in each `package.json` and the version ranges between the four packages. This was checked
by packing both releases and diffing the tarballs. Each package's changelog also gains an rc.3
entry. The repository at the rc.3 tag additionally includes test-harness and CI changes made since
rc.2 — among them the harness fix that motivated this release — none of which ship in the
published packages. There are no behavior changes, no new features, and no fixes to
the runtime, CLI, or operator in this release. Everything described in the rc.2 release notes
applies to rc.3 unchanged.

## The credential windows restart on rc.3

v1.0 needs 14 consecutive green nightly runs of the official Next.js compatibility suite (still
against Next.js v16.3.5) for each supported runtime x builder combination:

- Node runtime x Turbopack builder
- Node runtime x Webpack builder
- Bun runtime x Turbopack builder
- Bun runtime x Webpack builder

The credential is measured against one specific release tag, so once the windows move to rc.3 the
count restarts from zero for all four combinations — including the Node ones, whose rc.2 nights do
not carry over. Treat rc.3 as not yet credentialed until those runs accumulate.

## Upgrading: install the operator before the CLI

The upgrade order is unchanged: if you run your own cluster, **upgrade the knext operator (and its
CustomResourceDefinition) first, then the CLI.** This release makes no operator or CRD change, but
the rule still applies if you are coming from an older release. A CLI newer than your installed
operator can fail with an error like:

```
strict decoding error: unknown field "spec.…"
```

If you see that error, upgrade the operator first, then retry:

```sh
kubectl apply -f https://github.com/getknext-dev/knext/releases/download/operator-latest/install.yaml
```

An operator that is *ahead* of your CLI version is always safe.

## Known limits in this release candidate

- **v16.3.5 is not yet a completed compatibility credential** — see above.
- **The compiled single-executable Bun build target is experimental** and outside this window's
  verification scope.
- This is a **release candidate**: expect the version number to change again before the final v1.0
  tag, and do not treat rc.3 as a long-term-support release.
