# knext v1.0.0-rc.1

**This is a release-candidate, not the final v1.0.** rc.1 opens a rehearsal window for the
process that will produce a fully credentialed v1.0: each supported runtime x builder combination
needs 14 consecutive green nightly runs of the official Next.js compatibility suite against a
frozen release reference before v1.0 ships. rc.1 exercises that machinery end to end; the actual
v1.0 credential is expected to land on a later release candidate (rc.2 or beyond).

## What's in this release

`@getknext/core`, `@getknext/lib`, `@getknext/db`, and the `kn-next` bin all move to `1.0.0-rc.1`
together — they are published as a set and always carry the same version number.

## Which Next.js version this is credentialed against

rc.1's nightly compatibility runs are pinned to **Next.js v16.2.12** (the latest 16.2.x release at
or above the published CVE floor). **New apps scaffolded by `knext create` still pin a newer
Next.js release (16.3.x)** — that combination has not yet completed its own compatibility runs, so
treat 16.3.x support as unverified until a later release candidate re-runs the suite against it.
See `docs/compat-matrix.md` for the full, currently-verified support matrix and how it is kept
honest (every supported row is backed by a real, re-runnable check — not just a claim in this
document).

## Runtime x builder coverage in this window

Four combinations are being run nightly against the frozen rc.1 reference:

- Node runtime x Turbopack builder
- Node runtime x Webpack builder
- Bun runtime x Turbopack builder
- Bun runtime x Webpack builder

An experimental compiled single-executable build target (Bun, bytecode-compiled) exists and is
under active development, but is not part of this rc.1 verification window.

## Upgrading: install the operator before the CLI

If you run your own cluster, **always upgrade the knext operator (and its CustomResourceDefinition)
before upgrading to this `@getknext/core` release.** A newer CLI can describe an application using
a field an older operator's CRD does not know about yet. `knext` (and its `kn-next` alias) applies
its resources with strict validation, so if you upgrade the CLI first you may see an error like:

```
strict decoding error: unknown field "spec.…"
```

If you see that error, upgrade the operator first, then retry:

```sh
kubectl apply -f https://github.com/getknext-dev/knext/releases/download/operator-latest/install.yaml
```

An operator that is *ahead* of your CLI version is always safe — you only need to avoid running a
CLI newer than your installed operator.

## Runtime environment contract

Deployed apps read a `KNEXT_BUILD_ID` environment variable identifying the specific build that
produced the running image — useful for correlating logs, traces, and dashboards back to a
specific `knext build` invocation. This is set automatically; no configuration is required.

## CLI name

The command-line tool's canonical name is `knext`. The older name `kn-next` keeps working as a
deprecated alias — it dispatches identically and prints one extra line pointing you at `knext` —
so existing scripts and CI jobs that invoke `kn-next` are not broken by this change.

## Known limits in this release candidate

- **The Next.js version pin used by newly scaffolded apps (16.3.x) is not yet part of the verified
  compatibility window** — see above. It is expected to be credentialed in a later release
  candidate.
- **The compiled single-executable Bun build target is experimental** and outside this window's
  verification scope.
- **The config file name is unchanged in this release** — a rename is planned for a later release
  candidate and will be called out explicitly with a migration note when it ships.
- This is a **release candidate**: expect the version number to change again (rc.2, etc.) before
  the final v1.0 tag, and do not treat rc.1 as a long-term-support release.
