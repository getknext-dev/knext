# knext v1.3.0-rc.8

**This is a release candidate on a separate line, published to the npm dist-tag `next`.** It does
not replace `1.0.0-rc.5`: the `rc` dist-tag stays on `1.0.0-rc.5`, `latest` is unchanged, and the
v1.0 compatibility credential keeps running against `1.0.0-rc.5`. The v1.0 schedule is unchanged
by this release.

This release fixes the first build on the documented path, adds a version line for the operator,
removes the operator's cluster-wide access to Secrets, and fixes more vinext and Bun-compile
problems found on `1.3.0-rc.7`. Everything else in `1.3.0-rc.7` is unchanged.

## What's new since 1.3.0-rc.7

### Fixed: the first build works on the documented path

After `npm i @getknext/core` followed by `knext create`, a lockfile can sit in a parent directory.
Next.js then moved its workspace root up and nested the standalone server, so the first
`knext build` failed. A scaffolded app now pins the file-tracing root to the app
(`outputFileTracingRoot`, plus `turbopack.root` on the default builder), so the build succeeds. The
vinext scaffold pins `outputFileTracingRoot` only, so `knext deploy` takes its Docker build context
from the app.

If an existing app still ends up with the nested layout, `knext build` now fails with the real
cause: it names the inferred root and the lockfile behind it, and says to set
`outputFileTracingRoot` to the app or remove the lockfile. Before, it blamed
`output: 'standalone'`, which was set correctly. A root deliberately set above the app, as in a
workspace monorepo that shares dependencies, is not supported yet, and the error and the docs say
so.

### Added: the operator has a version line, and `knext doctor` shows it

Operator releases are now tagged `operator-vX.Y.Z`. Each release publishes a digest-pinned
`install-vX.Y.Z.yaml` next to `install.yaml`, so you can pin, upgrade to and roll back to an
operator version by name. The operator's major and minor follow the package set; the patch is
independent. `operator-latest` is unchanged.

`knext doctor` has a new "Operator version" row. It reads the installed operator's version and image
digest, and warns, without failing the preflight, when the operator is older than the CLI, when the
majors differ, when the operator is an unreleased build, or when it reports no version. The
deploy-time schema preflight stays the check that decides whether a deploy proceeds.

### Changed: the operator no longer has Secrets RBAC

The operator's cluster role granted read and write on core Secrets in every namespace, and the
operator never used it. The grant is removed. An app that references Secrets by name (`envFrom`,
`spec.database`, image pull secrets) still works, because the kubelet resolves those references,
not the operator. This needs an operator built from this line; the published operator images still
carry the old grant.

### Fixed: more apps build on the vinext target

- A tsconfig `paths` entry with several targets falls back to the later targets when the first does
  not resolve, and a `.d.ts` target is never used as a module, as in TypeScript and Next.js.
- `import data from "./data" with { type: "json" }` loads the file as JSON even when it has no
  `.json` extension. It failed with a parse error before.
- A `require()` in a branch that `process.env.NEXT_RUNTIME` rules out is no longer resolved, so an
  instrumentation file that requires a module only in its non-Node.js branch no longer fails the
  build.
- A Pages Router app loads `_document` first, then `_app`, then the page modules, matching Next.js,
  so side effects at the top of a custom document run before the app's and the page's.
- `experimental.inlineCss` works for App Router apps, on both runtimes. Pages render their
  stylesheets inline in `<style>` tags instead of `<link rel="stylesheet">`, as with `next start`.
  Before, the build looked for the stylesheets in a directory that the knext build never writes.

### Fixed: the Bun compile step on vinext

`knext build --target=vinext` no longer fails or produces a binary that crashes in these cases:

- A server bundle that aliases the bare `import.meta` object no longer fails the compile with an
  "import.meta use(s) survived the rewrite" error.
- A page or route that reaches a package only through a runtime `require()` that Bun's bundler
  cannot see statically no longer compiles into a binary that crashes every request with
  `Cannot find module`.
- In a monorepo, a dependency hoisted to the workspace root and reached through a symlink is
  bundled, instead of being wrongly treated as unresolvable. An unrelated package that merely sits
  higher up on the build machine's disk is still refused.
- Code that only checks whether an optional package is installed
  (`try { require.resolve('pkg') } catch {}`) no longer fails a `--self-contained` build or one
  with `KNEXT_COMPILE_STRICT_REQUIRES=1`.

## What this release does not claim

- **No new credentialed combinations.** knext's compatibility credential (14 consecutive green
  nightly runs of the official Next.js compatibility suite) covers four combinations: Node and Bun,
  each with Turbopack and webpack. That credential is **still in progress**, and it is being earned
  on `1.0.0-rc.5`, not on this release.
- **No vinext compatibility claim.** The vinext target is Beta and not credentialed.
- **No compatibility-count claim** is made for this release.

## Install

```sh
npm i @getknext/core@next
```

`@getknext/lib` and `@getknext/db` are installed at the same version through `@getknext/core`'s
dependencies. To run the CLI without installing:

```sh
npx -p @getknext/core@next knext --help
```

To stay on the v1.0 line instead, install `@getknext/core@rc` (`1.0.0-rc.5`).

## Upgrade notes

- **Upgrade the operator (and its CRD) first, then the CLI, once an operator release from this line
  exists (see Known issues).** This release adds no new `NextApp` field.
- **The `PrivateExposure` warning (added in `1.3.0-rc.5`) needs an operator built from the 1.3
  line.** The published operator images do not include it; upgrade the operator before relying on
  the warning.
- **The `next` dist-tag moves.** Later releases on this line will also publish to `next`. Pin an
  exact version (`@getknext/core@1.3.0-rc.8`) if you need the install to stay fixed.

## Package delta against 1.3.0-rc.7

Derived from the source diff between the two release commits. It has not been checked by
comparing the packed tarballs file by file.

- **`@getknext/lib`, `@getknext/db`, `kn-next`:** no code change beyond the version bump.
- **`@getknext/core`:** the scaffold templates and the build's nested-layout check, the `knext
  doctor` operator-version row, the vinext compile step, and the bundled vinext patches. No new
  runtime dependency: `acorn` was added in `1.3.0-rc.7` and is unchanged.
- **Operator (not an npm package):** the cluster-wide Secrets grant is removed from the manager
  role, and the release scripts stamp the version label; no new `NextApp` field.

## Known issues

- **No published operator release supports this line's two new `NextApp` fields yet.** The
  operator releases (`operator-latest`, and the rolling `operator-edge`) are built from the v1.0
  line, whose CRD has neither `spec.networking.visibility` (`1.3.0-rc.4`) nor
  `spec.security.writeFree` (`1.3.0-rc.2`). A deploy that sets either field fails the deploy
  preflight with an `unknown field` error, before anything reaches the cluster. Against those
  operators:
  - **private apps cannot be deployed** (`networking.visibility: "cluster-local"` or `--private`);
  - **a vinext app in its default (not self-contained) mode fails `knext deploy`** when the CLI
    builds the image in the same run, which is the normal case, on either runtime, because the
    CLI then sets `spec.security.writeFree`;
  - **a standalone app with `storage` configured fails `knext deploy`** when the CLI builds the
    image in the same run. The preflight runs before the build and assumes the field, so building
    with `KNEXT_IMAGE_CACHE_HANDLER=0` does not avoid it. Standalone self-contained executables
    fail the same way.

  Other standalone apps deploy as before. What to do until an operator release from
  this line is published:
  - **standalone apps with `storage` or a self-contained executable:** stay on `1.0.0-rc.5`
    (`@getknext/core@rc`). On `1.0.0-rc.5`, a Node app with `cache: redis` silently uses an
    in-memory cache instead of Redis (fixed in `1.3.0-rc.2`);
  - **vinext on Bun:** use `1.3.0-rc.1`, which sets neither field. `1.0.0-rc.5` does not work for
    a vinext app created on this line, because its scaffold runs `knext vinext-patches` on install
    and that command does not exist before `1.3.0-rc.1`;
  - **vinext on Node, and standalone apps with `storage` that need this line:** there is no tested
    workaround yet.

- **A custom domain makes a private app public.** Private apps only mark the app's Knative
  Service as cluster-local. A Knative `DomainMapping` that points at that service is still routed
  through the public load balancer, even if the `DomainMapping` itself is labelled cluster-local.
  So adding a custom domain to a private app silently publishes it. Do not add a `DomainMapping`
  to a private app (an operator from this line warns about it; the published operator images do
  not yet). To reach one from outside the cluster, run a tunnel to the cluster's internal
  gateway that rewrites the `Host` header, behind an identity-aware proxy.
- **The "Edge Runtime is deprecated" warning does not yet match Next.js** on the vinext target.
  Next.js's own test for that warning still fails, so treat it as not yet fixed.
- **The vinext shebang fix from `1.3.0-rc.2` has two known limits:**
  - A byte-order mark (BOM) before the shebang line is not detected, so such a file still fails to
    build.
  - Source maps for a file whose shebang was stripped and reattached are one line off, which can
    point a debugger or stack trace at the wrong line for that file.
- **Patched Bun toolchain (experimental, opt-in `compile.bun: 'knext-patched'`):** unchanged from
  `1.3.0-rc.1`. There is no cluster-deploy proof yet, each binary's SBOM records only the file and
  its digest, the binaries are compiled on a shared build service account, and the compile step is
  about 4–5% slower than stock Bun.
