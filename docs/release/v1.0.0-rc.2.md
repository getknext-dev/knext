# knext v1.0.0-rc.2

**This is a release-candidate, not the final v1.0.** Like rc.1, rc.2 is part of the rehearsal
process that produces a fully credentialed v1.0: each supported runtime x builder combination
needs 14 consecutive green nightly runs of the official Next.js compatibility suite against a
frozen release reference before v1.0 ships.

## What's in this release

`@getknext/core`, `@getknext/lib`, `@getknext/db`, and the `kn-next` bin all move to `1.0.0-rc.2`
together — they are published as a set and always carry the same version number.

## The config file has been renamed to `knext.config.ts`

The config file has a new name: `knext.config.ts`. There is no dual-read — the CLI reads
`knext.config.ts` only, and does not fall back to the pre-rename filename.

**If your app still has the pre-rename config file, rename it before your next `knext`
command.** Running any `knext` command in a directory that still has the old file (and no
`knext.config.ts`) now fails fast with one actionable error that names the exact rename to make —
never a silent fallback read and never a warning that lets an old-named config keep working. Just
run any `knext` command and follow that error; `knext doctor` flags the same condition as a failing
check with the same instruction. `knext create` scaffolds `knext.config.ts` for new apps, and the
GitHub Action and docs site refer to `knext.config.ts` throughout.

## Request bodies are now capped on the standalone build too

Request bodies are capped in-process on every build target — Turbopack or Webpack, Node or Bun,
compiled or not. Previously only the compiled single-executable target enforced this; the
standalone build now does too.

The default cap is **8 MiB** per request body, on every route. A body larger than that is answered
with `413 Payload Too Large` and the connection is closed; the cap counts the bytes that actually
arrive, so a chunked request with no `Content-Length` header is refused as well, and an oversized
body never reaches your route handler.

**This is a behavior change if your app accepts uploads larger than 8 MiB through a route
handler.** Raise the cap before upgrading by setting `KNEXT_MAX_REQUEST_BYTES` (in bytes) in the
`env` map of `knext.config.ts`, or in `spec.env` on the `NextApp`. Setting it to `0` removes the
cap entirely (logged loudly on start so the choice is visible); an invalid value falls back to the
8 MiB default with a warning. The app prints the cap in force on start. See the hardening guide on
the docs site for the full detail, including how this differs from Next's own, separate 1 MB
Server Action body limit.

## Experimental surfaces and the stability policy

Two small surfaces that already shipped are now explicitly marked **experimental** — public, and
usable, but not yet covered by the semver policy the rest of the public API follows. Each may still
change in a minor release, and each carries a visible marker (in its types, in `--help` output, or
in the CLI reference) so the carve-out is never a surprise:

- the `selfContained` config key and `knext build --self-contained` flag (the opt-in
  single-executable build mode, whose on-disk shape is still settling), and
- the `preview` and `loadtest` directly-runnable CLI entries, whose flags and output are not yet
  part of the committed CLI contract.

Nothing else in the public API is experimental. See the public API reference on the docs site for
the full policy.

Separately, this release also documents the **exit code** for every CLI verb in the CLI reference —
previously only a handful of verbs had this written down. No exit-code behavior changed; this is a
documentation gap closed, not a new contract.

## The compile-cache build step is more robust

The build step that produces the Node standalone runtime's warm-boot cache used to fail with an
opaque "server did not answer" error for apps whose home route (or another route on the warm path)
redirects or is rewritten by middleware — for example, an app that redirects `/` to a localized or
authenticated route. That build step now waits for the server to accept a connection rather than
for a full HTTP round-trip through the app's own routing, and follows same-origin redirects on the
warm path by hand. A redirect loop is now reported as the non-2xx status it is instead of a timeout,
and a warm path that redirects to a third-party host is reported as the redirect it is rather than
followed off-cluster during the build. No runtime behavior of the deployed app changes — this is a
build-time reliability fix.

## Which Next.js version this is credentialed against

rc.2 moves the compat credential window from Next.js v16.2.12 (rc.1's reference) to **v16.3.5** —
the same release `knext create` scaffolds today, closing the gap between the two. Doing that
required individually re-verifying every existing compatibility-quarantine entry against v16.3.5
first (not just accepting that the version bump would probably be fine): all four runtime x builder
combinations were dispatched against v16.3.5 with the full test corpus. Of the twelve entries
removed from the quarantine list, eight now pass on the first attempt in every combination, and
four are no longer run because upstream Next.js itself skips those tests at v16.3.5. Two further
entries, for a Bun runtime gap, were kept: their quarantined cases were not exercised by these
runs, so there is no evidence yet that they pass.

Six upstream tests are quarantined at v16.3.5 (unrelated to the re-verification above — these are
newly introduced by upstream between the two versions). Each fails deterministically because the
part of the test that fails encodes behavior that only Vercel's own hosting infrastructure
produces — for example, a response header set by Vercel's CDN, or the order in which Vercel's
routing layer decodes a URL-encoded path segment — rather than anything a self-hosted deploy target
can or should reproduce. In every one of these cases, knext's actual behavior matches what the test
itself expects from a self-hosted deployment. These are documented with their evidence and
reasoning in the compatibility matrix, not silently skipped.

Confirmation runs at v16.3.5 have passed on all four runtime x builder combinations: the Bun
combinations in the first dispatch, and the Node combinations in follow-up runs after a fix to
knext's own build-cache verification step, which had failed on two new upstream test fixtures;
the 14 consecutive nightly runs the v1.0 credential requires are only just starting at this new
reference. See `docs/compat-matrix.md` for the current, continuously-updated evidence for each
combination.

## Runtime x builder coverage in this window

The same four combinations as rc.1 are run nightly against the frozen reference:

- Node runtime x Turbopack builder
- Node runtime x Webpack builder
- Bun runtime x Turbopack builder
- Bun runtime x Webpack builder

The default `Bun runtime x Turbopack builder` combination above is itself a compiled, bytecode
Bun executable (`runtime: "bun"` compiles the standalone server into a single executable) — it is
one of the four credentialed cells, not experimental. The `vinext` build target is a separate,
experimental single-executable build (the Vite/rolldown Next reimplementation, compiled whole via
`bun build --compile --bytecode`) that exists and is under active development, but is not part of
this verification window.

## Upgrading: install the operator before the CLI

If you run your own cluster, **always upgrade the knext operator (and its CustomResourceDefinition)
before upgrading to this `@getknext/core` release.** A newer CLI can describe an application using
a field an older operator's CRD does not know about yet. `knext` (and its `kn-next` alias) applies
its resources with strict validation, so if you upgrade the CLI first you may see an error like:

```
strict decoding error: unknown field "spec.…"
```

If you see that error, upgrade the operator first, then retry:

```sh
kubectl apply -f https://github.com/getknext-dev/knext/releases/download/operator-latest/install.yaml
```

An operator that is *ahead* of your CLI version is always safe — you only need to avoid running a
CLI newer than your installed operator.

## GitHub Packages interim channel retired

The interim `@getknext-dev/*` publish channel on GitHub Packages has been retired. It existed only
while the canonical `@getknext/*` npmjs path was believed to be blocked; that has not been true for
some time. If you were still installing from `@getknext-dev/*`, migrate to `@getknext/*` on the
public npm registry — see the installation instructions in the docs.

## CLI name

The command-line tool's canonical name is `knext`. The older name `kn-next` keeps working as a
deprecated alias — it dispatches identically and prints one extra line pointing you at `knext` —
so existing scripts and CI jobs that invoke `kn-next` are not broken by this change.

## Known limits in this release candidate

- **v16.3.5 is not yet a completed compatibility credential.** The window just moved to it; treat
  it as unverified until the required 14 consecutive nightly runs accumulate. The v16.2.12 rc.1
  evidence remains valid history but does not, on its own, cover v16.3.5.
- **The `vinext` compiled single-executable build target is experimental** and outside this
  window's verification scope. This is distinct from the default `Bun runtime x Turbopack builder`
  cell, which is also a compiled bytecode executable but is credentialed and in-scope.
- This is a **release candidate**: expect the version number to change again before the final v1.0
  tag, and do not treat rc.2 as a long-term-support release.
