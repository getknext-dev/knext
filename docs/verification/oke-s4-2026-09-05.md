## Row detail

### C-2 — the headline (crash-loop never before observed fixed)
`kubectl logs … user-container`:
```
LISTENING:3000 METRICS:9464
REQUEST_BYTE_CAP:8388608 METRICS_BYTE_CAP:65536 (default)
WARMED:/api/health status=200 ms=244
```
The app binds its metrics listener on **9464**, not 9091 — no EADDRINUSE, no queue-proxy
collision. `restartCount=0` held across a 5.5-minute watch and remains 0 on the settled pod. The
C-2 crash-loop (Finding C-2, never before observed fixed) is **fixed on OKE**. This is
runtime-attributed: the deployed operator injects no `METRICS_PORT` env, so the app's own 9464
default governs — independent of the operator's stale 9091 annotation.
Caveat: under this cluster's CPU saturation the pod was **rescheduled once** (f2q6j→stkrw, a Normal
graceful move, not OOM, restartCount stayed 0) — a scheduling artifact, not the C-2 failure mode.

### NetworkPolicy
`s4app-allow-ingress` (podSelector `serving.knative.dev/service=s4app`) admits
`8012/8013/8112` (queue-proxy), `9090` (autoscaling), **`9091`** (app metrics). The operator's own
`NetworkPolicyEnforced` condition is **False (NoPolicyController)** — "flannel … the reconciled
NetworkPolicy is declarative only — it is written but enforces NOTHING on this cluster." So the app
port is NOT reachable-only-through-queue-proxy in any enforced sense here; isolation is absent
(flannel), exactly as CLAUDE.md §7 predicts. The `9091` (vs main's 9464) is the deployed operator's
pre-#951 value.

### #951 drift is LIVE on this cluster (cross-cutting finding)
The deployed operator stamps `prometheus.io/port=9091` and admits 9091 in the NetworkPolicy, but the
app (main) **listens on 9464**. A Prometheus scraping the annotation would hit 9091 and get nothing.
This is precisely the drift #951/#963 fixes — and it is live because the operator predates the fix.
It concretely motivates the P2 upgrade-order rule (**operator/CRD first, then CLI**, #548): shipping
the 9464-runtime CLI against a 9091-stamping operator breaks metric scraping until the operator is
upgraded.

### G — byte cap (ADR-0044 Option C)
| Case | Result | Note |
|------|--------|------|
| honest 500 B POST `/` | **405** | under cap → reaches app; app has no POST handler on `/` (no 413). "→200" not literally reproducible on the stock scaffold (no 200 POST route). |
| honest 9 MiB POST `/` (Content-Length) | **413** | both via ingress and **direct against Bun** (port-forward) |
| chunked 9 MiB POST `/` (no Content-Length) | **405 (not 413)** | direct against Bun — see divergence below |
| metrics `:9464` GET `/metrics` | **200** | 2,303 B Prometheus exposition (`# HELP knext_bunexec_process_resident_memory_bytes …`) |
| metrics `:9464` POST 65 KiB `/metrics` | **413** | the fixed 64 KiB metrics cap fires |

**Divergence (chunked no-Content-Length 9 MiB → expected 413, OBSERVED 405).** Direct against the Bun
listener, a 9 MiB chunked body to `/` returned **405, not 413**. Mechanism: the stock `/` route
rejects POST **by method before reading the body**, so Bun never consumes past the cap and the
streamed-body limit never engages; the Content-Length path (declared size) is rejected up-front and
correctly 413s. So the "chunked→413" guarantee holds only for a handler that **reads** the body — it
is **not** a property of every route. Flagged for the lead: the T1/byte-cap "chunked→413" claim may
be resting on a body-reading test route, and does not generalise to a method-reject route. (Over the
Kourier ingress the same chunked request returns 400 — Envoy rejects it before Bun, a second reason
the ingress path can't verify this assertion.)
